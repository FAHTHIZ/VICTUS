# VICTUS Roadmap

Living, evidence-driven plan. Work directly on `main` in small, buildable commits. Status reflects verified repository state, never ambition.

**Current maturity (2026-11-18, through Slice 78):** a broad engine with tested runtime, editor and tooling: core runtime, SDL3 platform layer, RHI on SDL_GPU (Vulkan verified on lavapipe, Metal on CI's virtual Apple GPU), render graph, 2D sprite/tilemap renderer with 2D lights, clustered forward HDR PBR renderer (cascaded and local-light shadows, SSAO, IBL and physical sky, reflection probes, baked/dynamic irradiance volumes, TAA with motion vectors and temporal upscaling, LODs, GPU occlusion culling, projected decals, quality tiers), material assets, surface shaders and material graphs, archetype ECS, versioned scenes and prefabs, asset pipeline with cooked cache and texture compression, VICTUS Studio editor (gizmos, thumbnails, command palette, autosave/recovery, multi-selection, profiler, graph/material/sequencer/terrain tools, play-in-editor incl. multiplayer), Luau scripting and visual scripting, Jolt/Box2D physics with characters and joints, skeletal and sprite animation, CPU particles, in-game UI, miniaudio audio, Recast/Detour navigation, behaviour-tree AI with perception, heightmap terrain with foliage scatter, a timeline sequencer, save games, deterministic captures, encrypted server-authoritative multiplayer, `victus` CLI and `victus export`, and two complete sample games. **Not production-ready:** no game has shipped, no rendering on a physical GPU or phone has been measured, Windows rendering and Android devices are untested, and GPU device loss ends the session instead of recovering; native plugins (ADR-0078) are trusted code without a sandbox or hot reload. Per-subsystem maturity: [docs/KNOWN_LIMITATIONS.md](docs/KNOWN_LIMITATIONS.md); platform evidence: [docs/PLATFORM_SUPPORT.md](docs/PLATFORM_SUPPORT.md).

## Direction
VICTUS is a general-purpose engine, not an Auroria-specific one. Auroria remains a demanding showcase only. The defining visual goal is **perceptual-equivalence rendering across capable, supported hardware**: a lower-cost device may use different algorithms and representations from a high-end PC, but the final image should preserve the same visual intent and remain within tested perceptual tolerances. Reduce the cost of producing the image before reducing its visible quality. Coordinate geometry, lighting, shadows, reflections, materials, texture residency, temporal reconstruction, VFX and non-authoritative simulation rather than treating quality as a simple preset switch. Establish a realistic minimum hardware floor; do not promise flagship output on every legacy device. See [the Perceptual-Equivalence Rendering handoff](docs/handoff/VICTUS_PERCEPTUAL_EQUIVALENCE_RENDERING.md) for the whole-system objective, architecture, implementation sequence and acceptance gates.

6g. [ ] **V.A.U.L.T. (Virtual Asset & Unified Loading Technology — working codename).** A VICTUS-owned runtime resource manager, not a replacement for the existing asset database/cooker and not a third-party dependency decision. The name is provisional.
   - **Audit and contract:** map current asset UUIDs, sidecar metadata, cooked-cache dependency hashes, packaged archive access, GPU upload ownership and runtime references before designing handles. Keep source identity/import/cook in the existing assets module; define a separate runtime lifetime/residency contract. Do not expose raw backend pointers in gameplay APIs.
   - **Requests and lifetime:** add typed asynchronous request handles/leases with explicit retain/release, progress, completion, failure context, cancellation and dependency closure. Deduplicate concurrent requests; avoid synchronous disk/decode work on the frame thread; safely marshal GPU resource creation/destruction to the RHI-owning thread and account for in-flight command buffers.
   - **Residency and prioritisation:** maintain separate CPU/GPU budgets by resource class and quality tier. Add priority/deadline and prefetch hints, reference-aware eviction, recency/significance signals, hysteresis, fallback/coarser resources and memory-pressure recovery. Never evict data still referenced by a scene, job, draw in flight or gameplay/network operation.
   - **Streaming formats:** first implement texture-mip streaming with per-view projected footprint and explicit mip-chain byte accounting; then investigate mesh/geometry LOD residency, animation/pose data, audio chunks and packaged-archive range reads. Preserve compressed BC/ASTC variants where supported. Do not load every mip simply because the cooked file contains every mip.
   - **Diagnostics and safety:** expose request queues, bytes resident/pending/evictable, cache hit/miss, stalls, upload time, failed/cancelled requests, dependency chains and eviction reasons. Test stale handles, cancellation races, missing/corrupt resources, device/context generation changes, memory pressure and package parity.
   - Progress (ADR-0087, stage 1): `assets::AsyncLoader` (deduplicated per-asset slots, priority dispatch with a decode limit, byte-budgeted hand-out, cached failures, cancellation) and `GpuAssetCache::set_async_loading`: textures and models decode on Background jobs and upload under a per-frame byte budget; pending assets return `ErrorCode::Pending` and are skipped by extraction (`ExtractStats::loading_assets`); the game thread no longer runs Background jobs while it waits; the player streams in interactive runs (`--sync-assets` opts out). Stage 3 (ADR-0089): mip streaming — extraction reports each `.vmat` material texture's and decal texture's projected footprint (`projected_pixels`, scaled by UV tiling); `pump()` keeps only the levels the largest footprint needs (raises at once, drops after `mip_drop_frames`, never under `min_streamed_size`), raises only as far as the budget allows and drops top levels of in-use textures when over it; re-decodes go through the async loader; `rendering.texture_streaming`. Verified sync and async by a GPU test.

## Definition of done
A task is complete only when code is integrated on main, relevant tests pass, build commands work, errors/fallbacks are handled, platform and license limits are documented, performance claims have evidence, the diff is audited, and SHA plus verification are recorded in `docs/STATUS.md`. A demo or placeholder is not completion.

## Cross-workstream dependency order

These are planned capabilities, not a commitment to implement every feature at once. Work proceeds in small, audited, testable slices:

1. **6d audit first:** produce the source-linked subsystem matrix and re-check current main before each implementation slice. Keep hardware-blocked claims explicit.
2. **6l reliability is continuous:** begin with transactional save/migration/recovery foundations early, then maintain them across every new subsystem. Do not postpone data-safety fixes until the end.
3. **6g V.A.U.L.T. before 6h World/Scene Streaming:** world cells, audio chunks and asset prefetch must share one resource lifetime/residency manager.
4. **6i Animation Intelligence supports 6f A.R.C.:** A.R.C. research/backend prototypes may proceed, but production hybrid physical animation depends on stable pose blending, contact/IK and root-motion hand-off. Coordinate ownership; do not duplicate systems.
5. **6e A.E.G.I.S. consumes 6g/6h signals:** it coordinates approved visual/simulation/replication budgets; V.A.U.L.T. owns asset residency and World Streaming owns cell lifecycle.
6. **6j Destruction integrates with 6h/6g/6e:** fracture assets stream through V.A.U.L.T., fragments obey world-cell lifetime, and simulation/visual budgets constrain debris.
7. **6k Audio uses 6g and 6e:** streamed clips use the shared residency contract; expensive acoustic updates respect significance and low-tier budgets.

Each workstream remains incomplete until its own acceptance criteria, authoring workflow, tests, profiling, platform evidence and documentation are satisfied. Avoid parallel implementations of the same ownership boundary.

## Execution order
Follow dependency order and complete each subsystem end-to-end. If a phase is blocked by unavailable hardware, credentials or platform-holder access, document the precise blocker and continue independent work. After every verified commit, update status and immediately proceed to the next unblocked task.

# VICTUS Roadmap

Living, evidence-driven plan. Work directly on `main` in small, buildable commits. Status reflects verified repository state, never ambition.

**Current maturity (2026-11-18, through Slice 78):** a broad engine with tested runtime, editor and tooling: core runtime, SDL3 platform layer, RHI on SDL_GPU (Vulkan verified on lavapipe, Metal on CI's virtual Apple GPU), render graph, 2D sprite/tilemap renderer with 2D lights, clustered forward HDR PBR renderer (cascaded and local-light shadows, SSAO, IBL and physical sky, reflection probes, baked/dynamic irradiance volumes, TAA with motion vectors and temporal upscaling, LODs, GPU occlusion culling, projected decals, quality tiers), material assets, surface shaders and material graphs, archetype ECS, versioned scenes and prefabs, asset pipeline with cooked cache and texture compression, VICTUS Studio editor (gizmos, thumbnails, command palette, autosave/recovery, multi-selection, profiler, graph/material/sequencer/terrain tools, play-in-editor incl. multiplayer), Luau scripting and visual scripting, Jolt/Box2D physics with characters and joints, skeletal and sprite animation, CPU particles, in-game UI, miniaudio audio, Recast/Detour navigation, behaviour-tree AI with perception, heightmap terrain with foliage scatter, a timeline sequencer, save games, deterministic captures, encrypted server-authoritative multiplayer, `victus` CLI and `victus export`, and two complete sample games. **Not production-ready:** no game has shipped, no rendering on a physical GPU or phone has been measured, Windows rendering and Android devices are untested, and there is no GPU device-loss recovery, plugin SDK or localization. Per-subsystem maturity: [docs/KNOWN_LIMITATIONS.md](docs/KNOWN_LIMITATIONS.md); platform evidence: [docs/PLATFORM_SUPPORT.md](docs/PLATFORM_SUPPORT.md).

## Direction
VICTUS is a general-purpose engine, not an Auroria-specific one. Auroria remains a demanding showcase only. The defining product goal is **high-end visual quality that scales down to entry-level Android phones**: every rendering feature must have a cheap mobile path (or a documented Low-tier fallback), favour bandwidth-light techniques on tile-based GPUs, and be measured rather than assumed.

## Definition of done
A task is complete only when code is integrated on main, relevant tests pass, build commands work, errors/fallbacks are handled, platform and license limits are documented, performance claims have evidence, the diff is audited, and SHA plus verification are recorded in `docs/STATUS.md`. A demo or placeholder is not completion.

## Execution order
Follow dependency order and complete each subsystem end-to-end. If a phase is blocked by unavailable hardware, credentials or platform-holder access, document the precise blocker and continue independent work. After every verified commit, update status and immediately proceed to the next unblocked task.

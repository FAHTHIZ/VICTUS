## Research conclusions added 2026-11-16
- Unreal's public Gameplay Framework documentation demonstrates the value of a composable layer for game/session lifetime, rules/state, controllers, pawns, cameras and components. VICTUS therefore specifies its own flexible gameplay framework rather than exposing only ECS primitives.
- Godot's official 2D documentation explicitly describes a dedicated 2D renderer and physics engine plus tilemaps, particles and animation. VICTUS therefore treats 2D as a complete product track, not merely sprites drawn by the 3D renderer.
- Unreal's networking overview describes server authority as the source of truth. VICTUS adopts server-authoritative networking as the default shared-state model, with client prediction/reconciliation and impairment testing as explicit requirements.
- Khronos describes glTF 2.0 as an API-neutral runtime delivery format with scene, mesh, material, camera, skin and animation data. It is a strong import/cook interchange baseline, but does not replace VICTUS authoring or world-streaming systems.
- Khronos describes OpenXR as a royalty-free common API for AR/VR devices. XR remains an optional, evidence-gated extension after the core renderer and input model are stable.

## Research conclusions added 2026-11-16 (Slice 5)
- Scripting: Luau 0.747 (luau-lang/luau, MIT) was chosen over Lua 5.4, LuaJIT, Wren, AngelScript, C# and WASM (ADR-0008). Deciding factors: a supported sandbox (`luaL_sandbox`, read-only globals), VM interrupts for time budgets, gradual typing, a native `vector` value type, interpreter-only portability to iOS/consoles, and active releases. LuaJIT was rejected because its JIT is not permitted on iOS/consoles and its release cadence is irregular.
- Physics: Jolt Physics v5.7.0 (jrouwe/JoltPhysics, MIT) and Box2D v3.2.0 (erincatto/box2d, MIT) were verified as the latest releases on 2026-11-16 from their GitHub release pages and chosen over PhysX 5, Bullet 3 and Chipmunk2D (ADR-0009). Deciding factors: permissive licenses, active maintenance, multithreaded solvers with external task-system hooks, sensor/contact event APIs, small static builds suitable for mobile, and production use (Jolt: Horizon Forbidden West, Godot 4.4+). Open questions: cross-platform determinism cost, character controller choice (`CharacterVirtual` vs. kinematic body), mesh collider cooking in the asset pipeline.
- Physics (next slice): Box2D v3.2.0 (2026-10-19, MIT; adds double-precision large-world positions) for 2D and Jolt v5.7.0 (2026-11-14, MIT; always-deterministic simulation, samples on iOS/Android) for 3D. Box3D (announced 2026-06) noted as a younger alternative; Jolt is preferred for maturity and shipped-title track record.

## Research conclusions added 2026-11-16 (Slice 7)
- Audio: miniaudio 0.11.26 (mackron/miniaudio, public domain or MIT-0) was verified as the latest release (published 2026-10-31, GitHub releases API) and chosen over SDL3 audio, OpenAL Soft, SoLoud and proprietary FMOD/Wwise (ADR-0010). Deciding factors: single-file build with no runtime dependencies, backends for every target platform including AAudio/OpenSL ES and Web Audio, built-in decoders and spatializer, a no-device mode for deterministic headless tests, and a license that needs no attribution. Open questions: DSP effects/reverb and HRTF (miniaudio has no HRTF; Steam Audio is a candidate), Opus decoding, streaming from packed archives.

## Research conclusions added 2026-11-16 (Slice 8)
- Packaging: an owned `.vpak` format was chosen over zip (miniz/libzip) and PhysicsFS (ADR-0011) to keep the parsing surface small, keep payloads aligned for future memory mapping, verify per-entry checksums and produce byte-reproducible exports; no new dependency was added. Open questions: compression codec (LZ4 for speed vs. zstd for ratio), GPU texture compression (ASTC for mobile, BC7 for desktop, e.g. via Basis Universal/KTX2), signing, and platform bundles (APK/AAB, iOS/macOS app bundles).

## Research conclusions added 2026-11-16 (Slice 9, rendering quality)
Techniques are implemented from the published descriptions below; no third-party code was copied or added.
- Bloom: Jorge Jimenez, "Next Generation Post Processing in Call of Duty: Advanced Warfare" (SIGGRAPH 2014 Advances in Real-Time Rendering) — https://www.iryoku.com/next-generation-post-processing-in-call-of-duty-advanced-warfare/ . 13-tap downsample with Karis-average on the first mip to suppress fireflies, 3×3 tent upsample accumulated additively up the chain. VICTUS adds a soft-knee threshold so artists can keep bloom energy-preserving (threshold 0) or stylised.
- Ambient occlusion: Morgan McGuire et al., "The Alchemy Screen-Space Ambient Obscurance Algorithm" (HPG 2011) and "Scalable Ambient Obscurance" (HPG 2012) — https://research.nvidia.com/publication/2012-06_scalable-ambient-obscurance . Spiral sampling from a depth buffer with reconstructed view-space positions, followed by a depth-aware blur; VICTUS runs it at half resolution on the High tier and with distance fade so far geometry does not darken.
- Specular occlusion: Sébastien Lagarde and Charles de Rousiers, "Moving Frostbite to Physically Based Rendering 3.0" (SIGGRAPH 2014 course notes) — https://seblagarde.wordpress.com/2015/07/14/siggraph-2014-moving-frostbite-to-physically-based-rendering/ . Used to attenuate environment specular by AO and roughness.
- Environment BRDF approximation: Brian Karis, "Physically Based Shading on Mobile" (Unreal Engine blog, 2014) — https://www.unrealengine.com/en-US/blog/physically-based-shading-on-mobile . Analytic fit chosen over a BRDF LUT to save a texture fetch on mobile.
- Cascaded shadows: Fan Zhang et al., "Parallel-Split Shadow Maps" (GPU Gems 3, ch. 10) — https://developer.nvidia.com/gpugems/gpugems3/part-ii-light-and-shadows/chapter-10-parallel-split-shadow-maps-programmable-gpus . Practical split scheme (logarithmic/uniform blend, lambda 0.8), texel-snapped bounding spheres to stop shimmering, cascades packed into one 2×2 atlas.
- Anti-aliasing: Timothy Lottes, "FXAA" (NVIDIA white paper, 2009; FXAA 3.11 quality preset) — https://developer.download.nvidia.com/assets/gamedev/files/sdk/11/FXAA_WhitePaper.pdf . Luma stored in alpha by the tonemap pass.
- Tonemapping: Khronos PBR Neutral tone mapper — https://github.com/KhronosGroup/ToneMapping/tree/main/PBR_Neutral (spec published under Apache-2.0; VICTUS implements the formula), Stephen Hill's ACES fitted curve (BakingLab, MIT, formula only), and extended Reinhard. Auto exposure follows the log-average luminance method with exponential adaptation (Reinhard et al. 2002, "Photographic Tone Reproduction for Digital Images").
- Open questions: TAA/TSR (needs motion vectors and jitter — next rendering slice), clustered lighting beyond 16 point lights, reflection probes, and measured timings on real mobile GPUs (only llvmpipe CPU numbers exist today).

## Research conclusions added 2026-11-16 (Slice 11, characters and joints)
No third-party code was added; Jolt 5.7.0 was already a dependency.
- Jolt `CharacterVirtual` class reference — https://jrouwe.github.io/JoltPhysics/class_character_virtual.html . It has no rigid body and moves by collision checks only, it is updated by the application, `ExtendedUpdate` combines `Update`, `StickToFloor` and `WalkStairs`, and `mInnerBodyShape` makes the character visible to the simulation. VICTUS uses all of these; velocity handling follows Jolt's `CharacterVirtualTest` sample in the 5.7.0 source.
- Jolt architecture documentation, constraints section — https://jrouwe.github.io/JoltPhysics/index.html . Constraint types (fixed, point, distance, hinge, slider), motors with force/torque limits, breakable constraints by checking total lambda after each step and calling `SetEnabled(false)`, the fact that bodies do not track their constraints (VICTUS removes constraints before bodies), and `GroupFilter` for skipping collisions between connected bodies.
- Open questions: ~~ragdolls (swing-twist + `GroupFilterTable`)~~ (done, ADR-0091), Box2D 3.2 joints and a 2D character mover, and parallel character updates.

## Research conclusions added 2026-11-16 (Slice 12, skeletal animation)
No third-party code was added; cgltf 1.15 was already a dependency.
- glTF 2.0 specification, sections 3.7.3 Skins and 3.11 Animations — https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html . Joint order matches `inverseBindMatrices` (identity when absent); `JOINTS_n`/`WEIGHTS_n` sets give up to four influences each and implementations may support only one set; the skinned vertex matrix is the weighted linear sum of joint matrices and the transform of the node holding the skinned mesh must be ignored; animation outputs clamp outside the input range; LINEAR rotations use shortest-path slerp and CUBICSPLINE rotations must be normalized; glTF does not define playback order or looping, which VICTUS adds in the `Animator`. VICTUS follows all of these, keeps the top four influences across sets 0–1, and skips `weights` (morph) channels.
- Open questions: blend trees/state machines, root motion extraction, dual-quaternion skinning, and a compact pose buffer for large crowds.

## Research conclusions added 2026-11-16 (Slice 14, 2D characters and joints)
No third-party code was added; Box2D 3.2.0 was already a dependency.
- Box2D v3.2.0 `samples/geometric_mover.cpp` and `include/box2d/collision.h`/`world.h` — https://github.com/erincatto/box2d/tree/v3.2.0/samples . The geometric mover collects collision planes with `b2World_CollideMover`, solves a position correction with `b2SolvePlanes`, sweeps the remaining delta (`b2World_CastMover`) and clips velocity with `b2ClipVector`. VICTUS follows that loop but sweeps with `b2World_CastShape` so it can skip sensors, itself and rejected one-way platforms per hit, and takes plane contact points from `b2Shape_GetClosestPoint`, because `b2PlaneResult.point` lies on the mover's core segment rather than the surface, which is not usable for "is the character above this platform".
- Box2D v3.2.0 `samples/dynamic_mover.cpp`, `samples/sample_character.cpp` (one-way elevator) and `b2PreSolveFcn` in `types.h`/`world.h` — same tree. One-way collision for rigid bodies uses pre-solve (enable the contact only when the normal points up and the body is not already deep inside); it requires `enablePreSolveEvents` on the shape and is called from worker threads, so the callback must be thread-safe (VICTUS keeps flags in shape user data only).
- Open questions: 2D step-up for small ledges, 2D ragdolls/soft bodies, and polygon/chain colliders for terrain.

## Research conclusions added 2026-11-16 (Slice 13, particles)
No third-party code was added.
- Tristan Lorach, "Soft Particles" (NVIDIA white paper, 2007) — https://developer.download.nvidia.com/whitepapers/2007/SDK10/SoftParticles_hi.pdf . Compare each particle fragment's depth with the scene depth read as a texture, fade with the scaled, saturated difference, and discard fragments behind the scene. VICTUS reconstructs linear view depth from the depth buffer (`proj[3].z / (d + proj[2].z)` for its 0..1 right-handed projection) and fades over the emitter's `softness` in metres.
- Open questions: GPU simulation with compute and indirect draws, depth-buffer collisions, trails/ribbons, flipbook animation with motion vectors, and lit particles.

## Research conclusions added 2026-11-16 (Slice 16, navigation)
- Recast & Detour 1.6.0 — https://github.com/recastnavigation/recastnavigation/releases/tag/v1.6.0 ; build pipeline from `RecastDemo/Source/Sample_SoloMesh.cpp` (heightfield → walkable filters → compact heightfield → erosion → distance field/watershed regions → contours → poly mesh → detail mesh → `dtCreateNavMeshData`). Voxel parameters are converted as `walkableHeight = ceil(h/ch)`, `walkableClimb = floor(climb/ch)`, `walkableRadius = ceil(r/cs)`; polygon vertex indices are 16-bit, so one tile holds < 65 535 vertices.
- DetourCrowd (`DetourCrowd/Include/DetourCrowd.h`, CrowdTool sample) — agent parameters `collisionQueryRange = 12 r`, `pathOptimizationRange = 30 r`, separation weight 2 and the four obstacle-avoidance quality presets used by the sample; agents are moved by `dtCrowd::update`, and external positions are applied with `dtPathCorridor::movePosition`.
- Triangles are walkable when `cross(v1 - v0, v2 - v0)` points up (`rcMarkWalkableTriangles`), so collider triangles are wound outward from the convex shape's center.
- Open questions: tiled/background rebuilds for open worlds (DetourTileCache), off-mesh links for jumps and ladders, area costs, 2D (top-down/platformer) navigation.

## Research conclusions added 2026-11-17 (Slice 42, tilemaps)
- Godot, "Using TileSets" (https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html, accessed 2026-11-17): a TileSet atlas is created from a texture grid of a fixed tile size; collision comes from physics layers with per-tile polygons; terrain sets match corners and sides, corners, or sides, with `-1` for empty neighbours. Adopted: grid atlas (`columns`/`rows`), per-tile collision kinds, side-matching terrains with `-1` for unset entries. Deferred: per-tile polygons and corner matching.
- Unity, "Tilemap Collider 2D component reference" (https://docs.unity3d.com/Manual/tilemaps/work-with-tilemaps/tilemap-collider-2d-reference.html, accessed 2026-11-17): tile collision shapes are generated per tile and can be merged through a Composite Collider 2D. Adopted: VICTUS merges solid cells into rectangles on one static body by default.
- Open questions: chunked drawing with camera culling for very large maps, slopes, animated tiles, corner-aware (47-tile) terrains.

## Research conclusions added 2026-11-17 (Slice 41, procedural meshes and helper processes)
- Unity `Mesh.SetVertexBufferData` (https://docs.unity3d.com/ScriptReference/Mesh.SetVertexBufferData.html, accessed 2026-11-17): copies packed vertex data directly into a vertex buffer whose layout was declared first with `SetVertexBufferParams`, with minimal validation for speed. Adopted: VICTUS `set_mesh_data` takes a declared `layout` string and decodes packed buffers in C++.
- Godot `ArrayMesh` (https://docs.godotengine.org/en/stable/classes/class_arraymesh.html, accessed 2026-11-17): `add_surface_from_arrays` builds a surface from vertex, normal, colour, UV and optional index arrays; front faces wind clockwise. Adopted as the table form of `set_mesh_data`; winding is explicit (`flip_winding`, mirrored `scale`) because source engines differ.
- Open questions: mesh colliders from procedural data, saving procedural meshes into scenes, bridges in multiplayer editor clients.

## Research conclusions added 2026-11-17 (Slice 40, pixel-art texture filtering)
- Unity, "Default texture Import Settings window reference" (https://docs.unity3d.com/Manual/texture-type-default.html, accessed 2026-11-17): Filter Mode is a per-texture import setting; Point (no filter) "appears blocky up close", Bilinear "appears blurry up close". Adopted: the filter lives in VICTUS texture import settings (ADR-0039).
- Godot, CanvasItem (https://docs.godotengine.org/en/stable/classes/class_canvasitem.html, accessed 2026-11-17): `texture_filter` is "the filtering mode used to render this CanvasItem's texture(s)"; nearest "reads from the nearest pixel only". Considered and rejected as the primary switch (per-sprite setting repeats across every sprite of a sheet); VICTUS keeps a per-sprite `nearest` flag only at the render level.

## Research conclusions added 2026-11-17 (Slice 39, sprite sheets and sprite animation)
- Godot `Sprite2D` — https://docs.godotengine.org/en/stable/classes/class_sprite2d.html (accessed 2026-11-17): `hframes`/`vframes` are the columns and rows of a sprite sheet and `frame` the cell shown; `region_rect` draws a region of an atlas texture. VICTUS adopts the same grid model (`columns`, `rows`, frames numbered row by row) and exposes the region as `Sprite.uv`.
- Godot `SpriteFrames` — https://docs.godotengine.org/en/stable/classes/class_spriteframes.html (accessed 2026-11-17): a resource of named animations, each with frames, a playback speed in frames per second and a loop mode (none, linear, ping-pong). VICTUS sheets hold named clips with frame lists, fps and a loop flag; ping-pong is expressed by listing frames (`[0,1,2,1]`) and per-frame durations by repeating frames.
- Open questions: packed (non-grid) atlases with per-frame rectangles, per-frame events, half-texel insets or nearest filtering for pixel art, Aseprite import.

## Research conclusions added 2026-11-17 (Slice 38, scene transitions)
- Godot `SceneTree.change_scene_to_file` — https://docs.godotengine.org/en/stable/classes/class_scenetree.html (accessed 2026-11-17): the outgoing scene is removed immediately and the new scene is added at the end of the frame. VICTUS also defers the switch, but keeps the outgoing scene fully alive until the end of the update so the rest of the frame's scripts see a consistent world.
- Unity `SceneManager.LoadScene` — https://docs.unity3d.com/ScriptReference/SceneManagement.SceneManager.LoadScene.html (accessed 2026-11-17): a single-mode load completes in the next frame, not immediately, and unloads unused assets. VICTUS applies the switch at the end of the calling update and validates the target before accepting the request, so a bad path fails at the call site instead of a frame later.
- Open questions: additive/streamed scenes, asynchronous loading with progress, persistent entities across scenes, built-in fade transitions.

## Research conclusions added 2026-11-17 (Slice 37, material instances)
- Unreal Engine, "Instanced Materials" — https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-materials-in-unreal-engine (accessed 2026-11-17): instances inherit all attributes from a parent and look identical until edited; only parameterised attributes are editable; constant instances are fixed before run time, dynamic instances are created from scripts. ## Research conclusions added 2026-11-17 (Slice 33, material assets)

- Open questions: material graphs and project-authored shaders, triplanar mapping, per-texture sampler overrides, material instances (parent + overrides).

## Research conclusions added 2026-11-17 (Slice 29, state digests)
- Factorio Friday Facts #55 — https://www.factorio.com/blog/post/fff-55: multiplayer runs a "heuristic CRC" every tick, "incomplete but very fast", over a few crucial values (players, active entity count, production statistics); full-state CRCs are a slower debugging mode. Factorio Friday Facts #47 — https://factorio.com/blog/post/fff-47: replays save state with human-readable tags at the first diverging tick, where "the difference is usually very small - typically just a value of one variable". VICTUS follows both: probes choose the state that matters and every line stays readable, so the first divergent digest names the variable.
- Photon Quantum, "Debugging Desyncs" — https://doc.photonengine.com/quantum/v1/community-wiki/knowledge-base/debugging_desyncs: checksums recorded after individual systems show which step desynced (e.g. after `PhysicsSystemPre`), and frame dumps are diffed between clients. VICTUS tags lines by subsystem (`script.*`, `physics.*`) rather than hashing per system, which gives the step and the value in one report.
- Open questions: probing nested script tables and entity references, cost of probes on very large scenes, and sharing the probe format with networked desync checks.

## Research conclusions added 2026-11-17 (Slice 28, reconnect)

## Research conclusions added 2026-11-17 (Slice 27, listen servers)
- Valve Developer Community, Source Multiplayer Networking — https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking: the server is authoritative over simulation, rules and input; entity interpolation adds 100 ms of view delay even on a listen server, and low latency is an advantage that prediction and lag compensation only reduce. VICTUS keeps one authoritative world for the host and gives the host no prediction or interpolation (it reads the authoritative state directly).
- Edgegap glossary, "Listen Server" — https://edgegap.com/glossary/listen-server: a listen-server game has three roles (server, remote client, host) and code written for two often misses the third; the host's inputs never cross the network, so playtesting as host hides remote-player problems; the match ends when the host leaves unless host migration exists; the host's frame rate sets the pace for everyone. VICTUS therefore models the host as a server-owned character (same script code path as offline: `net.authority()` and `is_local()` are true), lists it as id 0 so scoreboards include it, and keeps `victus serve` for fair or long-running sessions.
- Open questions: host migration, NAT traversal or relays for internet play, ticking the server at a fixed rate independent of the host's render frame rate.

## Research conclusions added 2026-11-17 (Slice 26, session security)
- The Noise Protocol Framework — https://noiseprotocol.org/noise.html: handshake patterns built from DH tokens; NX (`-> e  <- e, ee, s, es`) gives an anonymous initiator and a responder that transmits and proves its static key; a running hash of the transcript is authenticated. Adopted the NX shape and the transcript hash.
- Stratum V2 protocol security — https://stratumprotocol.org/specification/04-protocol-security/: a production protocol using Noise NX for the same client/server trust model (clients verify the server they connect to; servers do not authenticate clients in the handshake), terminating the session on any MAC failure. Supported choosing NX over XX.
- Monocypher — https://monocypher.org/: XChaCha20-Poly1305, BLAKE2b, X25519, EdDSA; under 2000 lines, no dependencies, CC0-1.0 or BSD-2-Clause. Chosen library.
- libsodium documentation — https://doc.libsodium.org/: portable NaCl fork, ISC licence, broad platform support. Rejected for build size, kept as the fallback if more primitives are needed.
- Open questions: player identity/accounts without a mandatory backend, rekeying, NAT traversal and relays.

## Research conclusions added 2026-11-17 (Slice 25, divergence reports)
- Factorio wiki "Desynchronization" — https://wiki.factorio.com/Desynchronization: a desync report keeps both the player's and the server's copy of the game state; it records the state at the desync rather than the cause, and its files can be compared with text diff tools. Informed keeping the hashed state lines inside the capture.
- Factorio Friday Facts #47 — https://factorio.com/blog/post/fff-47: a replay that checks the CRC every tick stops at the first desynchronized tick, where the difference is typically just one variable; human-readable tags make the diff usable. Informed reporting the first diverging digest with named entities and readable values.
- Factorio Friday Facts #55 — https://factorio.com/blog/post/fff-55: a cheap "heuristic" CRC of crucial state runs every tick, with full-state checks reserved for debugging. Informed keeping the digest interval at 60 frames with optional detail.

## Research conclusions added 2026-11-16 (Slice 24, regression captures)
- Gaffer On Games "Deterministic Lockstep" — https://gafferongames.com/post/deterministic_lockstep/: the same initial condition and inputs must give exactly the same result; a checksum of the physics state at the end of each frame would be identical; determinism on one machine/binary/OS does not imply it across compilers, OSes or architectures, or even between debug and release. Informed digests every N frames and the cross-platform caveat (our Debug and Release builds did match on this machine).
- Luau standard library — https://luau.org/library: `math.randomseed(seed)` makes later `math.random` calls a deterministic sequence that depends only on the seed (the VM's default seed varies per run). Informed `HostOptions::random_seed`; Luau's implementation takes a 32-bit integer, so the 64-bit capture seed is folded.
- Open questions: cross-platform float determinism of Jolt/Box2D builds, digesting script state, capture of networked sessions.

## Research conclusions added 2026-11-16 (Slice 23, delta snapshots)
- Quake 3 network model (Fabien Sanglard's source review) — https://fabiensanglard.net/quake3/network.php: snapshots are diffed against the last one the client acknowledged; when an update or ack is lost the server keeps using the older acknowledged baseline, so the next packet carries old and new changes; with no usable baseline it diffs against a zeroed dummy snapshot. Adopted directly.
- Gaffer On Games "Snapshot Compression" — https://gafferongames.com/post/snapshot_compression/: encode relative to the most recent acknowledged snapshot; quantize positions (512 values/m) and orientations with smallest-three (29 bits absolute, ~23 bits as deltas). Informed the millimetre quantization; smallest-three and bit packing deferred.
- Open questions: bit packing vs varints measured on real game scenes, per-entity baselines when the newest ack is missing, compressing reliable variable diffs.

## Research conclusions added 2026-11-18 (animation controllers, ADR-0068)
- Rune Skovbo Johansen, "Automated Semi-Procedural Animation for Character Locomotion" (MSc thesis, Aarhus 2009) sec. 6.3 — https://runevision.com/thesis/rune_skovbo_johansen_thesis.pdf (accessed 2026-11-18): gradient-band interpolation; each example's influence is the minimum over the others of a linear falloff along the vector between them, clamped at zero and normalized. Exact at examples, smooth, defined everywhere. Adopted for 2D blend spaces (Cartesian variant).
- Unity forum answer on 2D blend weights — https://discussions.unity.com/t/how-weights-of-2d-blending-are-calculated/167823 (accessed 2026-11-18): Unity's Freeform Cartesian 2D blend type uses that gradient-band method. Confirms it is production-proven for locomotion.
- Godot AnimationNodeBlendSpace2D — https://docs.godotengine.org/en/4.7/classes/class_animationnodeblendspace2d.html (accessed 2026-11-18): blends with triangles (auto-triangulated); points outside the triangulation snap to the nearest edge. Considered; gradient bands need no triangulation and need no special handling outside the hull.
- Unity Manual, Animation transitions (6000.6) — https://docs.unity3d.com/Manual/class-Transition.html (accessed 2026-11-18): exit time is the source state's normalized time; on looping states exit times below 1 are evaluated every loop and true only on the frame they are crossed, exit times above 1 once; with conditions, all must hold; any-state transitions are queued first. Adopted the exit-time and ordering semantics; per-transition interruption sources are not offered (the destination's transitions always may interrupt).
- Godot AnimationMixer (stable) — https://docs.godotengine.org/en/stable/classes/class_animationmixer.html (accessed 2026-11-18): `root_motion_track` names the node; its position/rotation/scale are "canceled visually" so the animation stays in place, and `get_root_motion_position()`/`get_root_motion_rotation()` return per-frame deltas the game applies, e.g. `velocity = rotation * root_motion_position / delta` into a `CharacterBody3D`. Informed reporting the delta (not only applying it) and the Luau `entity:root_motion()` usage with `move_character`. Godot warns its accumulator values jump when a clip loops; VICTUS unwraps the cycle instead.
- Unity Manual, How Root Motion works (6000.6) — https://docs.unity3d.com/Manual/RootMotion.html (accessed 2026-11-18): each frame the change of the Root Transform (the body projected onto the ground plane) is applied to the GameObject; "Bake Into Pose" keeps Y position (most clips), XZ (idles, avoids drift) or rotation in the pose instead. Generic rigs use a chosen Root Node. Informed the defaults: XZ travel and yaw become motion, Y stays in the pose, a controller-level `root_node`, and per-state opt-in so idles never drift.
- Open questions: layered/additive blending with masks, sync markers (foot phase) instead of normalized-time sync, sub-state machines, root motion on 2D blend spaces with turning clips (the yaw/travel coupling is approximated per clip), root motion through physics bodies other than script-applied CharacterController moves.

## Research conclusions added 2026-11-18 (A.R.C. — physics-driven character behaviour)

### Public references and findings

- **Rockstar / NaturalMotion — separate engine and behaviour layers.** Rockstar's 2011 *Asked & Answered* says the updated RAGE version included Rockstar's updated physics and graphics engines, while Euphoria was its character-behaviour system; Rockstar describes the two as working closely together. Take-Two's 2009 *Red Dead Redemption* announcement likewise names RAGE and NaturalMotion's Euphoria as distinct technologies used together. This is the important architectural lesson: character behaviour is a specialised system integrated with the engine's physics, animation and gameplay—not simply the name of the physics solver. Public material describes capabilities, not Euphoria's complete implementation. References: https://www.rockstargames.com/newswire/article/ak14o88381o725/asked-answered-max-payne-3-la-noire-red-dead-and-more.html ; https://ir.take2games.com/static-files/53773798-9091-42f8-bb65-6bda2b26b4a3 .

- **Jolt Physics 5.7.0 — the current VICTUS backend already contains a useful ragdoll foundation.** The exact pinned v5.7.0 source has RagdollSettings and Ragdoll, skeleton/pose support, GetPose/SetPose, DriveToPoseUsingKinematics and DriveToPoseUsingMotors. The version-pinned sample guide demonstrates a humanoid ragdoll whose constraint motors track a sprint animation in local space, maps a high-detail animation skeleton to a lower-detail ragdoll skeleton and maps the simulated pose back; it also demonstrates many ragdolls sleeping when inactive. References: https://github.com/jrouwe/JoltPhysics/blob/v5.7.0/Jolt/Physics/Ragdoll/Ragdoll.h ; https://github.com/jrouwe/JoltPhysics/blob/v5.7.0/Docs/Samples.md ; https://jrouwe.github.io/JoltPhysics/class_ragdoll.html . The public Jolt API reference may track upstream master, so implementation work must use the repository's pinned v5.7.0 source as the contract.

- **Unreal Engine — physics-driven animation as a practical authoring reference.** Epic documents blending physical simulation with keyframed skeletal animation, including activating simulation for a bone subtree and controlling the blend weight between animation and physics. This is a useful baseline for partial-body blending and editor-facing physics assets, but it is not by itself a complete balance/recovery controller. Reference: https://dev.epicgames.com/documentation/unreal-engine/physics-driven-animation-in-unreal-engine .

- **NVIDIA PhysX 5.7 — reduced-coordinate articulations as a comparison candidate.** PhysX documents articulations for ragdolls and other linked mechanisms. The reduced-coordinate representation uses a root pose plus joint coordinates and is designed to avoid joint error by construction and handle larger link mass ratios; it has tree/loop constraints and stability-tuning considerations, including damping and velocity limits. This merits a controlled benchmark, not an automatic backend replacement. Reference: https://nvidia-omniverse.github.io/PhysX/physx/5.7.0/docs/Articulations.html .

- **Physics-based character animation review (2023).** Llobera and Charbonnier survey motor-control principles and physics-based character-animation controllers, describing control of simulated articulated bodies through forces and torques. The review identifies interactive adaptation to perception and rich environmental contacts as continuing challenges. Reference: https://doi.org/10.1016/j.plrev.2023.06.012 .

- **DeepMimic (2018).** Peng et al. combine reference-motion imitation and task objectives to train physically simulated characters that adapt to disturbances and learn recovery behaviours. This is a research direction for a later optional controller-training pipeline, not a prerequisite for the initial engine implementation. Reference: https://arxiv.org/abs/1804.02717 .

- **AMP — Adversarial Motion Priors (2021).** Peng et al. use unstructured motion clips to learn a style prior for physically simulated characters, allowing a reinforcement-learning controller to select and combine behaviours without hand-authoring a clip-selection objective for every motion. This is a candidate for later offline training and must be evaluated against simpler controllers, runtime cost and motion-data rights. Reference: https://arxiv.org/abs/2104.02180 .

### VICTUS-specific conclusion

VICTUS currently pins Jolt 5.7.0 and exposes rigid bodies, character capsules, fixed/point/hinge/slider/distance joints and velocity motors through its own physics API. Its public physics wrapper does not yet expose Jolt ragdolls, skeletal ragdoll mapping, pose-driven joint motors or active balance/recovery. The roadmap's physics phase also still lists ragdolls as unfinished. Therefore A.R.C. should first wrap and test the pinned Jolt ragdoll capability behind VICTUS-owned types, then build the character controller and authoring workflow above it. A solver alone will not make a character behave intelligently: physical animation, posture/balance control, contact-aware response, environment interaction and recovery are separate layers.

Do not replace Jolt with PhysX merely to obtain articulation terminology or assume that reduced-coordinate simulation automatically provides lifelike behaviour. Benchmark actual VICTUS rigs and game workloads first. Keep the first runtime deterministic where practical, budgeted for mobile, and useful without machine-learning inference; evaluate learned motion policies only after a stable baseline exists. Treat Euphoria as a capability and integration reference, not a source-code target or a claim of equivalent results.

### Open research and validation questions

- Which Jolt 5.7.0 constraints and drive modes produce stable character rigs across the intended mass and scale ranges?
- What body proxies, joint limits and collision filters are robust for soft-bodied humanoids as well as the current hard-surface Vanguard starter characters?
- Which balance controller provides a good trade-off between believable stepping/bracing, controllability, determinism and CPU cost?
- How should high-detail render skeletons map to compact simulation rigs without visible foot, hand or root drift?
- How should character simulation tiers behave in headless/server and multiplayer sessions, where authoritative simulation must not depend on client camera visibility?
- What are the acceptable per-character CPU, memory and update-rate budgets on desktop and physical Android hardware?
- Which original or appropriately licensed motion datasets are available if offline policy training is later justified?


## Research conclusions added 2026-11-18 (runtime resource streaming, world partitioning, budgets, animation, destruction, audio and recovery)

The research below informs roadmap priorities 6e and 6g–6l. Public engine documentation is used for design comparison only; no proprietary implementation or code is copied.

### V.A.U.L.T. — runtime asset loading, lifetime and residency

- **VICTUS baseline (main, 2026-11-18):** the assets module already provides stable UUIDs, sidecar metadata, a cooked cache whose header includes source/importer/settings/dependency hashes, packaged asset indexes and archive support. Cooked textures contain mip chains and compressed variants; AssetDatabase can import and synchronously load cooked textures/models. These are useful source/cook foundations, but they do not amount to a unified runtime request-handle, priority, reference-lifetime and eviction manager. Checked KNOWN_LIMITATIONS.md and the asset database/cooked API declarations.
- **Unreal Asset Manager** — https://dev.epicgames.com/documentation/unreal-engine/asset-management-in-unreal-engine (accessed 2026-11-18): primary assets and streamable handles provide discovery, asynchronous loading and explicit retention. Lesson: make resource lifetime visible in the API instead of exposing untracked pointers.
- **Unreal Asynchronous Asset Loading** — https://dev.epicgames.com/documentation/unreal-engine/asynchronous-asset-loading-in-unreal-engine (accessed 2026-11-18): requests complete through handles/callbacks and work with cooked data as well as development data. Lesson: editor and packaged runtime should share the request contract; avoid main-thread blocking and define cancellation/completion ownership.
- **Unreal Texture Streaming Overview** — https://dev.epicgames.com/documentation/en-us/unreal-engine/texture-streaming-overview-for-unreal-engine (accessed 2026-11-18): desired mip levels are selected from view/texture needs, a memory pool constrains residency, and priority influences allocation. Lesson: mip streaming is a budgeted residency system, not simply selecting lower mips while keeping all mips resident.
- **Godot ResourceLoader** — https://docs.godotengine.org/en/latest/classes/class_resourceloader.html (accessed 2026-11-18): threaded loading, progress reporting, path/UID references and cache modes provide useful public API comparisons.
- **Conclusion:** create VICTUS-owned typed handles/leases, dependency closure, cancellation, reference-aware eviction, separate CPU/GPU budgets, staged decode/upload, per-view mip demand, safe GPU in-flight lifetime and telemetry. Expand into mesh, animation, audio and archive streaming only after the texture path is measured. No loader library/storage format is selected.

### World/scene streaming and persistent environments

- **VICTUS baseline:** the scene API currently serializes and loads complete scenes; KNOWN_LIMITATIONS.md explicitly lists no additive/streamed scene loading. Stable entity UUIDs, hierarchy, prefabs, terrain and navigation are foundations, but streamed cell ownership, cross-cell references and persistence semantics are not established.
- **Unreal World Partition** — https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition-in-unreal-engine (accessed 2026-11-18): a persistent world is divided into runtime grid cells that load/unload around streaming sources. Lesson: model streaming as world data and dependency relationships, not only as a renderer distance check.
- **Unreal World Partition Data Layers** — https://dev.epicgames.com/documentation/en-us/unreal-engine/world-partition---data-layers-in-unreal-engine (accessed 2026-11-18): data layers support editor/runtime grouping and can be enabled/disabled for gameplay events and world states. Lesson: spatial cells and logical gameplay layers solve different problems and should compose.
- **Conclusion:** define versioned cell descriptors, persistent non-spatial content, multiple streaming sources, prefetch/hysteresis, explicit cross-cell UUID resolution, per-cell save state and clear loaded/hibernated/unloaded simulation rules. Use V.A.U.L.T. for dependencies and resource lifetimes. No proprietary grid implementation or external world-partition dependency is selected.

### A.E.G.I.S. — independent visual, simulation and replication budgets

- **VICTUS baseline:** current A.E.G.I.S. work already includes screen-space geometry LOD, camera/view sensitivity, Hi-Z culling, terrain chunk LOD and instanced foliage. Remaining work includes persistent instance buffers/GPU-driven foliage paths, stable transitions, residency and physical hardware measurement. Existing gameplay/network systems remain authoritative and must not become visibility-dependent.
- **Unreal Mass Gameplay LOD** — https://dev.epicgames.com/documentation/unreal-engine/overview-of-mass-gameplay-in-unreal-engine (accessed 2026-11-18): documents separate representation/visual, simulation and per-client replication LOD outputs; simulation can use variable-frequency updates while replication relevancy is viewer-specific. Lesson: a single distance/visibility LOD is the wrong abstraction for all engine systems.
- **Unreal Animation Budget Allocator** — https://dev.epicgames.com/documentation/unreal-engine/animation-budget-allocator-in-unreal-engine (accessed 2026-11-18): allocates animation work against a CPU time budget and adjusts update behavior by significance. Lesson: expose measurable budgets and decisions, not a hard-coded far-distance switch.
- **Conclusion:** A.E.G.I.S. should become a significance/budget coordinator with separate visual, simulation cadence and replication relevance policies, using gameplay importance and anti-starvation guarantees. Camera visibility alone must never stop authoritative simulation. It consumes resource/world streaming signals; it does not own those managers.

### Animation Intelligence

- **VICTUS baseline:** state machines, 1D/2D blend spaces, controller layers, two-bone/FABRIK/look-at IK, bone-name retargeting, root motion and animated glTF morph targets already exist. Current documented gaps include binary masks instead of weighted per-bone masks, no layer sync, no joint limits or chain pole, limited contact-aware retargeting, root motion restricted to horizontal travel/yaw, and CPU-side morph deformation without per-vertex motion vectors.
- **Unreal Motion Matching** — https://dev.epicgames.com/documentation/en-us/unreal-engine/motion-matching-in-unreal-engine (accessed 2026-11-18): searches a motion database using pose/trajectory queries and can complement rather than replace conventional state machines. Lesson: motion matching is an optional animation path with database size, query cost and content requirements.
- **Unreal IK Rig and IK Retargeting** — https://dev.epicgames.com/documentation/unreal-engine/unreal-engine-ik-rig ; https://dev.epicgames.com/documentation/unreal-engine/ik-rig-animation-retargeting-in-unreal-engine (accessed 2026-11-18): authorable solvers and rig-to-rig retarget workflows can preserve hand/foot targets with IK. Lesson: runtime solvers alone are not a complete creator workflow; rig mapping and diagnostics matter.
- **Unreal Motion Warping** — https://dev.epicgames.com/documentation/unreal-engine/motion-warping-in-unreal-engine (accessed 2026-11-18): adjusts authored root motion to reach a target transform. Lesson: target-aligned interactions should extend root motion with explicit tests rather than use unconstrained correction.
- **Conclusion:** first finish and expose VICTUS's existing layers, IK, retarget, contact and root-motion systems; evaluate motion matching after a solid conventional baseline. This work is a dependency for the full A.R.C. hybrid animation/physics hand-off. No new animation runtime dependency is selected.

### Destruction and deformation

- **VICTUS baseline:** the physics abstraction already exposes breakable joints and rigid-body/collider events. There is no fracture-asset format, clustered geometry runtime or Studio fracture-authoring workflow documented in the current limitations.
- **Unreal Chaos Destruction Overview** — https://dev.epicgames.com/documentation/unreal-engine/destruction-overview (accessed 2026-11-18): public documentation describes pre-fractured Geometry Collections, clustering, connectivity constraints/strain thresholds, runtime separation and cached playback for larger simulations, with integration points for effects and audio. Lesson: authored fracture data plus hierarchical clusters and strict runtime budgets are more practical than unrestricted arbitrary mesh fracture every frame.
- **Conclusion:** evaluate a compact VICTUS-owned cooked fracture representation before adopting a library. Treat general deformation/cloth/soft-body as separate research; cap active fragments, bodies, collision cost and memory; define save/replay and authoritative replication. Chaos is a public reference, not a code or dependency choice.

### Audio Intelligence

- **VICTUS baseline:** miniaudio already supplies output/device management, buses, spatial attenuation/panning, streamed clip decoding, per-bus low-pass and a shared comb-filter reverb. Current limitations include no HRTF, geometry-aware occlusion/transmission, advanced reflections/convolution, per-source effects, voice virtualization/concurrency policy or audio profiling.
- **Steam Audio public guide** — https://github.com/ValveSoftware/steam-audio/blob/master/core/doc/guide.rst (accessed 2026-11-18): describes geometry-based direct-sound occlusion, material-dependent transmission and multi-band filtering of transmitted sound.
- **Steam Audio feature overview** — https://github.com/ValveSoftware/steam-audio/blob/master/core/doc/index.rst (accessed 2026-11-18): describes HRTF spatialisation, reflections and multi-path propagation around geometry. Lesson: acoustics needs scene geometry/material data and deliberate CPU/GPU budgets, not only distance attenuation.
- **Conclusion:** keep miniaudio as the baseline; compare authored zones and baked acoustic probes with optional dynamic tracing. Steam Audio is a candidate only after exact version, licence, platform, binary-size and performance review. Ensure low-tier approximations and use V.A.U.L.T. for streamed audio data.

### Engine Reliability and Recovery

- **VICTUS baseline:** crash/session diagnostics, local reports, editor autosave/recovery, versioned serialization for current formats, mutation-style robustness tests and ASan/UBSan CI already exist. Remaining gaps include transactional multi-generation writes and broad migration coverage, a safe editor recovery mode, stronger platform validation, and genuine in-process GPU device recreation (not supported by the currently documented SDL_GPU path).
- **Unreal Recovery Hub** — https://dev.epicgames.com/documentation/unreal-engine/recovery-hub-in-unreal-engine?lang=en-US (accessed 2026-11-18): records edit transactions and offers selective replay after an abnormal exit; it is explicitly complementary to autosave. Lesson: transaction history and autosave solve related but distinct loss scenarios, and transaction history needs bounded disk cost/user control.
- **Godot Project Manager Recovery Mode** — https://docs.godotengine.org/en/stable/tutorials/editor/project_manager.html (accessed 2026-11-18): recovery mode can bypass risky project startup behavior so a project can be opened and repaired. Lesson: safe mode matters when normal editor/project startup itself is the failure.
- **LLVM libFuzzer** — https://llvm.org/docs/LibFuzzer.html (accessed 2026-11-18): coverage-guided fuzzing mutates seeded corpora and can be combined with AddressSanitizer and UndefinedBehaviorSanitizer. Lesson: continue targeted parser/file-format fuzzing; do not replace existing mutation/sanitizer tests with a generic tool without a gap analysis.
- **Conclusion:** prioritise transactional save generations, explicit schema migrators, validation/repair diagnostics, editor safe mode and fault-injection/recovery tests. Treat device recreation as backend-capability research; until a backend genuinely supports it, preserve graceful exit and autosave.

## Research conclusions added 2026-11-19 (GPU particle simulation)
- **Wicked Engine, "GPU-based particle simulation" (Turánszki)** — https://wickedengine.net/2017/11/gpu-based-particle-simulation/ (accessed 2026-11-19): emit/simulate/sort/draw compute passes with dead and alive index lists, atomic counters and indirect arguments; collision against the depth buffer by projecting the particle, comparing with scene depth within a thickness and reflecting the velocity off a normal rebuilt from neighbouring depth samples. Adopted the depth-collision method and the compute simulate + instance-buffer draw; replaced the dead/alive lists with CPU-owned slot bookkeeping (ADR-0097) so counts and bounds stay exact without readback.
- **Bridson, Hourihan, Nordenstam, "Curl-Noise for Procedural Fluid Flow" (SIGGRAPH 2007)** — https://dl.acm.org/doi/10.1145/1275808.1276435 (accessed 2026-11-19): velocity (or acceleration) fields as the curl of a potential are divergence-free, so particles swirl without sinks or sources. Adopted a closed-form periodic curl field (two rotated octaves of cosines, exactly divergence-free) instead of curl of gradient noise, cheap and identical on CPU and GPU.
- **Unreal Engine Niagara overview** — https://dev.epicgames.com/documentation/en-us/unreal-engine/overview-of-niagara-effects-for-unreal-engine (accessed 2026-11-19): emitter-level logic (spawn rate, bursts, emitter lifetime) separate from per-particle scripts that can run on the GPU. Adopted the split.
- **Conclusion:** keeping emission and slot allocation on the CPU and only per-particle work on the GPU gives deterministic, testable GPU particles (readback matches a C++ reference to 2.4e-7 m in tests) for a spawn cost that is negligible next to simulating every live particle.

## Research conclusions added 2026-11-19 (volumetric fog)
- **Wronski, "Volumetric Fog: Unified compute shader based solution to atmospheric scattering" (SIGGRAPH 2014, Ubisoft / Assassin's Creed 4)** — https://bartwronski.com/wp-content/uploads/2014/08/bwronski_volumetric_fog_siggraph2014.pdf (accessed 2026-11-19): decouple ray marching into a per-cell lighting and density pass over a camera-aligned volume, a 2D compute march through the volume slices accumulating in-scattering and extinction, and a lookup at the pixel's depth applied in forward or deferred; about 1.1 ms on PS4/Xbox One. Adopted the three-pass split, the camera-aligned grid with non-linear depth and the full-screen composite (ADR-0098).
- **Hillaire, "Towards Unified and Physically-Based Volumetric Lighting in Frostbite" (SIGGRAPH 2015 Advances)** — https://advances.realtimerendering.com/s2015/ (accessed 2026-11-19): physically based participating-media parameters (scattering, extinction, phase), temporal reprojection of the volume with jittered samples and the energy-conserving analytic integration of in-scattering over a slice. Adopted the parameters, the analytic integration step and jitter + reprojection; local fog volumes kept as analytic boxes instead of a voxelised extinction volume.
- **Godot 4 "Fog Volumes arrive in Godot 4.0"** — https://godotengine.org/article/fog-volumes-arrive-in-godot-4/ (accessed 2026-11-19): Godot's volumetric fog follows Wronski's approach and adds FogVolume nodes (box/ellipsoid/world shapes with density and albedo) injected into the same froxel grid. Adopted the box FogVolume component design (density, albedo, edge fade); ellipsoids and density textures are follow-ups.
- **Conclusion:** a froxel grid stored in storage buffers fits the current RHI (no read-write storage textures) and gives lit, shadowed fog whose uniform-medium result matches the analytic solution within 3/255 in tests; 3D storage textures would enable hardware filtering and fogging transparent surfaces and particles, and are the main follow-up.

## Research conclusions added 2026-11-19 (script debugging)
- **Lute debugger architecture (Luau team)** — https://lute.luau.org/cli/debug/ARCHITECTURE.html and https://lute.luau.org/cli/debug/index.html (accessed 2026-11-19): breakpoints through `lua_breakpoint` plus the `debugbreak` callback; stepping through `lua_singlestep` and `debugstep` with step conditions (depth and line) evaluated per line event; the VM blocks inside the callback while a client inspects.
- **Luau C API and performance notes** — https://luau.org/api/ and https://luau.org/performance/ (accessed 2026-11-19): `lua_breakpoint` moves to the next line with code and patches the bytecode, so breakpoints cost nothing until hit; single-step mode calls the hook on every instruction. Measured here in the Debug build: 107 ms → 439 ms over a 3M-iteration loop with single-step on, so VICTUS enables it only while stepping or pausing.
- **luau-debugger (sssooonnnggg)** — https://github.com/sssooonnnggg/luau-debugger (accessed 2026-11-19): a DAP server over Luau that needs chunks compiled with debug level 2 for locals and upvalue names; it evaluates in an environment built from frame locals.
- **godot-luau-script debugger discussion** — https://github.com/Fumohouse/godot-luau-script/discussions/2 (accessed 2026-11-19): a blocking debug loop on the game thread and single-step depth tracking work for engine-embedded Luau.
- **Debug Adapter Protocol overview (Microsoft)** — https://microsoft.github.io/debug-adapter-protocol/overview (accessed 2026-11-19): Content-Length framing; initialize → launch → initialized → setBreakpoints → configurationDone; stopped → threads/stackTrace/scopes/variables; variable references are valid only until resume.
- **Conclusion:** Luau's built-in bytecode breakpoints and single-step hooks give a zero-cost-when-idle source debugger. A transport-free DAP session plus a stdio adapter reaches VS Code and other DAP editors without a custom IDE. Debugging inside Studio play needs the game loop off the UI thread first.


## Research conclusions added 2026-11-19 (format migrations)
- **Unreal Engine custom versions** — https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FCustomVersionContainer?lang=en-US and https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FCustomVersion?lang=en-US (accessed 2026-11-19): each package stores a container of (GUID, version) pairs, one per system, so a serializer upgrades its own data based on the version it was saved with, independently of the package format. Adopted as per-component `$version` with a step chain per component (ADR-0100).
- **Unity `FormerlySerializedAs`** — https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/serialization/formerlyserializedasattribute (accessed 2026-11-19): renaming a serialized field keeps old data loading by declaring the former name. Adopted as `SerializerRegistry::add_former_name` for components.
- **Unity forum on `MovedFrom` and `SerializeReference`** — https://discussions.unity.com/t/formerlyserializedasattribute-for-serializereference/878027 (accessed 2026-11-19): type renames need a separate mapping from the old type name, and data that cannot be mapped is lost on save. VICTUS keeps unreadable (newer or unknown) component data and saves it back unchanged instead.
- **Conclusion:** a whole-document version handles structural changes, per-component versions handle field changes without bumping the scene format, and migrations must be transactional, refuse newer data and keep the original file once.

## Research conclusions added 2026-11-19 (editor safe mode)
- **Godot project manager, recovery mode** — https://docs.godotengine.org/en/stable/tutorials/editor/project_manager.html (accessed 2026-11-19): when the editor crashes while opening a project, the next opening offers recovery mode, which disables tool scripts, editor plugins, GDExtension addons, automatic scene restoring and running the project, and shows a banner. Adopted the detection idea and the list of skipped features, mapped to VICTUS (edit-time scripts, asset import, thumbnails, automatic check, autosave, play mode) (ADR-0101).
- **Godot command line tutorial** — https://docs.godotengine.org/en/latest/tutorials/editor/command_line_tutorial.html (accessed 2026-11-19): `--recovery-mode` starts the editor in recovery mode directly. Adopted as `victus_editor --safe-mode`.
- **Conclusion:** a per-project "opening not finished" record is a cheap, reliable crash signal that needs no crash handler cooperation. Skipping everything that runs project content automatically, while keeping manual editing, lets users repair the file that crashes the editor from inside the Studio.

## Research conclusions added 2026-11-19 (perceptual image comparison)
- **NVIDIA FLIP (Andersson et al., HPG 2020)** — https://research.nvidia.com/publication/flip and https://research.nvidia.com/sites/default/files/node/3260/FLIP_Paper.pdf (accessed 2026-11-19): approximates the difference perceived when flipping between two images at a given pixels-per-degree viewing condition, combining a colour pipeline (contrast sensitivity filtering in YyCxCz, Hunt-adjusted L*a*b* distance) with an edge/point feature pipeline; outputs a per-pixel error in [0,1]. Adopted as the primary metric (ADR-0102).
- **NVlabs/flip** — https://github.com/NVlabs/flip (accessed 2026-11-19): BSD-3-Clause, header-only `FLIP.h` with a CPU path (`FLIP::evaluate` on linear RGB); default PPD 67 (0.7 m, 4K, 0.7 m wide); magma colour map for error maps. Vendored at d3ab02a.
- **SSIM (Wang, Bovik, Sheikh, Simoncelli 2004)** — https://docs.rs/crate/ssim/0.1.0/source/image-quality-assessment.pdf (accessed 2026-11-19): luminance, contrast and structure terms over an 11×11 Gaussian window (σ 1.5), K1 0.01, K2 0.03; mean SSIM over the image. scikit-image (https://github.com/scikit-image/scikit-image/blob/v0.18.0/skimage/metrics/_structural_similarity.py) averages only pixels where the window fits. Adopted unchanged on luma.
- **MS-SSIM (Wang, Simoncelli, Bovik 2003)** — https://www.cns.nyu.edu/pub/lcv/wang03b.pdf (accessed 2026-11-19): multi-scale SSIM is more robust to viewing distance; not adopted yet because FLIP already models PPD.
- **Conclusion:** use FLIP for "would a viewer see it", SSIM for structure, report worst tiles so local breakage cannot hide in a mean, and compare frame-to-frame change against the reference for temporal artefacts. Comparisons are only meaningful if the renderer is deterministic, which the first measurement showed it was not (wall-clock shader time, now fixed).

## Research conclusions added 2026-11-19 (rendering-path diagnostics)
- **SDL GPU query API, libsdl-org/SDL#11696** — https://github.com/libsdl-org/SDL/issues/11696 (accessed 2026-11-19): timestamp and occlusion queries are not in SDL_GPU; a proposal exists and the issue is milestoned for 3.6.0, with open questions about Metal's stage-boundary sampling. VICTUS reports GPU timing as unavailable until then instead of estimating it (ADR-0103).
- **Linux graphics stack book, SDL3 GPU chapter** — https://github.com/turbofish-pk/linux-graphics-stack-book/blob/main/chapters/part-18-rendering-abstractions/ch81-sdl3-gpu.md (accessed 2026-11-19): confirms that query objects (occlusion, timestamp, pipeline statistics) are not exposed.
- **Conclusion:** the useful diagnostic available today is the decision trail: which feature ran, at which quality, and why the others did not, attributed to tier, user setting, scene content, budget or capability. Cost per subsystem on the GPU waits for SDL_GPU queries.

## Research conclusions added 2026-11-19 (reference scenes)
- **Unreal Engine Screenshot Comparison Tool** — https://dev.epicgames.com/documentation/en-us/unreal-engine/screenshot-comparison-tool-in-unreal-engine (accessed 2026-11-19): screenshot functional tests compare captures against a "Ground Truth" image that is approved by hand. A mismatch fails the test, and a failing capture can replace the ground truth or be added as an alternative. Adopted: committed goldens per device class, and an explicit regenerate switch (`VICTUS_UPDATE_GOLDENS=1`) instead of automatic acceptance (ADR-0104).
- **Conclusion:** reference scenes are useful only if every feature they cover changes pixels in a measurable place. Each scene element maps to a feature the render-path report names. The tolerances come from measured regressions: removing spot shadows moved the mean FLIP by only 0.0013, but the worst tile by 0.019, so local limits are what catch real breakage.

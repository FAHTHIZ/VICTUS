## ADR-0001 — C++20 dependency-light foundation
Accepted for bootstrap. Standard-library-only core gives CI a reliable baseline. Revisit C++23 only after compiler/platform validation.

## ADR-0002 — Main-branch delivery
Accepted by owner. Commit coherent verified increments directly to main; keep commits small, preserve history and never force-push.

## ADR-0003 — Graphics backend (accepted 2026-11-16)
**Problem.** VICTUS needs real 2D/3D rendering on Windows, Linux, macOS, Android and iOS now, without a multi-year investment in three native backends before any game can render, and without becoming a wrapper around another engine.

**Candidates.** bgfx (BSD-2; own shader language/toolchain and build system, renderer-level abstraction), Diligent Engine (Apache-2.0; large, heavy build), direct Vulkan + Metal + D3D12 (maximum control, largest cost), SDL_GPU from SDL 3.4.x (zlib; explicit modern API: command buffers, render/copy/compute passes, cycling resources, Vulkan/Metal/D3D12 backends, Android/iOS support, small).

**Decision.** Engine renderers program only against the VICTUS RHI (`engine/rhi/include/victus/rhi/rhi.hpp`: generational handles, formats, pipelines, passes, uploads, readback). Its first backend is SDL_GPU (`engine/rhi/src/rhi_sdl.cpp`). Render graph, renderers, materials, shaders and all scene logic are VICTUS-owned. Shaders are authored once in GLSL 450 using SDL's resource-set convention and compiled offline by `tools/shaders/compile_shaders.py` into SPIR-V + MSL embedded in `engine/render/generated/builtin_shaders.cpp`; CI verifies the generated file matches sources by SHA-256 without needing the tools.

**Evidence.** Vulkan via Mesa lavapipe 26 (Vulkan 1.4) headless and through an X11 swapchain under Xvfb: clear/readback, sprite batching, PBR + shadow-map scene, tonemap and HUD overlay verified by pixel probes and visual inspection (see STATUS.md).

**Risks / gaps.** Metal path compiles shaders to MSL but has not been executed on Apple hardware; D3D12 requires DXIL (not yet generated) so Windows currently uses SDL_GPU's Vulkan driver; no GPU timestamp queries in SDL_GPU 3.4 (CPU profiling only); bindless/ray tracing/mesh shaders are not available through SDL_GPU. **Revisit trigger:** a measured bottleneck or required feature that SDL_GPU cannot provide; a native backend would then be added behind the same RHI. DXC (linux release v1.9.2609) is the planned DXIL path.

## ADR-0007 — Platform layer (accepted 2026-11-16)
SDL3 3.4.20 (zlib), fetched by pinned URL + SHA-256 (`cmake/VictusDependencies.cmake`), statically linked; `VICTUS_USE_SYSTEM_SDL` allows distro packages. Engine code sees only `victus::platform` (windows, keyboard/mouse/gamepad/touch input, lifecycle events, clipboard). `VICTUS_WITH_GRAPHICS=OFF` builds the core headless without SDL (servers, simulations).

## ADR-0004 — ECS and scheduler (accepted provisionally 2026-11-16)
**Decision.** VICTUS owns its ECS (`engine/ecs`): archetype storage with one aligned SoA column per component, archetype add/remove edges, generational 32+32-bit entities, runtime-registered components (needed for scripting and editor-defined data), cached queries over archetypes with exclusion filters, deferred command buffers and parallel iteration via the existing VICTUS job system (chunked `parallel_for`). Structural changes during iteration assert. Scenes (`engine/scene`) layer identity (UUID), hierarchy (intrusive sibling lists in a `Hierarchy` component) and serialization on top; serialization is a registry of named component serializers so unknown components round-trip unchanged.

**Why not Flecs/EnTT now.** Both are MIT and excellent; adopting either would expose its API across editor, scripting and networking. A small owned core keeps the replication/serialization/scripting seams under VICTUS control. **Evidence so far:** `victus_bench_scene` (STATUS.md, Slice 3). **Still required:** an identical-workload comparison against Flecs and EnTT; if VICTUS is materially slower on iteration or structural changes, either optimise or adopt behind the `victus::ecs` API. The job system remains custom (Slice 1); Taskflow/enkiTS comparison is still open.

## ADR-0008 — Scene format and asset pipeline (accepted 2026-11-16)
- Scenes: JSON `{"format":"victus.scene","version":1,"entities":[...]}` with entity UUIDs, parent UUIDs and components sorted by name for diff-friendly files. Loading is 3-pass (create, parent, components). A binary cooked scene format is planned for shipped builds.
- Assets: every source file gets a `<file>.meta` sidecar (`victus_meta`, `uuid`, `importer`, `settings`) that is meant to be committed with the project. Cooked results go to `<project>/.victus/cache/<uuid>.vcooked` (header `VCOOK`, format version, key hash of source bytes + settings + importer version, dependency hashes); the cache is disposable. Invalid metas are reported, never silently overwritten; duplicated UUIDs (copied files) are reassigned.
- glTF: cgltf 1.15 (MIT, single header, no dependencies) chosen over tinygltf (pulls in JSON library + stb) and fastgltf (C++20, simdjson dependency, faster but larger). File access is sandboxed to the asset's directory; remote URIs are rejected.
- Layering note: `engine/assets` depends on `engine/render` only for CPU types (`Image`, `MeshData`); a future split of those types into a GPU-free module will let headless cookers drop the render dependency.

## ADR-0005 — Editor UI (accepted 2026-11-16)
**Decision.** The VICTUS editor (`victus_editor`) is built on Dear ImGui v1.93.0-docking (commit `b916186e`, MIT), vendored unmodified in `third_party/imgui`. Only the upstream SDL3 *platform* backend is used; rendering goes through VICTUS's own renderer in `engine/ui` on the VICTUS RHI, so the editor exercises the same GPU path as games (Vulkan verified, Metal/D3D12 via SDL_GPU). The editor is a library (`victus_editor_core`) plus a thin executable so it can be driven headlessly by tests.

**Candidates.** Qt 6 (LGPL-3.0/commercial; strong accessibility, text and native widgets but heavy packaging, dynamic-linking obligations and a second rendering stack); Avalonia/.NET (MIT but needs a managed runtime and a GPU interop layer); a custom retained UI (largest effort, no ecosystem). ImGui wins today on embeddability, licensing, one-process debugging and iteration speed.

**Risks / revisit triggers.** ImGui has limited accessibility (screen readers), IME and rich-text support and the docking branch API moves. Mitigation: editor features live in VICTUS code behind panels, undo commands and the scene/asset APIs, not in ImGui state, so a shell replacement does not touch engine data. Revisit before a 1.0 editor if accessibility or text-heavy tools (script editing, localisation) require it. Runtime game UI is a separate decision (Phase 9); ImGui is not the shipped game UI.

**Fonts.** ImGui's embedded ProggyClean/ProggyForever fonts (MIT, Tristan Grimmer / Disco Hello) are used; no other fonts are bundled.

## ADR-0006 — Original license
Selected: Apache-2.0 for original VICTUS code. Third-party components retain their own licenses/notices. Maintain SBOM.

## ADR-0008 — Gameplay scripting language (accepted 2026-11-16)
**Problem.** Games need fast-iteration gameplay code that hot reloads in the editor, cannot crash or hang the engine, is safe to run from downloaded projects and mods, and works on every target including iOS (no JIT allowed) and consoles.

**Candidates.** Luau 0.747 (MIT, Roblox; Lua 5.1-derived with gradual typing, a native `vector` type, a built-in sandbox and VM interrupts); Lua 5.4 (MIT; smaller, no sandbox or types, standard library must be stripped by hand); LuaJIT (MIT; fastest on x86/ARM64 desktop but its JIT is forbidden on iOS and consoles, interpreter-only there, and upstream releases are irregular); Wren (MIT; small community, no types); AngelScript (zlib; C++-like, weaker sandboxing story); C# via .NET/Mono (MIT; large runtime, AOT complexity on iOS/consoles, GC pauses); WebAssembly (safe and language-agnostic but needs a toolchain per language and an ABI for every engine call).

**Decision.** Embed Luau (VM + compiler only, fetched as the pinned 0.747 release tarball). `engine/script` owns one VM per `ScriptHost`, applies `luaL_sandbox` (read-only globals, per-module sandboxed threads), a tracking allocator with a hard memory limit and an interrupt-based per-call time budget (an infinite loop raises an error instead of freezing the editor). Scripts are `.luau` assets referenced by a serialized `ScriptComponent` (path + property overrides + enabled). The API (`entity`, `scene`, `input`, `time`, `log`) is VICTUS's own and goes through the scene/serializer registry, so scripts see the same component data as the editor and scene files. Faulted instances are disabled until their file is reloaded; errors go to the log/console with file and line.

**Evidence.** `victus_script_tests` (sandboxing, budget, memory limit, lifecycle, hot reload, properties), the three templates are fully scripted and played headlessly by `victus_project_tests` and `victus simulate` in CI; `victus_bench_script` Release p50 on 2 vCPU Xeon: 10 000 scripted entities `update` 3.89 ms (~0.39 µs/entity incl. transform read/write), 1M-iteration arithmetic loop 8.15 ms.

**Risks / revisit triggers.** Luau's native code generator is not used yet (interpreter only; evaluate on desktop once hot spots are measured). Type checking (Luau.Analysis) is not wired into `victus check` yet. A managed or WASM tier may be added later for heavy systems; C++ remains the language for engine systems. Visual scripting is deferred and will compile to the same runtime API.

## ADR-0009 — Physics engines (accepted 2026-11-16)
**Problem.** VICTUS needs production-grade 3D and 2D rigid-body physics (shapes, dynamic/kinematic/static bodies, triggers, queries, contact events) that is deterministic enough for tests, scales across worker threads, runs on mobile CPUs and has a permissive license for commercial games.

**Candidates.** 3D: Jolt Physics v5.7.0 (MIT, Jorrit Rouwe; used by Horizon Forbidden West and Godot 4.4+ as its default 3D backend); PhysX 5 (BSD-3-Clause; very capable but a heavy build, GPU features NVIDIA-only); Bullet 3 (zlib; mature but largely unmaintained); a custom solver (years of work). 2D: Box2D v3.2.0 (MIT, Erin Catto; v3 rewrite with SIMD solver, multithreading via task callbacks, sensor events); Chipmunk2D (MIT; inactive); a custom 2D solver.

**Decision.** Jolt 5.7.0 and Box2D 3.2.0, fetched as pinned release tarballs with SHA-256 verification, built as third-party targets without VICTUS warning flags, behind one owned API (`victus::physics`). Scenes only see VICTUS components (`RigidBody`, `Collider`, `RigidBody2D`, `Collider2D`) that are serialized, reflected into the editor inspector and exposed to Luau; the backends never leak into public headers. `PhysicsWorld` syncs components to bodies (create/update/destroy, kinematic targets, teleports), steps in `Simulation` FixedUpdate, writes dynamic transforms back, and publishes sorted per-tick contact/trigger events that `ScriptHost` dispatches as `on_collision_enter/exit` and `on_trigger_enter/exit`. Both solvers run on the engine `JobSystem` when one is supplied. Build choices: Jolt `CPP_RTTI_ENABLED=ON` (needed to subclass `JobSystemWithBarrier` without undefined typeinfo), AVX/AVX2/AVX-512 off so binaries run on any x86-64 (SSE4.2 baseline; ARM64 uses NEON), `OBJECT_LAYER_BITS=32` with a VICTUS-encoded (layer, mask, motion) object layer so per-collider masks and the 16x16 layer matrix are honoured.

**Evidence.** `victus_physics_tests` (falling bodies come to rest on ground in both dimensions, kinematic platforms carry bodies, triggers, layer masks, raycasts/overlaps, velocities/forces/impulses, teleports, reparenting, determinism of repeated runs, serialization round-trips); `victus_script_tests` physics case; `victus_project_tests` plays the 2D platformer on Box2D (land, run to the wall, jump, collect coins via triggers) and the 3D template (crate stack settles, the kinematic ball knocks it over); `victus_bench_physics` (see STATUS).

**Risks / revisit triggers.** Cross-platform bit-exact determinism is not claimed (Jolt supports it with `CROSS_PLATFORM_DETERMINISTIC`, which costs speed; revisit for lockstep networking). Character controllers (`JPH::CharacterVirtual`), joints, mesh/convex-hull colliders and 2D polygons are not exposed yet. If either upstream stalls, the owned component API allows swapping the backend without touching scenes or scripts.

## ADR-0010 — Audio engine (accepted 2026-11-16)
**Problem.** Games need low-latency playback of sound effects and streamed music, mixing buses with volume/mute, 3D spatialization following scene transforms, and decoding of common formats, on desktop and mobile, with headless tests that can assert real mixed output.

**Candidates.** miniaudio 0.11.26 (single-file C, public domain or MIT-0, David Reid; backends for WASAPI, CoreAudio, ALSA/PulseAudio/JACK, AAudio/OpenSL ES, Web Audio; built-in WAV/FLAC/MP3 decoders, node graph, spatializer); SDL3 audio (already linked, but only device/streams: no decoding, mixing or spatialization); OpenAL Soft (LGPL, dynamic linking constraints); FMOD/Wwise (proprietary, per-title licensing); SoLoud (zlib; less active).

**Decision.** miniaudio 0.11.26 fetched as a pinned release tarball (SHA-256 verified) and compiled from one implementation unit (`engine/audio/third_party/miniaudio_impl.c`) with `MA_NO_ENCODING`, stb_vorbis from miniaudio's `extras/` for Ogg Vorbis, warnings disabled, behind an owned API (`victus::audio`). stb_vorbis is compiled from a copy patched at configure time for memory-safety bugs found by fuzzing (see THIRD_PARTY_AND_LICENSES.md). `audio::inspect_clip` decodes a clip from memory with the same decoders, without an engine, to validate it. Scenes see only `AudioSource`/`AudioListener` components (serialized, reflected into the inspector, exposed to Luau). Six fixed buses (Master, Music, Sfx, Ui, Ambient, Voice) are miniaudio sound groups under Master. `AudioEngine::create` falls back to a no-device engine when no output exists (or `VICTUS_NO_AUDIO=1`), and `render()` pulls mixed frames from that engine so tests assert actual sample output. On Apple, `MA_NO_RUNTIME_LINKING` links CoreAudio/AudioToolbox directly (required for iOS App Store builds).

**Evidence.** `victus_audio_tests` (6 cases: null-device mixing of a WAV clip with non-silent output, finishing and looping, bus volume/mute, pause/stop; spatial attenuation by listener distance and panning; one-shot reaping, voice cap and bad-clip reporting; streamed Ogg Vorbis and FLAC decoding; component serialization and system-driven playback; MP3 is decoded by miniaudio but not covered by a test file), script audio case in `victus_script_tests`, template audio assertions in `victus_project_tests`, `victus_bench_audio` (see STATUS).

**Risks / revisit triggers.** No DSP effects (reverb, filters, ducking) or HRTF exposed yet; Opus is not decoded; streaming reads files directly (no packed-archive VFS yet, revisit with `victus export`). Device hot-plug relies on miniaudio's default rerouting.

## ADR-0011 — Game packaging and the `.vpak` archive (accepted 2026-11-16)
**Problem.** Games must ship as a runnable folder that contains no editor-only data (source images, glTF, `.meta` files), never runs importers on players' machines, loads fast on mobile storage, and can be checked for corruption.

**Candidates.** Loose folders (simple, but slow to open thousands of files on mobile, easy to tamper with and ship sources by mistake); zip via miniz/libzip (standard tooling, but zip's central directory and per-entry extras add parsing surface and compression is per-entry deflate only); PhysicsFS (zlib; full VFS but another dependency and C-style global state); an owned archive format.

**Decision.** An owned, deliberately small format (`victus/core/pack.hpp`): 40-byte header, 16-byte-aligned payloads, a table of contents with sanitized relative paths, per-entry FNV-1a 64 checksums verified on every read and a TOC checksum verified on open; offsets and sizes are bounds-checked against the file, duplicate or escaping paths are rejected. Entries are written in sorted order, so the same project exports byte-identical packs. A codec field is reserved (only "stored" today). `fs::mount(root, pack)` overlays a pack on a folder so `read_binary/read_text/exists/list_files` transparently read pack entries; everything above core (projects, scenes, scripts, audio through a miniaudio VFS, cooked assets) works unchanged. `AssetDatabase::open_packaged` reads an asset index written at export instead of scanning and never imports or writes. `victus export` validates scenes and scripts before writing, copies the player, embeds third-party license texts collected at configure time from the pinned dependency sources, and writes an `export.json` manifest.

**Evidence.** `victus_core_tests` pack and mount cases (round trip, reproducible output, corrupted payload/header/TOC/truncation detection, path escapes, overlay precedence and listing), `victus_export_tests` (export contents, packaged texture/model/scene/script/audio loading from a mounted pack with nothing written next to it, re-export, refusal to write into unrelated or in-project folders, broken-script and missing-reference failures), `victus_cli_smoke` exports all three templates and runs each exported game headless with a screenshot.

**Risks / revisit triggers.** No compression yet (cooked textures are uncompressed RGBA8 mip chains; GPU texture compression and LZ4/zstd are the next size wins). Packs are read with buffered reads, not memory-mapped. FNV-1a detects corruption, not tampering; signing is a later item. Export targets the host platform only.

## ADR-0012 — Scalable rendering quality pipeline (accepted 2026-11-16)
**Problem.** The 3D renderer must look close to modern high-end engines on desktop while the same content runs on phones. Every expensive effect therefore needs a cheaper fallback and a switch, chosen per project and overridable per run, without content changes.

**Candidates.** Deferred shading (G-buffer bandwidth is the main cost on tile-based mobile GPUs); forward with a depth prepass (cheap on tilers, MSAA/FXAA friendly, gives SSAO its depth); clustered forward (better for hundreds of lights, more complexity than today's 16-light limit needs); ray-traced AO/shadows (not available on most mobile hardware).

**Decision.** Forward HDR PBR with an optional depth prepass that feeds SSAO (Alchemy/SAO, optional half resolution + depth-aware blur), cascaded shadow maps (1–4 cascades in a 2×2 atlas, practical split scheme, texel snapping, dithered cascade transitions, optional soft PCF), dual-filter bloom (13-tap Karis downsample, tent upsample, 3–6 levels), GPU auto exposure (64×64 log-luminance → 1×1 R32F ping-pong with separate brighten/darken adaptation speeds), selectable tonemappers (ACES fitted, Khronos PBR Neutral, Reinhard, none) with exposure compensation, saturation, contrast and vignette, then FXAA 3.11. `RenderSettings::preset(QualityTier)` defines Low/Medium/High/Ultra (Low: 0.75 render scale, 1 hard cascade, no SSAO/bloom, 4 lights; Ultra: 4 cascades, full-res 16-sample SSAO, 6 bloom levels); `sanitized()` clamps hand-written values. Per-scene look lives in the reflected `Environment` component; the tier lives in `victus.project` (`rendering.quality`, `rendering.render_scale`) and can be overridden with `--quality`. Each pass is a render-graph node, so disabled effects cost nothing.

**Evidence.** `victus_gpu_tests` "gpu quality" cases (8): pass counts per tier, distant casters shadowed only with CSM, SSAO darkening a crease but not open floor, bloom halo around an emissive, auto exposure normalising dark and bright scenes and adapting over time, tonemapper/grading differences, FXAA reducing hard step edges, render scale; Environment component end-to-end case; `victus_render_tests` preset/sanitize cases; `victus_cli_smoke` runs each template at every tier. Timings in STATUS are llvmpipe CPU numbers only.

**Risks / revisit triggers.** No temporal AA/upscaling, motion blur or depth of field yet; point lights are capped at 16 (move to clustered forward when scenes need more); no reflection probes or GI; tiers are not yet validated on physical mobile GPUs. Revisit the prepass on tilers if measurements show it costs more than it saves.

## ADR-0013 — Automatic GPU instancing (accepted 2026-11-16)
**Problem.** Scenes repeat the same mesh and material many times (foliage, props, crowds). One draw call per object makes CPU submission the bottleneck long before the GPU is busy, which is worst on mobile drivers.

**Candidates.** Explicit instancing components authored by users; automatic batching of identical draws with per-instance vertex data; GPU-driven culling with indirect draws and storage buffers (best scaling, but needs compute culling and multi-draw-indirect, which are not uniformly available on SDL_GPU targets and older mobile GPUs).

**Decision.** Automatic instancing inside `SceneRenderer`: every mesh draw is instanced (a single object is a batch of one), with model and inverse-transpose normal matrices (112 bytes) in a per-frame vertex buffer at slot 1 using instance step rate. Visible draws are sorted by pipeline, base texture, a mesh+material key, then distance; runs with the same mesh and exactly equal material (checked field by field, not just by hash) become one `draw_indexed` with N instances. Shadow cascades batch by mesh only. Each pass binds its own contiguous instance range by offset (no reliance on base-instance support). The instance buffer grows geometrically and is uploaded with `discard` so in-flight frames are renamed instead of stalling. `RenderSettings::instancing` turns batching off for A/B comparison. Indirect, GPU-driven culling stays a later option.

**Evidence.** `victus_gpu_tests` "gpu instancing" cases (identical image with batching on/off within 1 LSB, batch counts in main/prepass/shadow passes, materials and meshes never merged, buffer growth across frames). `victus_bench_render`: 4 096 cubes, Low tier, 320×180 on llvmpipe: 21.8 ms instanced vs 258.8 ms unbatched (p50).

**Risks / revisit triggers.** Front-to-back order is only kept within a batch, so heavy overdraw scenes on the Low tier (no prepass) may lose some early-z benefit; instances are rebuilt every frame (no persistent static batches yet); skinned meshes will need their own path.

## ADR-0014 — Character controller and physics joints (accepted 2026-11-16)
**Problem.** Games need a player character that walks on slopes, climbs stairs, stands on moving platforms and pushes objects without the jitter and tunnelling of a plain rigid body, plus doors, levers, pendulums, ropes and breakable connections. Both must stay behind owned `victus::physics` types so the backend can change.

**Candidates.** A dynamic rigid-body capsule (`JPH::Character`): simple, but friction and stepping need hacks and it is pushed around by the solver. Jolt `CharacterVirtual`: collision-query based, moved by the game each step, with built-in stair walking, floor sticking and contact callbacks. An owned kinematic sweep controller: full control but duplicates work Jolt already ships and tests. For joints: expose Jolt constraint types directly vs a small owned `Joint` component that maps to them.

**Decision.** `CharacterController` component backed by `JPH::CharacterVirtual` (Jolt 5.7.0) with a capsule whose bottom sits at the entity origin and an inner rigid body (`mInnerBodyShape`) so raycasts, triggers and other bodies see the character. Characters are updated before each rigid-body step: ground velocity update, ground-relative desired velocity with exponential air control, gravity only along the ground normal while supported on a walkable slope, then `ExtendedUpdate` with stair step-up and stick-to-floor set to `step_height`. `push_force` sets the maximum force the character exerts on dynamic bodies (`mMaxStrength`). `Joint` component (fixed, point, hinge, slider, distance) references the connected entity by UUID (nil = world); body 1 is the connected body so angles and slider positions measure this entity. Limits, velocity motors (force/torque limited) and a break force (constraint impulse / dt checked after every step, then `SetEnabled(false)`) are supported; a `GroupFilter` gives every body its own group and skips pairs that share a non-colliding joint. Constraints are rebuilt only when bodies or non-motor fields change, and are removed before their bodies.

**Evidence.** `victus_physics_tests` 16 character/joint cases (see STATUS Slice 11), script and template tests, and `victus_bench_physics`: 256 characters step in 0.514 ms p50 on one 2.9 GHz Xeon thread. Sources: Jolt `CharacterVirtual` reference and architecture/constraints documentation (RESEARCH_REGISTER).

**Risks / revisit triggers.** Character capsules only (no crouch shape swap or custom shapes yet); characters are updated serially; 2D (Box2D) has no character controller or joints yet; no cone, swing-twist, 6-DOF or ragdoll joints and no position motors. Revisit the serial update if scenes need thousands of characters.

## ADR-0015 — Skeletal animation and GPU skinning (accepted 2026-11-16)
**Problem.** Characters need imported skeletal animation that plays, loops and cross-fades, is scriptable, renders with correct shadows and depth, and scales to hundreds of characters on mobile-class CPUs and GPUs.

**Candidates.** A third-party runtime (ozz-animation: excellent SoA sampling, but an extra offline format and dependency); CPU skinning (simple, but per-vertex work and buffer uploads every frame scale badly); GPU skinning with a per-draw joint palette; animating joints as ordinary scene entities vs a hidden pose buffer.

**Decision.** An owned `victus::animation` module that samples glTF 2.0 channels directly from the cooked model (STEP, LINEAR with normalized shortest-path quaternions, CUBICSPLINE, clamped ends). Joints stay ordinary scene entities bound by node name under the animator's root, so the editor, scripts, physics attachments and the existing transform propagation all see animated bones; the system writes local transforms in `Phase::Update` and evaluates animators in parallel with `parallel_for`. Skinning runs on the GPU: a separate `SkinVertex` stream (4 × u16 joints + 4 × f32 weights) and skinned vertex-shader variants for the main, pre-pass and shadow passes read a joint palette from a storage buffer; palettes are computed relative to the mesh entity so the skinned node transform is ignored as glTF requires; skinned draws of the same mesh and material still instance, each instance indexing its own palette range. The importer keeps the four strongest influences from up to two JOINTS/WEIGHTS sets and renormalizes them.

**Evidence.** `victus_animation_tests`, asset round-trip tests and pixel-probed `gpu skinning` cases (STATUS Slice 12); `victus_bench_animation`: 1 024 characters × 32 joints update in 1.481 ms on one thread and 0.827 ms with jobs (p50, 2 vCPU 2.9 GHz Xeon, 0 allocations). Source: glTF 2.0 specification skins and animations sections (RESEARCH_REGISTER).

**Risks / revisit triggers.** Entity-per-joint costs ECS memory for very large crowds; revisit with a compact pose buffer plus GPU-side palette generation if crowds reach thousands of animated characters. No dual-quaternion skinning (volume loss at twisting joints), blend trees, state machines, root motion, IK, retargeting or morph targets yet.

## ADR-0016 — Particles and VFX (accepted 2026-11-16)
**Problem.** Games need fire, sparks, smoke, dust and pickup effects that look good in the HDR pipeline (glow through bloom, no hard edges where sprites cut into geometry), are scriptable and deterministic, run on mobile-class GPUs, and work in both 2D and 3D scenes.

**Candidates.** GPU-simulated particles (compute shaders + indirect draws: scales to millions, but needs compute in the RHI, makes scripting/readback and determinism harder, and mobile GPUs pay for it in bandwidth); CPU simulation with instanced billboards; a third-party VFX runtime (e.g. Effekseer: rich authoring, but a large dependency with its own renderer integration).

**Decision.** An owned headless `victus::particles` module: a serialized `ParticleEmitter` component (rate, bursts per cycle, duration/loop, cap, point/sphere/cone/box shapes, speed, gravity, drag, size/colour over life with HDR intensity, spin, alpha/additive blend, optional texture, softness, 2D layer, seed) with hidden runtime state. Each emitter owns a PCG32 stream (seeded from `seed` or its entity UUID) and is simulated independently in `Phase::PostUpdate` (after scripts and physics move emitters), in parallel through `parallel_for`, so results are bit-identical serial or threaded. Each update produces 48-byte billboards that share `render::ParticleInstance`'s layout, so the runtime submits them without conversion. The renderer draws them as instanced camera-facing quads (six vertices from `gl_VertexIndex`, one instance per particle) in an HDR pass after the opaque forward pass, without a depth attachment: the fragment shader reads the scene depth texture, discards fragments behind geometry and fades near it (soft particles). Batches are frustum-culled by their bounds and drawn back to front; alpha batches sort their particles back to front, additive batches do not need to. 2D scenes draw the same billboards through `SpriteBatch`, which gained an additive pipeline.

**Evidence.** `victus_particles_tests` (10 cases incl. serial vs job-system byte equality), 4 pixel-probed `gpu particles` cases, template and script tests (STATUS Slice 13). `victus_bench_particles`: 64 emitters × 256 particles (16 384 live, steady state) update in 0.236 ms on one thread and 0.129 ms with jobs (p50, 2 vCPU 2.9 GHz Xeon, 0 allocations). Source: Lorach, "Soft Particles" (NVIDIA, 2007) (RESEARCH_REGISTER).

**Risks / revisit triggers.** CPU cost and upload bandwidth grow linearly; revisit with GPU simulation when scenes need more than ~100k live particles. No collision, trails/ribbons, flipbooks, curves editor, sub-emitters, lighting of particles or shadow casting yet; additive 2D colours are clamped to LDR.

## ADR-0017 — 2D character mover, one-way platforms and 2D joints (accepted 2026-11-16)
**Problem.** 2D games need a platformer-grade character (crisp, non-bouncy movement, ground detection, slopes, one-way platforms you jump through and drop off, pushing crates) and joints (chains, bridges, swinging props, wheels, motors), scriptable through the same Luau API as the 3D `CharacterController`/`Joint` (ADR-0014).

**Candidates.** A dynamic `RigidBody2D` driven by velocity plus raycast grounding (what the 2D template used: simple, but contact friction/restitution make it bouncy and sticky on edges, and one-way platforms need custom contact handling anyway); a kinematic body with hand-written sweeps; Box2D 3.2's geometric mover API (`b2World_CollideMover` + `b2SolvePlanes` + a sweep + `b2ClipVector`, as in its `geometric_mover.cpp` sample).

**Decision.** `CharacterController2D` (capsule `size`, `max_slope`, `snap_distance`, `gravity_scale`, `push_force`, `air_control`, layer/mask) uses the Box2D mover: each fixed step integrates a velocity model matching the 3D controller (desired velocity plus the ground body's point velocity on the ground (riding kinematic and dynamic platforms), `air_control` blend in the air, gravity), then up to 5 iterations of collide (5 mm skin) → plane solve → shape cast, clipping velocity against the solved planes; a 2 cm downward probe decides `grounded` against `max_slope`, and the character snaps down within `snap_distance` while walking. A kinematic inner capsule follows the mover through `b2Body_SetTargetTransform`, so raycasts, triggers and other bodies see it; dynamic bodies in the way get an impulse capped at `push_force × dt`. `Collider2D.one_way` platforms are filtered in two places: the mover rejects a one-way plane unless the bottom of the capsule's lower circle is above the platform's closest point (with `drop_through(seconds)` suppressing all one-way planes for a short window), and dynamic bodies use Box2D pre-solve/continuous callbacks (contact normal within ~45° of up and not already penetrating more than 8 cm). `Joint2D` (weld, revolute, prismatic, distance, wheel) maps 1:1 to Box2D 3.2 joints with limits (degrees or metres), springs (Hz/damping ratio), motors, `break_force` (checked against the constraint force/torque each step) and `collide_connected`; a nil `connected` attaches to a static anchor body at the world position of `anchor`. Joints are rebuilt when either body is rebuilt or the component changes, like the 3D joints.

**Evidence.** `victus_physics_tests` "2D character …"/"2D joint …" (13 cases), `victus_script_tests` "script: 2D character, one-way drop-through and 2D joint motor", the 2D template test (jump up through the one-way ledge, land, drop back through, lantern joint active) (STATUS Slice 14). Release `victus_bench_physics` (p50, 2 vCPU 2.9 GHz Xeon, one 1/60 s step): 64 2D characters 0.154 ms, 256 0.862 ms; 200 swinging chain links 0.226 ms, 1 000 links 1.19 ms. Sources: Box2D v3.2.0 samples and `collision.h`/`world.h` mover API (RESEARCH_REGISTER).

**Risks / revisit triggers.** The mover has no explicit step-up (ledges are climbed only as far as the capsule's rounding slides over them) and no rotating-platform angular carry; one-way filtering for dynamic bodies is per contact and can let fast thin bodies through. Revisit with ground-velocity inheritance and a Box2D upgrade if the mover API changes.

## ADR-0018 — In-game UI (accepted 2026-11-16)
**Problem.** Games need HUDs and menus that scale with the screen, are authored as scene data, scriptable from Luau and drawn in both 2D and 3D views.

**Candidates.** Dear ImGui widgets directly (immediate mode, editor-styled, not scene data); RmlUi (HTML/CSS, large surface); commercial middleware (Noesis, Coherent: licensing); owned retained components with a small layout core.

**Decision.** Owned retained ECS components in `engine/gameui` (canvas, rect, panel, image, text, button, layout) with headless layout and interaction so tests and `victus simulate` run without a GPU. Canvas scaling follows Unity's `CanvasScaler` match mode (weighted average of log2 width/height ratios). Rendering converts draw items to Dear ImGui 1.93 draw-list geometry in a private context (anti-aliased rounded shapes, dynamic font baking) through the existing RHI UI pipeline; ImGui widgets are not used. Default font: Inter 4 Medium/Bold, SIL OFL 1.1, embedded.

**Evidence.** STATUS Slice 15 tests; `victus_bench_gameui` 520 elements update 0.048 ms, draw list 0.024 ms (p50).

**Risks / revisit triggers.** No rich text, shaping (complex scripts) or accessibility; revisit text with HarfBuzz when localization lands, and add a visual editor.

## ADR-0019 — Navigation (accepted 2026-11-16)
**Problem.** Gameplay AI needs walkable-surface generation, path queries and agents that follow paths and avoid each other, authored with no manual navmesh step and scriptable from Luau.

**Candidates.** Recast & Detour 1.6.0 (zlib; industry standard, used by Unity's legacy navmesh lineage, Unreal, Godot 3, O3DE); owned grid A* (simple, poor on 3D levels, no crowd); Godot's `NavigationServer` (engine-coupled); commercial middleware (licensing).

**Decision.** Recast & Detour 1.6.0 (`Recast`, `Detour`, `DetourCrowd` only) as a private dependency of `engine/navigation`. The navmesh is a single tile built on demand from every static, non-trigger 3D `Collider` (box/sphere/capsule/cylinder triangulated in world space, outward winding); kinematic colliders contribute a quantized upright bounding cylinder so Y-rotation does not cause rebuilds; dynamic bodies, triggers and agents are ignored. A geometry signature (FNV-1a over collider shapes, world matrices and `NavMeshSurface` settings) is checked every 0.25 s and triggers rebuilds; agents keep their destinations across rebuilds. Agents are DetourCrowd agents (anticipate turns, visibility/topology optimization, obstacle avoidance and separation); `CharacterController` agents feed the crowd velocity to `PhysicsWorld::move_character` and re-sync the corridor to the physics position each frame, other agents are placed on the surface plus `base_offset`. Recast parameters follow the RecastDemo solo-mesh defaults (edge length 12 m, simplification 1.3, region min/merge 8²/20², 6 verts/poly).

**Evidence.** STATUS Slice 16 tests; `victus_bench_navigation` (Release, p50): build of a 60 × 60 m level with 100 obstacles 44 ms, path query across it 0.028 ms, crowd update 16 agents 0.056 ms and 128 agents 0.87 ms.

**Risks / revisit triggers.** Single-tile builds are synchronous (tens of ms on large levels): move to tiled navmeshes with background rebuilds of dirty tiles (DetourTileCache) for open worlds or frequent kinematic changes. No off-mesh links (jumps, ladders), area costs or 2D navigation yet.

## ADR-0020 — Networking (accepted 2026-11-16)
**Problem.** Games need two or more players against an authoritative dedicated server with replication, prediction and interpolation, testable headless and under bad network conditions, without a platform-service dependency. Networking is a high-risk foundation, so alternatives were compared.

**Candidates.** ENet 1.3.18 (MIT; small C library, reliable/unreliable channels over UDP, fragmentation, RTT, used widely; no encryption); Valve GameNetworkingSockets v1.6.1 (BSD-3; encryption, P2P/NAT traversal, but needs OpenSSL or libsodium plus protobuf, heavy to build on every platform); yojimbo v1.15.2 (BSD-3; connect tokens and encrypted packets, bundles libsodium, netcode and reliable, opinionated message model); an owned UDP protocol (full control, large reliability/fragmentation surface to get right).

**Decision.** ENet 1.3.18 behind VICTUS's own `net::Transport` interface (ENet and in-memory loopback backends, plus a link-condition emulator wrapping either), statically linked and private to `engine/net`, so the transport can be swapped (e.g. for GameNetworkingSockets when encryption is needed) without touching sessions or scripts. Above it VICTUS owns the protocol: a versioned handshake carrying a game fingerprint, a server-authoritative session that runs scripts and physics, spawns a player from the scene's `player_template` per client and routes each client's input only to its player, 30 Hz unreliable snapshots of `NetworkIdentity` entities (transform, velocity, script values) and reliable script messages; clients predict their owned player and are corrected past a threshold, and interpolate others 100 ms behind (extrapolating at most 0.1 s, then easing back).

**Evidence.** STATUS Slice 17: `victus_net_tests` (10 cases, 410 assertions) over memory and real UDP transports including emulated latency/jitter/loss; CLI smoke runs a real server with two UDP clients; measured snapshot 216 bytes for 10 entities.

**Risks / revisit triggers.** ENet traffic is unencrypted and unauthenticated: add encryption/auth (GameNetworkingSockets or yojimbo transport, or DTLS) before public servers. Full snapshots without delta compression cost bandwidth with many entities. No physics rollback or lag compensation yet.

## ADR-0021 — Input actions (accepted 2026-11-16)
**Problem.** Scripts hard-coded key names, so games could not be played with a gamepad or rebound, and network input only carried keys. Input is user-facing in every game, so options were compared.

**Candidates.** Raw SDL3 events and SDL gamepad calls exposed directly to scripts (no abstraction, every game re-implements mapping and dead zones); a third-party action library such as gainput (MIT; actions, devices and recording, but its own device layer duplicates SDL and the repository was archived in September 2021, unmaintained); an owned action map in `engine/gameplay` over the existing `InputSource` interface, with SDL3 only as the device backend.

**Decision.** Owned `gameplay::InputMap`: named actions with button bindings or positive/negative axis bindings and a dead zone, bindings written as readable strings (`Space`, `Mouse0`, `Pad.South`, `Pad.LeftX+`) using SDL3's standard gamepad layout names, stored in the `input` section of `victus.project` with defaults, validated on load and by `victus check`. Devices stay behind `InputSource`, so the same map is evaluated over SDL input, headless `ManualInput` and the network's `RemoteInput`; protocol v2 sends merged gamepad state (buttons bitmask plus six quantized axes). No new dependency.

**Evidence.** STATUS Slice 18: input-map, Luau, template, project and network tests; CLI smoke with `--hold Pad.*`.

**Risks / revisit triggers.** Gamepads are merged into one for single-player and network input; local multiplayer needs per-player device assignment. Touch and rumble are not covered. Revisit if games need input contexts/stacks or combos.

## ADR-0022 — Asset hot reload (accepted 2026-11-16)
**Problem.** Iterating on art required restarting the game or pressing Reimport. Reloading must never crash a running game or editor, must work the same on Windows, macOS and Linux, and must say clearly what cannot be reloaded.

**Candidates.** OS change notifications written per platform (inotify, FSEvents/kqueue, ReadDirectoryChangesW: immediate, three code paths, editors that save via rename/temp files produce bursts to debounce); efsw (MIT; wraps those backends with a generic polling fallback, one more dependency); polling file size + modification time from VICTUS's own code (one portable code path, latency bounded by the interval, cost of one directory walk per interval).

**Decision.** Polling in `runtime::AssetHotReloader` (0.5 s in the player, 1 s in the editor), with the asset database's existing content hashes deciding what really needs re-importing, so touched-but-identical files cost nothing. Re-imported textures/models are evicted from `GpuAssetCache` (SDL GPU frees released textures/buffers only once it is safe) and the animation cache; audio clips are reloaded by `AudioEngine::reload_clip`; scripts keep their own watcher. Failed imports keep the last good cooked file (the database falls back to it) and are reported. Scenes, fonts, shaders and code are reported or documented as restart-only. No new dependency; OS notifications (or efsw) remain an option if project sizes make polling expensive.

**Evidence.** STATUS Slice 20: GPU, audio and editor tests; live `victus run` edit of the template robot.

**Risks / revisit triggers.** Large asset trees make each scan slower (benchmark before adopting notifications). Modification-time resolution on some file systems is coarse (size changes and the next scan still catch it). Model node-graph changes need re-instantiation to show fully.

## ADR-0023 — Prefabs (accepted 2026-11-16)
**Problem.** Games need reusable entity hierarchies that can be placed many times, tweaked per placement, updated centrally, and spawned from scripts, without breaking references between entities or scene merges.

**Candidates.** Unity-style prefabs (https://docs.unity3d.com/Manual/Prefabs.html): instances keep links to source objects and store property-level modifications, plus nested prefabs and variants; very flexible, large implementation and UI surface. Godot `PackedScene` (https://docs.godotengine.org/en/stable/classes/class_packedscene.html): a serialized scene instantiated as a subtree, with "editable children"; simple, but every scene is a prefab and overrides are coarse. VICTUS-native: a `.vprefab` file in the scene snapshot format, instance root with `PrefabInstance`, parts tagged with `PrefabPart`, component-level overrides, deterministic derived uuids.

**Decision.** The VICTUS-native design: it reuses the existing versioned component serializers (no second format), keeps instances valid scene data (an unpacked or prefab-less scene still loads), and derived uuids make instantiation deterministic for diffs, networking and tests. Component-level overrides are the first step; per-property overrides, variants and nesting are recorded as remaining work in ROADMAP Phase 9.

**Evidence.** STATUS Slice 21: scene, script and editor tests; template runs in the editor-less player and an exported build.

**Risks / revisit triggers.** Component-level overrides discard upstream changes to an overridden component; nested prefabs are flattened (lose their own link). Revisit when variants/nesting are implemented.

## ADR-0024 — Save games and checkpoints (accepted 2026-11-16)
**Problem.** Games need durable progress/profile data that survives crashes and game updates, and players expect quick save/load of the whole game state, without VICTUS games each inventing a file format.

**Candidates.** Unreal-style save objects (https://dev.epicgames.com/documentation/en-us/unreal-engine/saving-and-loading-your-game-in-unreal-engine): typed `USaveGame` objects written to named slots per user; strong typing, but engine-reflected classes and no built-in whole-world capture. Godot's documented pattern (https://docs.godotengine.org/en/stable/tutorials/io/saving_games.html): persistable nodes return dictionaries from `save()` and are recreated on load, as JSON lines or binary `store_var`; flexible, but every game writes its own loader and recovery. VICTUS-native: JSON slots with checksums, backups and versioned migrations, plus checkpoints built on the existing scene snapshot format and per-script `save_state`/`load_state` hooks.

**Decision.** The VICTUS-native design. JSON keeps saves inspectable and reuses the engine's parser and limits; the checksum + `.bak` + atomic rename protect against torn writes; `data_version` with ordered migrations makes save compatibility an explicit, testable contract. Checkpoints reuse `Scene::save/load` (component serializers already versioned), so every serializable component is captured without per-game code, while scripts own their private state through hooks (Godot's `save()` idea). Restores happen at a frame boundary to keep systems consistent.

**Evidence.** STATUS Slice 22: store, migration, checkpoint and physics restore tests; template quick save/load tests; exported game writing to the per-user folder.

**Risks / revisit triggers.** Large worlds make JSON checkpoints slow and big (consider binary or compressed payloads, measured first). Runtime state outside components (physics velocities, playback positions) is lost on restore. Multiplayer needs server-side snapshots instead of client checkpoints.

## ADR-0025 — Delta snapshots against acknowledged baselines (accepted 2026-11-16)
**Problem.** Slice 17 snapshots sent every changed entity in full (12-byte float position + 8-byte rotation) and repeated unchanged ones every second to recover from loss, wasting bandwidth and still leaving up to a second of staleness after a lost packet.

**Candidates.** (1) Quake 3 style (https://fabiensanglard.net/quake3/network.php): the server compares the current state with the last snapshot the client acknowledged, sends only changed fields, and falls back to a zeroed dummy baseline (a full update) when no acknowledged snapshot is available; loss just means an older baseline. (2) Per-entity reliable updates (send each change reliably once): no redundant resends, but head-of-line blocking delays fresh transforms behind stale ones. (3) Gaffer On Games snapshot compression (https://gafferongames.com/post/snapshot_compression/): baseline deltas plus bounded-range quantization and smallest-three quaternions with bit packing.

**Decision.** Candidate 1 with byte-aligned zigzag varints: quantize to 1 mm and the existing 16-bit rotation components so both ends hold identical views; the server keeps 32 views per client, the client 64, acks ride on the existing 60 Hz input packets. Bit packing and smallest-three (candidate 3) are deferred until measurements show the varint format is the bottleneck. The full encoding stays behind `ServerOptions::delta_snapshots` for diagnosis and comparison.

**Evidence.** STATUS Slice 23: 977.5 → 485.6 bytes per snapshot in the test scene; exact decoding for a client on a 20%-loss link; header-only idle snapshots.

**Risks / revisit triggers.** A client whose acks are all lost for more than ~1 s gets full (zero-baseline) snapshots until one arrives. Memory is O(clients × views × entities) on the server; very large worlds need sparse views or interest management. Positions beyond ±1000 km clamp.

## ADR-0026 — Input-replay regression captures (accepted 2026-11-16)
**Problem.** Gameplay regressions (script, physics or engine changes that alter how a game plays) need a repeatable test that a developer can create by simply playing, and that CI can run headless.

**Candidates.** (1) Input recording with state checksums: rely on a deterministic simulation given the same initial state and inputs, record only inputs and verify periodic digests (the determinism and per-frame checksum idea in https://gafferongames.com/post/deterministic_lockstep/). (2) State recording: store full scene snapshots every frame and compare; robust to nondeterminism but large and it cannot replay changed code to find regressions. (3) Golden screenshots: catch visual changes but are GPU/driver dependent and say nothing about gameplay state.

**Decision.** Candidate 1. VICTUS already steps simulation with explicit frame times and single-threaded Jolt/Box2D in headless runs; the only nondeterministic gameplay input found was Luau's per-VM `math.random` seed, now fixed per run through `math.randomseed` (https://luau.org/library: the sequence "depends only on seed"). Recording feeds the simulation through the same `ReplayInput` used for playback, so pressed/released edges match by construction. Digests hash names and transforms rounded to 0.1 mm so replays are compared semantically, not by runtime UUIDs.

**Evidence.** STATUS Slice 24: four templates, player-to-headless and Debug-to-Release replays matching; divergence detected at the expected frame.

**Risks / revisit triggers.** Bit-exact floating point is not guaranteed across compilers, OSes or architectures (the same article warns about debug vs release and different machines); captures should be re-recorded per platform if CI shows that. Systems that read wall-clock time or threads with racy order would break determinism. Digests do not see script-only state.

## ADR-0027 — Entity-level capture divergence reports (accepted 2026-11-17)
**Problem.** A capture replay that only says "frame 120: digest X, got Y" tells a developer that gameplay changed but not what changed; finding the cause meant re-running and diffing by hand.

**Candidates.** (1) Store the hashed state lines with each digest and diff them on mismatch (like Factorio's desync reports, which keep both game states so they can be compared, https://wiki.factorio.com/Desynchronization). (2) Store a hash per entity: small, but the report can only name entities, not what or how much changed. (3) Store nothing and re-record a reference run on demand: needs the old build, which is usually gone after the regression lands.

**Decision.** Candidate 1, capped at 4096 entities per digest (`Capture::detail_limit`, 0 disables). The lines are the exact digest input, so the report and the digest can never disagree, and they are human-readable for manual diffing. Factorio's experience (https://factorio.com/blog/post/fff-47) is that at the first diverging tick the difference is usually tiny, so reporting the first differing digest with up to three named entities is what matters.

**Evidence.** STATUS Slice 25: unit, editor and CLI checks name the moved entity and component; 300-frame captures are 20 KB (58 entities) and 184 KB (580+ entities).

**Risks / revisit triggers.** Captures of large scenes grow with entities × digests; if this matters, store per-entity hashes beyond the cap or compress. Divergence in state not covered by the lines (script variables, velocities) still shows up only later as a transform change.

## ADR-0028 — Encrypted, authenticated multiplayer sessions (accepted 2026-11-17)
**Problem.** Multiplayer traffic was plaintext: anyone on the path could read it, inject input or impersonate a server, and servers could not restrict who joins. ENet provides no security.

**Candidates.** Libraries: (1) Monocypher 4.0.2 — X25519, BLAKE2b, XChaCha20-Poly1305, two C files under CC0-1.0/BSD-2-Clause, no dependencies, under 2000 lines (https://monocypher.org/). (2) libsodium — the same primitives and more, ISC licence, portable and widely packaged (https://doc.libsodium.org/), but a much larger build (autotools/MSVC projects, no upstream CMake) to vendor on three platforms. (3) DTLS via OpenSSL or mbedTLS — standard, but certificate infrastructure, large dependencies and a datagram layer that would sit awkwardly under ENet's reliability. Protocol: (a) a Noise pattern (https://noiseprotocol.org/noise.html), NX = client anonymous, server transmits its static key (`-> e  <- e, ee, s, es`); (b) netcode.io-style connect tokens from a web backend (needs an online service, conflicts with "no mandatory vendor"); (c) DTLS handshakes.

**Decision.** Monocypher with an NX-style handshake implemented as a `Transport` decorator, so every transport (UDP, memory, link emulation) and both sessions get it without changing the session protocol. Server authentication comes from DH with the static key (`es`) confirmed by an AEAD tag over the transcript; clients may pin the key the server prints, otherwise they trust and report it. Optional server passwords travel only inside the encrypted channel. Encryption is the default for `victus serve` and clients; `--insecure` opts out on both sides.

**Evidence.** STATUS Slice 26: 7 new tests (tampering, replay, pinning, passwords, plaintext peers, a full lossy two-client session, ENet loopback) and a real UDP run with password and pinned key.

**Risks / revisit triggers.** Not a byte-compatible Noise implementation (simplified key schedule, server static key sent in clear); revisit if third-party clients need interoperability. Trust-on-first-use without `--server-key` lets an active attacker learn passwords. No rekeying or player identities yet. Review Monocypher's changelog and advisories before updating the pinned version.

## ADR-0029 — Listen server: the host plays in its own authoritative session (accepted 2026-11-17)
**Problem.** Playing together required a separate `victus serve` process plus a client per player; a player could not simply host and play, which is how most small co-op sessions start.

**Candidates.** (1) In-process host character: the server spawns a server-owned copy of the player template driven by the machine's own input (the routing fallback), with no prediction (Unreal and Source "listen server" model; https://developer.valvesoftware.com/wiki/Source_Multiplayer_Networking). (2) In-process server plus a local client over a loopback transport, each with its own scene copy — uniform code paths, but two worlds in memory, double simulation, and the host suffers interpolation delay and corrections for no reason. (3) Spawn a `victus serve` child process and connect to it — no engine changes, but two processes to manage and the same loopback costs as (2).

**Decision.** (1). `ServerOptions::host_player/host_name`; the host's character is tracked like any player (kind `kPlayer`, owner `kServerId`), appears first in rosters and `clients()` as id 0 and is `NetServer::local_player()`; scripts see the same values as offline (`net.authority()` and `is_local()` true). `victus run`/`victus_player --host` wire it up with the same encryption, key file and password options as `victus serve`.

**Evidence.** STATUS Slice 27: a session test with a host and a remote client (independent movement, replication to the client, rosters, the host surviving a client leaving) and a real UDP run of `victus run --host` with a headless client, rendered as "Hosting 2 players".

**Risks / revisit triggers.** The host has zero latency to the authority (unfair for competitive games; use `victus serve`). The session ends when the host quits (no host migration). The server ticks inside the host's frame loop, so a slow host slows everyone; revisit with a fixed-rate server tick if hosts drop frames.

## ADR-0030 — Reconnect with server-issued tokens and held characters (accepted 2026-11-17)
**Problem.** A dropped connection (Wi-Fi blip, network switch, a frozen laptop) removed the player's character and score; the client could only fail and start over as a new player.

**Candidates.** (1) Server-issued random token in the welcome, presented in a later hello; the server holds the character for a grace period (Unreal's inactive PlayerState model, https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/GameFramework/AGameMode). (2) Match by network address — no protocol change, but addresses change on exactly the network switches reconnect exists for, and NAT can make two players share one. (3) Match by player name — trivial to spoof and names are not unique. (4) Transport-level session resumption (keep the session alive under a new address, like QUIC connection migration) — invisible to the session layer, but ENet has no migration and the encrypted layer would need resumable keys.

**Decision.** (1), protocol version 4. Tokens come from the OS random generator and travel only after the handshake (encrypted by default). Held characters stay in the world idle, leave the roster and count toward `max_clients`; a hello whose token matches a still-connected client retires that stale connection first. Clients retry every `reconnect_interval` (1 s) for `reconnect_window` (20 s); after a rejoin they drop snapshot baselines, prediction history and clock sync and prune entities the server did not re-announce. Secure-layer refusals (wrong password or key) are final; handshake timeouts during a rejoin are retried.

**Evidence.** STATUS Slice 28: two session tests (server noticed / did not notice the drop, same id and character afterwards, score kept, no duplicates on any machine; grace expiry gives a fresh player and prunes the old one; a client that never returns fails; goodbyes release at once) and a real encrypted UDP run where a client frozen for 16 s rejoined as the same client.

**Risks / revisit triggers.** Anyone holding the token can take the character over (it is a bearer secret; with `--insecure` it travels in clear). Held characters are frozen in place and can be hit or pushed while their owner is away; games can react to `client_dropped`. No persistence across server restarts. Revisit when player identities arrive (bind tokens to accounts).

## ADR-0031 — State probes in capture digests (accepted 2026-11-17)
**Problem.** Capture digests covered entity names and transforms only. A script whose score, timer or state machine diverged, or a body whose velocity changed before it had moved 0.1 mm, passed the replay check until (and unless) a transform drifted, and then the report named the symptom, not the cause.

**Candidates.** (1) Registered probes that add readable `@path|kind|value` lines next to the transform lines (Factorio's "heuristic CRC" of selected crucial state plus human-readable tags in its state dumps, https://www.factorio.com/blog/post/fff-55 and https://factorio.com/blog/post/fff-47). (2) Hash the serialized scene (every component) — complete, but editor-only and cosmetic fields would fail replays, and the report could only say which bytes differ. (3) Per-subsystem checksums recorded after each system (Photon Quantum's `recordChecksum` steps and per-component checksum dumps, https://doc.photonengine.com/quantum/v1/community-wiki/knowledge-base/debugging_desyncs) — pinpoints the system, but says nothing about which value, and needs one hash per system per digest. (4) Scripts opt in through `save_state()` — reuses existing code but most scripts do not implement it.

**Decision.** (1). `gameplay::register_state_probe(name, fn)`; the script host probes started instances' own primitive fields (`_`-prefixed fields are private), physics probes velocities, spin and grounded state; values are rounded to 1e-4 and sorted with the other lines. Capture format version 2 marks probe-aware digests; version-1 captures keep transform-only digests so recorded regression suites stay valid.

**Evidence.** STATUS Slice 29: a script-only divergence that moves nothing fails with "Keeper: script.score 11 expected 10" (and is missed by a version-1 capture of the same run); all four templates record and replay clean with probes; version-1 captures from the previous build still verify.

**Risks / revisit triggers.** Any newly probed value can make older version-2 captures of a changed game fail; deliberate. Scripts that keep caches or debug counters in public fields make replays fail on them — rename to `_field`. Revisit (bump the format) when adding probes for joints, animation or UI, and if probe cost shows up in profiles of large scenes.

## ADR-0032 — Editor-hosted play sessions and replication inspection (accepted 2026-11-17)
**Problem.** Multiplayer games could only be debugged from terminals (`victus serve`, `victus run --connect`) with no view of who owns what, which entities are replicated to whom, or what bandwidth they cost.

**Candidates.** (1) The editor's Play-mode scene becomes a listen server (the existing `NetServer` with a host player) and the editor reads counters the session keeps per entity and per client (Unreal's Play-In-Editor "Play As Listen Server" net mode and the configurable player count, https://dev.epicgames.com/documentation/en-us/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine ; Unity Netcode for GameObjects' Network Profiler with per-frame byte totals and per-object activity, https://docs-multiplayer.unity3d.com/tools/current/profiler/). (2) Run a separate `victus serve` process and attach to it over a debug socket — isolates crashes but needs a second protocol and process management. (3) Inspect packet captures — no ownership or relevance information.

**Decision.** (1). Counters live in the session (cheap integer adds in the snapshot and variable loops) and are exposed as plain structs (`ReplicationInfo`, `ClientDiagnostics`) so other tools (CLI, future profilers) can use them. Editor hosting always uses real encrypted UDP so external clients can join with the shown key; recording stays offline so captures remain deterministic.

**Evidence.** STATUS Slice 30: an in-process client joins the editor-hosted session over UDP with the pinned key and appears in the clients and replication tables with the right owner and traffic.

**Risks / revisit triggers.** The editor process now also carries server load; heavy sessions should use `victus serve`. Revisit when adding multi-client play mode (several clients in one editor) and when sessions exceed a few thousand replicated entities (table virtualisation, sampling).

## ADR-0033 — In-editor clients as full client machines over loopback UDP (accepted 2026-11-17)
**Problem.** Testing a multiplayer game from the editor needed several terminals; prediction, interpolation and per-player HUDs could not be checked side by side with the host.

**Candidates.** (1) Each in-editor player is a complete client (own scene copy, scripts, physics) talking to the editor's listen server over real UDP loopback with the session's encryption (Unreal's Play-In-Editor "Number of Players" with "Run Under One Process", https://dev.epicgames.com/documentation/en-us/unreal-engine/play-in-editor-multiplayer-options-in-unreal-engine). (2) Clients on `MemoryNetwork` — deterministic and faster, but the editor's server is on UDP for external players, and a second transport would hide UDP/encryption problems. (3) Separate player windows/instances launched by the editor (as in Unity Multiplayer Play Mode, whose up to three Virtual Players open in separate windows, https://docs-multiplayer.unity3d.com/mppm/current/about/) — isolation and real windows, but process management, an extra editor instance per player and no shared inspector.

**Decision.** (1), capped at 3 clients. The viewed peer gets the keyboard and the panels; the rest idle. Nothing is shared between peers except assets on disk and the job system.

**Evidence.** STATUS Slice 31: two in-editor clients join with key and password; driving one moves only its character on the server, its prediction and the other client's remote copy.

**Risks / revisit triggers.** Simulation cost scales with peers; heavy projects should test with `victus run --connect`. Revisit for split-screen viewing, bots driving idle peers, or more than 3 clients.

## ADR-0034 — Material assets as small JSON files referencing textures by UUID (accepted 2026-11-17)
**Problem.** Mesh renderers only had a colour, metallic and roughness; a game could not put a texture on a primitive, tile a floor texture or share one look across many objects without importing a glTF per surface.

**Candidates.** (1) A `.vmat` JSON asset (PBR factors, four texture slots by asset UUID, UV scale/offset, filter, alpha cutoff, unlit, double sided) used from source like prefabs and referenced from `MeshRenderer`. (2) Inline material fields on `MeshRenderer` — no sharing, every entity edited separately. (3) A cooked binary material format — consistent with textures/models, but materials are tiny, hand-editable and change often; cooking adds a step without a size or speed benefit. (4) A material graph — the long-term direction (ROADMAP Phase 11), but it needs a shader compiler at import time first.

**Decision.** (1). Texture references are UUIDs so renames keep working; type errors in the file are reported (not silently defaulted) while missing keys keep defaults. The material replaces the mesh's own material; `MeshRenderer.base_color` stays a per-entity tint. The GPU asset cache memoizes results including failures, so a broken file is read once; broken or missing materials fall back to the component's own look and count as missing assets. UV scale/offset follow KHR_texture_transform's order (scale, then translate). Files are saved with 6 significant digits so hand-typed values stay readable.

**Evidence.** STATUS Slice 33: tiling 8× multiplies on-screen checker transitions; hot reload swaps an edited material without a restart; broken JSON and unknown UUIDs keep drawing; export and `victus check` reject bad references.

**Risks / revisit triggers.** No material inheritance/instances yet; shader variants are fixed to the built-in PBR shader. Revisit when project shaders or a material graph land (the file gains a `shader` field and parameters), or if material count makes per-file loading slow.

## ADR-0035 — Project surface shaders compiled at load time with glslang and SPIRV-Cross (accepted 2026-11-17)
**Problem.** Every mesh used the one built-in PBR shader; games could not author animated, stylised or procedural surfaces (energy fields, dissolves, holograms, water tints) without changing engine code.

**Candidates.** (1) Surface functions in GLSL spliced into the built-in PBR fragment shader and compiled when first used, with glslang and SPIRV-Cross linked into the engine (Godot's spatial shaders, where `fragment()` writes `ALBEDO`, `ROUGHNESS`, `EMISSION` etc. and the built-in renderer does the lighting, with a global `TIME`, https://docs.godotengine.org/en/stable/tutorials/shaders/shader_reference/spatial_shader.html). (2) Whole custom vertex+fragment shaders — full freedom, but every shader must re-implement shadows, SSAO, fog and lighting and breaks whenever the renderer changes. (3) Compile at import time with the `glslangValidator` CLI — needs the Vulkan SDK on every user's machine. (4) A node-based material graph — friendlier, but it needs (1)'s compiler path first.

**Decision.** (1). The `Surface`/`SurfaceInput` structs in `pbr.frag` are a stable contract; the surface runs after texture sampling and before lighting. Shaders cannot add resources — they get four per-material `vec4` parameters (`Material` UBO `custom[4]`) and time, which keeps the pipeline layout identical to the built-in shader so SDL_GPU resource counts never change. Compilation happens in `GpuAssetCache` (results and failures cached; errors fall back to built-in PBR), `victus check`/export compile every shader so broken shaders never ship, and hot reload recompiles. glslang 16.6.0 (released 2026-09-10, https://github.com/KhronosGroup/glslang/releases/tag/16.6.0) and SPIRV-Cross vulkan-sdk-1.4.363.0 are fetched by CMake with pinned hashes; glslang is built without HLSL, optimizer, tools or tests. MSL is generated only on Metal devices.

**Evidence.** STATUS Slice 36: params and time change on-screen pixels; a compile error falls back and recovers through hot reload; error messages carry the `.vshader` line number; the 3D template's glowing cube works in `victus run`, the editor and an exported game.

**Risks / revisit triggers.** glslang adds build time and binary size; first use compiles on the render thread. No D3D12 DXIL path (Vulkan is used on Windows). Revisit for a shader cache on disk/in packs, async compilation, vertex/sprite/post-process hooks, extra textures per shader, or a material graph that emits surface code.
## ADR-0037 — Packed vertex colour in Vertex3D; fog and coverage in the forward PBR shader (accepted 2026-11-17)
**Problem.** Procedural and stylised games (AURORIA first) colour meshes per vertex, need distance fog for atmosphere and a weather coverage layer (snow) masked per vertex; VICTUS had none of these.

**Candidates.** (1) One packed RGBA8 colour in every `Vertex3D` (4 bytes, default white so existing meshes are unchanged) plus uniform-driven fog and coverage in `pbr.frag`. (2) A separate optional colour vertex stream — no cost for meshes without colour but doubles pipeline variants. (3) Bake colours into textures — loses per-vertex authoring and needs UVs.

**Decision.** (1). RGB is stored sRGB-encoded (glTF COLOR_0 linear values are encoded on import) and decoded in the vertex shader; alpha is linear and either opacity or, per material, a coverage mask. Fog is applied in the forward pass after lighting; coverage blends albedo/roughness on faces whose normal.y exceeds a threshold.

**Evidence.** STATUS Slice 35.1 GPU probes.

**Risks / revisit triggers.** 4 extra bytes per vertex for all meshes; revisit if vertex bandwidth matters on mobile. Height fog and sky fog are not done.

## ADR-0036 — Material instances as sparse .vmat files with a parent reference (accepted 2026-11-17)
**Problem.** Variations of one look (team colours, damaged versions, shader parameter tweaks) required copying a whole material; a later change to the shared look had to be repeated in every copy.

**Candidates.** (1) A `"parent"` UUID in the same `.vmat` format, the file storing only the keys it overrides, resolved at load time (Unreal's Material Instance Constants inherit everything from a parent and change only exposed parameters without recompiling, https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-materials-in-unreal-engine). (2) A separate `.vmatinst` asset type — clearer in listings, but duplicates parsing, references and editor code for the same fields. (3) Parameters explicitly exposed by the parent (Unreal's model) — finer control, but every VICTUS material field is already a plain value, so the extra declaration step brings no benefit yet.

**Decision.** (1). Every field can be overridden; presence of a key is the override (so `null` textures override to none). Resolution happens in `AssetDatabase::resolve_material`, which the renderer cache, export and `check` share; chains are capped at 16 levels and cycles are errors. Because surface shaders read their values from material parameters, instances also vary shader looks without new shaders.

**Evidence.** STATUS Slice 37: three-level inheritance, propagation of parent edits through hot reload, rejected cycles/missing parents, and the editor's inherited/override markers.

**Risks / revisit triggers.** Resolution reads each file in the chain per cache miss (cheap for small chains). Revisit if parents need to lock fields, if run-time instances from scripts are needed, or if load times grow with deep chains (cache resolved parents).

### ADR-0037: Scene transitions are validated at the call and applied at the end of the update
- Status: Accepted (2026-11-17, Slice 38).
- Context: games need menus, levels and restarts; before this slice only the startup scene (or a checkpoint) could be loaded.
- Decision: `scene.load(path, params?)` reads and fully parses the target through `HostOptions::scene_loader` (default: `<project root>/<path>` through mounted packs) and returns `nil, error` when it is missing, outside the project or invalid; a valid request replaces the scene at the end of the current update (the newest of `scene.load`, `scene.reload` and `save.restore` wins). Every script instance is dropped and starts again; the single Luau VM and module-level state survive, and JSON-serialisable `params` reach the next scene via `scene.params()`. Hosts reset physics and audio through `on_scene_loaded`. Checkpoints store the scene path and params. Export/check reject literal `scene.load("...")` targets that are not project scenes.
- Consequences: transitions are deterministic (captures replay them) and work identically in `victus run`, exported games, `victus simulate` and editor play mode (which changes only its play copy). No additive or asynchronous loading yet: large scenes load synchronously within one frame.

### ADR-0038: Sprite animation uses grid sprite sheets (.vsheet) and a SpriteAnimator that writes Sprite UVs
- Status: Accepted (2026-11-17, Slice 39).
- Context: 2D games need animated characters and props; sprites could only show a whole texture.
- Candidates: (1) a JSON `.vsheet` asset that slices one texture into a grid and names clips, played by a `SpriteAnimator` component that sets the Sprite's texture and a new `uv` region (Godot's `Sprite2D` grid plus `SpriteFrames` clips, https://docs.godotengine.org/en/stable/classes/class_spriteframes.html); (2) one texture per frame — simple, but many textures break sprite batching; (3) packed atlases with per-frame rectangles — best texture usage, but needs a packer or external tool format.
- Decision: (1). Frames are numbered row by row; clips are explicit frame lists or `from`/`to` ranges with fps and loop. `AnimationSystem::update_sprites` runs inside `update()` (and with dt 0 in the editor for preview); a clip change restarts it; non-looping clips hold the last frame and report `finished`. Missing or invalid sheets leave the Sprite unchanged and are reported by `victus check`/`export`. Sheets hot-reload by clearing the system's cache.
- Consequences: every frame of a character shares one texture, so the batcher keeps one draw. Linear filtering can bleed neighbouring cells at frame edges; nearest filtering/insets and packed atlases remain open.

### ADR-0039: Texture filtering is an import setting read at draw time
- Status: Accepted (2026-11-17, Slice 40).
- Context: pixel-art sprites and sprite sheets need point sampling; linear filtering blurred them and bled neighbouring sheet cells. Materials already had a per-material `filter`, sprites had none.
- Candidates: (1) a `"filter"` key in the texture's import settings, read by the GPU asset cache when sprites and materials are drawn (Godot exposes texture filtering on the canvas item using the texture, Unity's Texture Import Settings carry a Filter Mode per texture); (2) a filter field on every Sprite component — flexible but repetitive for whole sheets; (3) bake a sampler into the cooked texture — the RHI binds samplers separately from textures, so this would still need a lookup.
- Decision: (1), with the sprite batch splitting batches by filter and materials using nearest when either the material or its base colour texture asks for it. The setting is not baked into the pixels; changing it re-imports (settings are part of the import key) and evicts the cache.
- Consequences: one switch per texture fixes pixel art and sheet bleeding everywhere it is used. Wrap mode stays fixed (sprites clamp, materials repeat).

### ADR-0040: External simulations run as project-declared helper processes; scripts build procedural meshes by id
- Status: Accepted (2026-11-17, Slice 41).
- Context: some games keep logic in an external program (a simulation server, an AI service, a tool written in another language) that speaks JSON lines, and some generate geometry at run time; VICTUS scripts are sandboxed and had no process, mesh-building or module APIs.
- Candidates: (1) projects declare named helpers in `victus.project` `bridges`; scripts can only open those names, so a script cannot run arbitrary commands; (2) a generic `os.execute`-style API — breaks the sandbox; (3) embed the .NET runtime — heavy and specific to one game. For meshes: (a) a runtime `ProceduralMeshComponent` holding an immutable shared mesh with a unique id that the GPU cache uploads once and collects when unused (Unity `Mesh.SetVertexBufferData` copies packed vertex data in a declared layout, https://docs.unity3d.com/ScriptReference/Mesh.SetVertexBufferData.html; Godot `ArrayMesh.add_surface_from_arrays`, https://docs.godotengine.org/en/stable/classes/class_arraymesh.html); (b) write temporary glTF assets — slow and pollutes the project.
- Decision: (1) and (a). Script layouts describe packed vertices (`f32x2/3`, `s8x4`, `u8x4`, `skip:N`) so bridge buffers decode without per-vertex Luau work; mirroring `scale` converts left-handed data and flips winding. `require` shares module tables across scripts. Time spent waiting on a bridge does not count towards the script time budget.
- Consequences: games with external simulations ship the helper next to the game and declare it; procedural meshes are runtime-only (not saved, no colliders yet).

### ADR-0041: Tilemaps store sparse cells and build merged static boxes for 2D physics
- Status: Accepted (2026-11-17, Slice 42).
- Context: 2D games need grid levels that are painted in the editor or generated by scripts, drawn efficiently, and collide with the 2D character mover and bodies; VICTUS had sprites and Box2D colliders but no grid representation.
- Candidates: (1) a `Tilemap` component with a sparse cell map (any size, negative coordinates, scripts paint freely) plus `.vtileset` assets describing the texture grid, per-tile collision and terrain rules (Godot TileSet atlases, physics layers and terrain sets, https://docs.godotengine.org/en/stable/tutorials/2d/using_tilesets.html); (2) dense fixed-size chunks — faster iteration but resizing and sparse levels cost memory; (3) one entity per tile — simple but floods the scene and physics. For collision: (a) merge solid cells into rectangles on one static body (Unity merges tile shapes with a Composite Collider, https://docs.unity3d.com/Manual/tilemaps/work-with-tilemaps/tilemap-collider-2d-reference.html); (b) one Box2D body per tile; (c) chain shapes around outlines — fewer shapes but harder with one-way tiles and holes.
- Decision: (1) and (a). Physics gains a generic runtime-only `StaticShapes2DComponent` so the physics module does not depend on tilemaps; tile sets autotile with a 16-entry side-neighbour mask; one-way tiles never merge vertically so only their top surface supports.
- Consequences: painting rebuilds one body per map (cheap for typical levels; very large maps rebuild whole). Slopes and per-tile polygons need a later extension of the box list; drawing is per cell without culling.

### ADR-0042: Image-based lighting bakes on the GPU with fragment passes and uses SH9 for diffuse
- Status: Accepted (2026-11-17, Slice 44).
- Context: high-end look needs environment lighting and reflections from real HDR skies; the target includes entry-level Android GPUs where SDL_GPU compute support, bandwidth and memory are limited.
- Candidates: prefilter (1) offline in the cooker, (2) on the CPU at load, (3) on the GPU at load with fragment passes, (4) GPU compute. Diffuse from (a) an irradiance cubemap or (b) 9 spherical-harmonic coefficients (Ramamoorthi & Hanrahan 2001, https://cseweb.ucsd.edu/~ravir/papers/envmap/envmap.pdf). Specular follows the split-sum approximation with GGX importance sampling (Karis 2013, https://cdn2.unrealengine.com/Resources/files/2013SiggraphPresentationsNotes-26915738.pdf) and filtered importance sampling (Křivánek & Colbert, GPU Gems 3 ch. 20, https://developer.nvidia.com/gpugems/gpugems3/part-iii-rendering/chapter-20-gpu-based-importance-sampling).
- Decision: (3) + (b). The GPU bake runs on every SDL_GPU backend (no compute requirement), takes one frame of work, and its size/sample count scale per quality tier (256/64, Low 128/32); SH9 is computed on the CPU at cook time and costs nine multiply-adds per pixel instead of a second cube fetch. Cubes are RGBA16F; the cooked texture stores half-float equirect pixels (licence: stb, public domain/MIT, already vendored; no new dependency).
- Consequences: changing an environment needs a re-bake (cheap); dynamic time-of-day (next slice) re-bakes a small cube. Revisit (1) if load time on phones matters more than package size, and add a BRDF LUT if the analytic split-sum approximation shows artefacts.

### ADR-0043: Physical sky is evaluated on the CPU into a small equirect and baked through IBL
- Status: Accepted (2026-11-17, Slice 45).
- Context: time of day must change sky, ambient and reflections together, and stay cheap on low-end phones.
- Candidates: (1) per-pixel ray marching in the sky shader (Nishita) — cost every frame and does not light the scene; (2) precomputed LUTs (Bruneton & Neyret 2008, https://inria.hal.science/inria-00288758; Hillaire 2020, https://sebh.github.io/publications/egsr2020.pdf) — best quality incl. multiple scattering but needs compute or several render passes per change; (3) single-scattering evaluation of a 128x64 equirect on the CPU when the sun moves, fed into the existing GPU prefilter + SH9 path.
- Decision: (3). It reuses ADR-0042, costs nothing per frame, works on every backend, and keeps sky, IBL and sun colour consistent. Coefficients from Hillaire 2020. No new dependency.
- Consequences: no multiple scattering (compensated by `sky_gain`); re-bakes cost ~21 ms (5 ms on Low) and happen only on ~0.5° sun moves. Revisit with (2) when compute paths exist and for planet-scale views.

### ADR-0044: Reflection probes are captured through readback into the existing IBL bake
- Status: Accepted (Slice 46)
- Context: local reflections need scene captures prefiltered like the global environment.
- Options: (a) render cube faces on the GPU and blit into cube layers, then prefilter in place; (b) render six faces, read back, convert to equirect and reuse `EnvironmentMap::create` (ADR-0042). Per-draw nearest probe versus per-pixel blending of several probes.
- Decision: (b), because it reuses the verified prefilter/SH path with no new GPU resource types; the stall is bounded by a capture budget (default 1 per frame) and captures only happen on change. Each draw uses the smallest containing axis-aligned box (one probe binding, keeps batching), with Lagarde and Zanuttini 2012 box projection for specular and the probe SH9 for diffuse.
- Consequences: no seams between probes are hidden yet (no blending/fade); a GPU-only capture path can replace (b) later without changing the component or shader interface.

### ADR-0045: TAA reprojects from depth; dynamic resolution uses CPU frame time
- Status: Accepted (Slice 47)
- Context: TAA needs per-pixel history positions. Full motion vectors need an extra render target written by every opaque pipeline (built-in, skinned, surface shaders) plus previous-frame model matrices and skin palettes.
- Options: (a) per-object motion vector MRT; (b) camera-only reprojection from depth with neighbourhood variance clipping (Karis 2014, Salvi 2016) bounding errors on moving objects; (c) FXAA/SMAA only.
- Decision: (b) now. It adds one fullscreen pass and two history textures, changes no material pipeline, and is correct for the dominant case (camera motion over static geometry); clipping removes ghosts from moving objects at the cost of some softening. The shader interface (reprojection per pixel) lets (a) be added later by replacing the depth-derived position with a velocity sample. TAA is enabled at High/Ultra; Low/Medium keep FXAA because the extra full-resolution RGBA16F read/write is a large share of bandwidth on entry-level phones.
- Dynamic resolution measures CPU frame time (SDL_GPU exposes no GPU timestamps), scales by sqrt(target/measured) with a cooldown, and recovers in small steps after sustained headroom to avoid oscillation. Fixed-step, recorded and replayed runs keep a constant scale so captures stay deterministic.

### ADR-0046: Clustered forward lighting with CPU light assignment
- Status: Accepted (Slice 48)
- Context: the renderer is forward (needed for transparency, cheap MSAA and tile-based mobile GPUs) and limited to 16 lights in a uniform buffer.
- Options: (a) deferred shading; (b) tiled forward (2D tiles, depth bounds from a pre-pass); (c) clustered forward (Olsson et al. 2012) with 3D clusters, no depth pre-pass dependency; light assignment on the CPU or in a compute shader.
- Decision: (c) with a 16x9x24 grid, logarithmic slices and CPU assignment. Clusters do not need the depth pre-pass (which the Low tier skips), work for transparent surfaces, and keep a single material path. CPU assignment is a few hundred microseconds for hundreds of lights, avoids compute shaders (unavailable or slow on some mobile drivers) and is unit-testable for conservativeness. Lights and the cluster list live in fragment storage buffers, which SDL_GPU supports on Vulkan, Metal and D3D12.
- Consequences: very high light counts (thousands, many per cluster) should move assignment to compute; the per-cluster cap (128) drops the farthest lights in extreme overlaps and is reported in stats.

### ADR-0047: Cooker-side BC and ASTC variants with runtime selection
- Status: Accepted (Slice 49)
- Context: textures need GPU block compression for memory and bandwidth, especially on phones. SDL_GPU supports BC1-7 and ASTC LDR but no ETC2/EAC formats, and compressed textures cannot have mips generated at run time.
- Options:
  - Encoders: (a) Basis Universal / KTX2 supercompression with transcoding at load; (b) direct encoders: bc7enc_rdo (MIT/Unlicense) for BC1/BC3/BC7 and Arm astcenc (Apache-2.0) for ASTC; (c) GPU compute encoders.
  - Variant handling: one format per platform at export time, or several variants per cooked file with selection at load.
- Decision: (b), with variants inside the cooked file, selected at load by `supports_format`, falling back to RGBA8.
  - Direct encoders target each GPU format natively, so there is no intermediate-format quality loss and no runtime transcoder.
  - Both libraries are small, permissively licensed and portable C++.
  - Keeping several variants in one cooked file lets the editor, desktop player and phone share a cache. ETC2 is skipped because SDL_GPU cannot create it; ASTC LDR is the common compressed format of Vulkan-capable mobile GPUs (Mali, Adreno, PowerVR, Apple).
  - Compression is opt-in per asset for now, so existing projects and pixel-exact tests are unchanged.
- Consequences:
  - Cook time and cached size grow with each variant. Exports should strip the variants a platform cannot use (follow-up).
  - Revisit (a) if download size dominates over load time.
  - HDR textures stay uncompressed until BC6H/ASTC HDR are added.

### ADR-0048: Android app as an SDLActivity shell around the native player
- Status: Accepted (Slice 50)
- Context: VICTUS must run on entry-level Android phones. The engine is C++ on SDL3 and SDL_GPU, and exported games are `game.vpak` packs opened by file path. SDL_GPU on Android has only a Vulkan backend (no OpenGL ES).
- Options:
  - App shell: (a) SDL's `SDLActivity` Java glue, with the engine in `libmain.so`; (b) `GameActivity` (AGDK) with our own window, input and audio glue; (c) `NativeActivity` with no Java.
  - Build: (a) Gradle with AGP `externalNativeBuild` driving the root CMake project; (b) a standalone CMake + `aapt2`/`d8`/`apksigner` script.
  - Pack access: read the pack straight from the APK through `AAssetManager`, or install it once to internal storage.
- Decision: SDLActivity with Gradle/AGP 9.5.1, and install-once to internal storage.
  - SDLActivity already implements the window, touch, gamepads, audio, IME and lifecycle events the platform layer consumes, and it ships with the SDL release we pin.
  - The Java glue is extracted from that same hash-checked tarball, so desktop and Android cannot drift. SDL is built shared on Android so its JNI exports survive linking.
  - AGP is the supported path for signing, Play bundles and Android Studio, and it builds the unchanged root CMake project.
  - Installing the pack keeps `pack::Pack` path-based, with one code path on every platform. The copy is streamed, atomic and skipped when the size and header (TOC hash) match.
  - Vulkan 1.1 is declared as a required manifest feature, so stores filter out devices SDL_GPU cannot drive.
  - The player picks `mobile_quality` (default medium) and `mobile_target_fps` (default 30, dynamic resolution) on phones.
- Consequences:
  - The pack takes its size twice on disk, and the first launch pays one copy. Revisit with `AAsset_openFileDescriptor`-based reads of the stored (uncompressed) asset if download size or first-launch time matters.
  - Only arm64-v8a is built. Devices without Vulkan 1.1 are unsupported until SDL_GPU gains a GLES backend.
  - No device or emulator run is verified yet. CI verifies the APK structure, exports and 16 KB alignment, and host tests cover the install and lifecycle logic.
  - GameActivity remains an option if SDL's Java layer becomes limiting (Game Mode, Performance Hint, predictive back).

### ADR-0049: Mesh optimisation and discrete LODs with meshoptimizer
- Status: Accepted (Slice 54)
- Context: imported meshes keep the glTF exporter's triangle and vertex order, and distant objects draw every triangle. Phones are vertex-bound well before desktop GPUs are.
- Options:
  - Library: (a) meshoptimizer (MIT, small portable C++, vertex cache/overdraw/fetch optimisers and an attribute-aware quadric simplifier); (b) our own quadric edge collapse; (c) offline DCC-authored LODs only.
  - Representation: (a) discrete LOD index lists sharing one vertex buffer; (b) per-LOD vertex buffers; (c) clustered (meshlet/Nanite-style) continuous LOD.
- Decision: library (a), representation (a).
  - The importer runs `generate_lods` (default 3 levels, each half the previous triangle budget, error at most 5% of the mesh extent; positions, normals, UVs and, for skinned meshes, the dominant joint are weighted) and then `optimize_mesh` (vertex cache, overdraw within 5% extra misses, fetch remap). Settings live in the model `.meta` (`optimize_meshes`, `lods`, `lod_error`) and are only written when changed.
  - Every level is simplified from the full mesh, so errors do not accumulate, and stores its geometric error in mesh units. The renderer projects that error with the camera's vertical pixel scale, the object's largest axis scale and the distance to its bounds, and picks the coarsest level within `lod_error_pixels` (1 px by default, 2 Low, 1.5 Medium, 0.5 Ultra).
  - All levels share the vertex (and skin) buffers and are concatenated into one index buffer, so a LOD switch is a different `first_index`/`index_count` and instancing still works (batches split by level).
  - Collision, navigation and CPU readers keep using LOD 0 (`MeshData::indices`).
- Consequences:
  - Index memory grows by about the sum of the level sizes (under 1x); the cooked format moves to v6 and the model importer to v5, so caches re-import once.
  - Switches pop (no cross-fade or dithering yet); the 1 px default keeps this below visibility on tests.
  - GPU-driven culling and indirect draws are a separate step (SDL_GPU has indirect draws, but no draw count buffer), as are occlusion culling and clustered LOD.
- Addendum (2026-11-18, roadmap 6b H1): shadow passes keep the main-camera level (as Godot and Unreal do by default) and add `RenderSettings::shadow_lod_bias` (0..3; Low 1, other tiers 0): directional cascades and local shadow tiles draw `lod + bias`, clamped per mesh, batched by that level; `force_lod` ignores the bias. Independent per-cascade selection from shadow texel density was rejected for now because the shadow silhouette could diverge from the lit surface. `SceneStats::shadow_triangles` and the `frame.shadow_triangles` profile counter report the shadow-pass cost. Evidence: docs/audits/CAMERA_RESPONSIVE_LOD.md.

### ADR-0050: Optional packed HDR colour (R11G11B10F) for bandwidth-bound GPUs
- Status: Accepted (Slice 55)
- Context: entry-level phones (e.g. Mali-G52 MC2 on a shared LPDDR4X bus) are limited by framebuffer bandwidth, not shader ALU. The HDR scene colour, bloom chain and TAA history were always RGBA16_FLOAT (8 bytes per pixel), and nothing in that chain uses alpha or negative values: blending uses source alpha, FXAA reads luma from the tonemapped LDR target, and tonemap, bloom and TAA read only RGB.
- Options: (a) keep RGBA16F everywhere; (b) R11G11B10_FLOAT always; (c) R11G11B10_FLOAT opt-in per renderer.
- Decision: (c). `SceneRendererOptions::compact_hdr` selects R11G11B10_FLOAT for those targets and their pipelines when the device can sample and render to it, else RGBA16F.
  - It halves colour traffic per pass on tiled GPUs. Its 6/6/5-bit mantissas sit well below tonemapped 8-bit output in practice, which is why most console engines use the same format.
  - Opt-in keeps desktop output and pixel-exact tests unchanged. Environment maps and reflection captures stay RGBA16F because they are filtered and reused many times.
- Consequences: the format is fixed when the renderer is created (pipelines are built then). Games enable it on phones; AURORIA does so in its phone profile (D-114).

### ADR-0051: GPU occlusion culling with a Hi-Z pyramid and indirect draws
- Status: Accepted (Slice 55)
- Context: the CPU frustum-culls and instances draws, but everything inside the frustum is shaded, even when a wall hides it. SDL_GPU 3.4 has compute pipelines and indirect draws, but no draw-count buffer (no multi-draw-indirect-count) and, unless the device feature is requested, no non-zero `first_instance` in indirect commands.
- Options:
  - Occluders: (a) the depth pre-pass of the current frame; (b) last frame's depth reprojected (two-phase); (c) CPU software rasterised occluders; (d) hardware occlusion queries.
  - Pyramid storage: (a) a storage buffer with every level packed; (b) a mipped R32F storage texture.
  - Output: (a) one indirect command per CPU batch with a GPU-written instance count; (b) a fully GPU-built draw list (needs draw-count buffers).
- Decision: occluders (a), storage (a), output (a).
  - When the pre-pass runs (SSAO or `depth_prepass`), `hiz_depth.comp` writes the farthest depth of each 8x8 tile, and `hiz_reduce.comp` halves it to 1x1 (one compute pass per level, so SDL orders the writes). `occlusion_cull.comp` projects each opaque main-pass instance's world AABB with the same (TAA-jittered) matrix, picks the coarsest level where the rectangle spans at most 2 tiles per axis and keeps the instance if its nearest depth is not behind the farthest Hi-Z depth (plus a depth-format tolerance). Boxes crossing the camera plane and partly off-screen rectangles are kept; fully off-screen ones are dropped.
  - Survivors are appended with an atomic counter to the batch's indirect command, packed from the batch's own instance offset, so commands use `first_instance = 0` and the draw binds the instance stream at that offset.
  - A buffer pyramid needs no extra texture formats or storage-texture usage, which keeps the same path on Vulkan, Metal and D3D12, and phones.
  - The pre-pass, shadows and transparent draws are unchanged. Only the main (shaded) pass is culled, so the depth buffer, and therefore the image, is identical with culling on or off.
  - RHI additions: `ComputePipelineDesc`/`create_compute_pipeline`, `ComputePass` (pipelines, read-only storage buffers, samplers, dispatch), read-write buffers per compute pass, compute uniforms, `RenderPass::draw_indexed_indirect`, `Device::read_buffer`, `BufferUsageComputeRead`, `DeviceCapabilities::compute`, dispatch and indirect-draw stats. The shader generator reflects compute workgroup sizes and read-write counts, and only recompiles shaders whose hash changed.
- Consequences:
  - Occluders are only pre-pass geometry (opaque, not alpha-tested or surface-shaded). Without a pre-pass (Low tier without SSAO) there is no culling.
  - Fragment shading is saved, but vertex work for hidden objects remains in the pre-pass. A two-phase, previous-frame Hi-Z variant could also cull the pre-pass and shadows later.
  - CPU batching still runs; there is no GPU frustum culling or GPU LOD selection, and indirect draws are one call per batch (no draw-count buffers in SDL_GPU).

### ADR-0052: Local light shadows in one perspective shadow atlas
- Status: Accepted (Slice 56)
- Context: spot and point lights (clustered since Slice 48) lit through walls. Scenes have many local lights, phones have little bandwidth, and SDL_GPU exposes no cube-array depth rendering or geometry shaders.
- Options:
  - Storage: (a) one 2D depth atlas with a fixed tile grid; (b) cube depth textures per point light plus 2D maps per spot; (c) dual-paraboloid maps for point lights.
  - Selection: (a) per-light opt-in plus a per-frame budget ranked by screen coverage; (b) every light.
- Decision: storage (a), selection (a).
  - `RenderSettings::local_shadow_atlas` / `local_shadow_tile` define a grid of at most 8x8 tiles (High 2048/512, Medium 1024/256, Ultra 4096/512, off on Low). Spot lights take one perspective tile (field of view twice the outer angle, up to 85 degrees). Point lights take six 90-degree tiles, picked in the shader by the major axis of the light-to-surface vector, so no cube textures are needed.
  - Lights opt in (`PointLight/SpotLight::cast_shadows`; scenes map `LightComponent::shadows`). Candidates in the view are ranked by range divided by the distance to their sphere, and tiles go out in that order; lights that do not fit stay unshadowed.
  - The world-to-tile matrices (atlas bias included) are appended to the clustered light buffer with the same 64-byte stride, so the PBR shader gains only one sampler (`u_local_shadow`) and no new buffer. Each light stores its first tile and its shadow texel angle; sampling uses a normal offset of about 1.5 texels at the surface's distance, the raster depth bias of the sun shadow pipeline, and the sun's 3x3 PCF setting, clamped inside the tile.
  - Casters are culled per tile on the CPU and batched like cascades; the shadow pipelines are shared with the sun.
- Consequences:
  - Every shadowed light is re-rendered every frame (no caching of static lights yet), and the atlas resolution is per tile, not per light.
  - Cube-face seams are possible at grazing angles because PCF clamps to each tile. Translucent and alpha-tested casters are not supported in local shadows yet (same as the sun pass).
  - Budget changes switch lights between shadowed and unshadowed without a fade.

### ADR-0053: Flipbook frames and stretched billboards for particles
- Status: Accepted (Slice 56)
- Context: games feed `submit_particles` from their own particle logic (AURORIA evaluates its stateless smoke, fire, spark, rain and snow formulas on the CPU). Smoke and flame textures are 4x4 flipbooks, and sparks and rain read as streaks along their motion; billboards could only show a whole texture as a rotated square.
- Options: (a) one texture per flipbook frame (a batch per frame); (b) per-material flipbook settings; (c) per-instance frame, grid and height/width in the reserved `ParticleInstance::params` fields.
- Decision: (c). `params.y` is the frame (left to right, top to bottom), `params.z` the grid (columns x 16 + rows; 0 = whole texture) and `params.w` the height/width ratio along the rotated up axis (0 or 1 = square). The particle vertex shader applies them; the instance layout (48 bytes) is unchanged.
- Consequences: one batch per effect regardless of frame; zeroed reserved fields keep existing emitters exactly as before. No frame blending (frames switch); grids up to 15 x 15.

### ADR-0054: Object motion vectors as a sparse pass after the forward pass
- Status: Accepted (Slice 57)
- Context: TAA reprojected history from scene depth with the camera matrices only, so moving and animated objects relied on neighbourhood clipping alone. Fine detail on them (stripes, text, foliage-like edges) smeared. Most scene pixels are static, mobile tiers do not run TAA, and every forward pipeline (PBR, surface shaders, blended variants) would need a second colour target for a full G-buffer-style velocity output.
- Options: (a) a second colour target on the forward pass for every draw; (b) a separate motion pass that redraws only the instances that moved, depth-tested against the finished scene depth; (c) per-pixel velocity reconstructed from depth plus an object-ID buffer.
- Decision: (b).
  - Draws carry an optional `motion_id` (`SceneRenderer::submit` / `submit_skinned`; scenes pass the entity id). The renderer keeps each id's previous model matrix and joint palette and, on TAA frames with a valid history, redraws visible opaque draws whose matrix or joints changed (bitwise compare). Previous joints are appended to the frame's joint palette, so skinned motion uses the same storage buffer.
  - `motion.vert` / `motion_skinned.vert` repeat the position math of the main pass (invariant `gl_Position`), test LessEqual against the scene depth without writing it, and `motion.frag` writes into an RG16F target the previous-camera texture-space position of the surface's current point minus that of its previous position. Untouched pixels stay 0.
  - `taa.frag` subtracts that offset from its camera reprojection, read at the same closest-depth texel of the 3x3 neighbourhood (so silhouettes are dilated with the foreground's motion).
  - The pass and its texture exist only on frames where something moved (`SceneStats::motion_draws`, `motion_batches`). `RenderSettings::motion_vectors` (default on) turns it off.
- Consequences:
  - Alpha-tested draws are skipped (the motion pass does not discard), so they keep camera-only reprojection. Blended draws and particles have no motion vectors.
  - Vertex animation in surface shaders is not seen (they only change fragments today). Ids must be unique per object; the first submission of an id in a frame wins.
  - Rejected (a): it doubles colour bandwidth for every opaque pixel on every frame. Rejected (c): it needs an extra ID target and per-object matrices in a buffer, for the same result.

### ADR-0055: Temporal upscaling inside the TAA resolve
- Status: Accepted (Slice 58)
- Context: dynamic resolution and `render_scale < 1` rendered the 3D scene at a lower size and the tonemap stretched it bilinearly, so lower scales cost detail roughly in proportion to the pixel count. TAA already jitters every frame and keeps a history; temporal upscalers (AMD FSR 2, MIT-licensed and documented at gpuopen.com; Unreal TSR documentation; Karis 2014 "High Quality Temporal Supersampling") use that jitter to reconstruct an output-resolution image.
- Options: (a) integrate FSR 2/3 source (MIT, large: ~10 compute passes, its own resource layout, HLSL/GLSL permutations to port to SDL_GPU MSL); (b) a spatial upscaler only (FSR 1 EASU/RCAS) after TAA; (c) a single-pass reconstruct-and-accumulate resolve owned by VICTUS, sharing taa.frag's reprojection and clipping.
- Decision: (c).
  - When TAA is on, `RenderSettings::temporal_upscale` (default on) and the render size is below the output in either axis, the resolve runs `taa_upscale.frag` at output resolution into an output-sized history. Each output pixel gathers the 3x3 render texels around it and weights them by a Gaussian fit of a Blackman-Harris window over their unjittered distance to the output pixel centre (the jitter offset is undone per sample). The reconstructed colour blends with the reprojected, Catmull-Rom sampled, YCoCg-clipped history; its weight scales with the nearest sample's kernel weight, so output pixels between this frame's samples lean on history.
  - The jitter cycle grows to `ceil(8 * ratio^2)` (FSR 2 recommendation), clamped to 8..64 (`temporal_jitter_period`).
  - Bloom, exposure and tonemap read the output-resolution image; the bloom chain still starts at render resolution (cost stays tied to render scale).
  - History stays at output size while dynamic resolution moves the render scale, so scale changes do not reset accumulation.
- Consequences:
  - Static and slowly moving content converges towards native-resolution edges (pixel-measured in `victus_gpu_tests`); fast disocclusions show the reconstructed render-resolution image until history builds again. No sharpening pass and no reactive/transparency mask yet: particles and blended draws can smear like in plain TAA.
  - Low and Medium tiers do not run TAA, so they keep bilinear scaling (mobile cost unchanged). Rejected (a): too large to own across three shader backends for the gain over (c) today; revisit with a measured quality gap. Rejected (b): spatial upscaling cannot recover sub-pixel detail.

### ADR-0056: Baked irradiance volumes (probe grid, SH9 per probe)
- Status: Accepted (Slice 59)
- Context: diffuse ambient light came only from the sky/environment SH, so interiors, areas under overhangs and surfaces next to bright or coloured geometry received the same ambient light as open ground. Roadmap item 13 asks for scalable GI, baked first. Reference designs: Unity Light Probe Groups / Adaptive Probe Volumes, Unreal Volumetric Lightmaps, Godot LightmapGI probes and DDGI (Majercik et al. 2019) for the dynamic follow-up.
- Options: (a) lightmaps (UV2 unwrapping, a path tracer, per-object atlases); (b) a regular grid of probes storing SH9 irradiance, interpolated per pixel; (c) jump straight to dynamic ray-traced probes (needs hardware RT or SDF tracing, not available on the SDL_GPU baseline).
- Decision: (b).
  - `render::IrradianceGrid` (world-aligned box, 2..32 probes per axis, 2..16 vertically) and `IrradianceVolume` store one `SphericalHarmonics9` per probe plus a validity flag, uploaded to an RGBA16F texture laid out (nx*ny) x (nz*9): rgb = coefficient * valid, a = valid.
  - `pbr.frag` binds it at fragment sampler 8 (SPIR-V storage buffers moved to 9/10). The world position is offset along the normal, eight probes are interpolated (two bilinear fetches per coefficient, mixed along y), coefficients are divided by the interpolated validity and the result blends with the environment irradiance by that validity, so unbaked probes and points outside the box fall back to the sky.
  - `IrradianceBaker` captures each probe with `capture_equirect` (the reflection-probe path) and projects it to SH9. It is progressive (`step` with a probe budget) and multi-pass: pass N renders the scene lit by pass N-1, adding one bounce per pass.
  - Runtime: `gameplay::IrradianceVolumeComponent` (size, spacing, intensity, normal offset, capture resolution, bounces, revision). `extract_scene` bakes stale volumes within `GpuAssetCache::set_irradiance_probes_per_frame` (default 8), keeps the previous bake lighting the scene while a rebake runs, and binds the volume containing the camera (smallest first), else the nearest. Moving or resizing rebakes.
  - `RenderSettings::irradiance_volumes` (off on Low: environment SH only).
- Consequences:
  - Coloured bounce light and darker interiors without UV2 or offline tools; editor scenes bake in the background in a few frames. Light changes need a rebake (revision), so dynamic sun/time of day are not tracked.
  - One volume per frame per renderer, no per-probe visibility/occlusion (DDGI depth moments) yet: thin walls can leak light, mitigated by the normal offset. The texture limits a volume to 32x16x32 probes.
  - Rejected (a): large tooling cost (unwrapping, path tracing) for static scenes only. Rejected (c) as the first step; a dynamic, incrementally updated probe option on High/Ultra remains the second half of item 13.

### ADR-0057: Dynamic GI by round-robin probe refresh with feedback
- Status: Accepted (Slice 60)
- Context: ADR-0056 volumes are baked once; a moving sun, time of day, lights switched on or emissive changes left stale indirect light until a manual rebake. Item 13 asks for a dynamic option on High/Ultra. DDGI (Majercik et al. 2019) and Unreal Lumen update probes incrementally with temporal hysteresis; both trace rays, which needs hardware RT or SDF tracing that the SDL_GPU baseline lacks.
- Options: (a) DDGI with compute ray tracing against a software BVH; (b) re-capture probes with the existing raster cube capture, a few per frame, with the volume applied to the capture (feedback) and blended into the stored SH; (c) full rebake on every change.
- Decision: (b).
  - `render::IrradianceRefresher` walks the probes round-robin within a per-step budget, renders each capture with the volume bound (volume intensity clamped to 1 during feedback so the loop cannot diverge with albedo < 1), and mixes the new SH9 into the stored one with weight `blend`. Each cycle adds one bounce; repeated cycles converge to multi-bounce light.
  - `IrradianceVolumeComponent::dynamic` / `dynamic_blend`. After a volume's bake finished, `extract_scene` spends the remaining per-frame probe budget on its refresh. `RenderSettings::dynamic_gi` gates it: on for High/Ultra, off for Low/Medium.
- Consequences:
  - Light changes propagate within about probe_count / budget frames (blend 1), smoother with lower blends. Cost is the per-frame probe budget (default 8 captures of six 16px faces) on the probe renderer.
  - Same limits as ADR-0056 (no visibility data, one volume per frame). Rejected (a) until a GPU BVH/SDF exists; rejected (c) as it stalls frames and drops the previous lighting.

### ADR-0058: Visual scripting graphs compile to Luau modules
- Status: Accepted (Slice 61)
- Context: roadmap item 14 asks for visual scripting over the Luau runtime with typed nodes, validation, debugging and deterministic serialization. Designers should not need a second VM, and graphs must keep every guarantee of scripts (sandbox, call budgets, heap limit, hot reload, per-entity properties, all scripting APIs). References: Unreal Blueprints (event graphs, exec vs pure nodes), Unity Visual Scripting (interpreted graphs; slower than C#), Godot VisualScript (removed in 4.0 for low adoption and maintenance cost), Defold/Roblox (text Luau only).
- Options: (a) interpret graphs at run time in C++; (b) compile graphs to Luau source and load them as ordinary script modules; (c) compile graphs straight to Luau bytecode.
- Decision: (b).
  - `.vgraph` is a JSON document ("format": "victus.graph", version 1): variables (name, type, default, exposed), nodes (id, type, position, literal inputs, config, comment) and links (from [node, pin], to [node, pin]). Serialization sorts nodes, links and literal keys, so files diff cleanly and repeated saves are byte-identical.
  - Pins are typed (exec, any, number, bool, string, vector, entity). A data input takes at most one link, an exec output feeds one node (Sequence fans out). Unlinked inputs use literals (an entity literal "self" is the scripted entity; another string finds an entity by name).
  - Node kinds: events (start, update, fixed_update, collision/trigger enter/exit) become module methods; statements expand a Luau template; pure nodes are inlined expressions; flow nodes (Branch, Sequence, For Range, Do Once) become structured control flow; variable get/set read and write `self` fields. Exposed variables are module fields (inspector-editable per entity like script fields); private ones are stored as `_v_<name>` and hidden.
  - Validation reports errors on the failing node and pin: unknown types/variables/pins, type mismatches, multiple links, duplicate events, exec loops, data loops, statement outputs used from another event, invalid or reserved variable names. Unreachable statements are warnings.
  - The compiler records the node of every generated line; runtime errors in a graph are reported as `... [node 12 Branch]`. An optional trace mode calls `__vg_trace(node)` before each statement for editor debugging.
  - `ScriptHost` loads `.vgraph` modules through the compiler (hot reload and budgets unchanged); `script::luau_source` lets `victus check` and `victus export` validate graphs; the asset database classifies `.vgraph` as a script.
- Consequences:
  - Graph scripts run at Luau speed with no second runtime, and generated code is readable for debugging. Graph changes reload like scripts.
  - Converging exec paths are emitted once per path (code duplication, capped at 200k lines). No functions/macros, custom events or per-node breakpoints yet; the editor graph panel and the debugger come in later slices.
  - Rejected (a): a second execution model to sandbox, budget and keep in sync with every API. Rejected (c): ties the format to Luau's bytecode version and loses readable output for little gain.

### ADR-0059: Graph Editor with its own snapshot undo, drawn with ImDrawList
- Status: Accepted (Slice 62)
- Context: Slice 61 graphs needed an editor. Graph files are assets like materials and prefabs, not scene data. Options for the canvas include the imnodes or imgui-node-editor libraries.
- Options: (a) third-party node-editor library; (b) a canvas drawn with ImGui's ImDrawList and our own hit testing; undo either through the scene UndoStack or a graph-local history.
- Decision: (b) with a graph-local history.
  - The canvas draws nodes, pins and bezier links itself (no new dependency, layout matches the `.vgraph` positions directly). Pin hit testing, node dragging, link dragging and panning are handled in `graph_panel.cpp`.
  - Undo stores serialized graph snapshots (up to 200), coalescing consecutive edits of the same literal, comment or variable. Scene undo is untouched; assigning a graph to an entity is the only scene edit and uses the scene stack.
  - All edits go through a public API that revalidates after each change, so tests and tools drive the editor without a window.

  - No zoom or minimap yet; nodes are fixed-width. Large graphs cost one serialization per edit (cheap at expected sizes).
  - Rejected (a): extra dependency with its own docking/state quirks for features we can add incrementally.

### ADR-0060: Graph debugging through per-graph trace recorders
- Status: Accepted (Slice 63)
- Context: designers need to see which nodes run and where a graph failed. Graphs are compiled Luau (ADR-0058); Luau offers debug hooks (line/call) and per-function instrumentation. Unreal Blueprints highlight executed wires and nodes during PIE; Unity Visual Scripting shows flow animation.
- Options: (a) Luau debug line hooks mapped through the compiler's line table; (b) compile-time trace calls (`__vg_trace(node)`) recorded by the host; (c) re-interpret graphs in a debug VM.
- Decision: (b). Traced builds start each module with `local __vg_trace = __vg_trace_for and __vg_trace_for("<path>") or function(_node) end`, so the recorder is bound once per module (no lookup per call) and untraced hosts or other runtimes stay valid. Events and statements are traced; pure nodes are inlined and not traced. The host counts runs per graph and node; the editor turns counts into fading highlights. Runtime errors keep the node from the existing `[node N Title]` annotation.
- Consequences:
  - Only editor play mode pays the cost (one C call per traced node); exported games compile without trace.
  - Breakpoints and stepping need pausing inside a Luau call (debug interrupt + resumable coroutine); left for script debugging (Phase 5 item). Rejected (a): hooks slow every script and the line table does not mark entry points cleanly; rejected (c): a second runtime.

### ADR-0061: Continuous frame profiler over the zone capture
- Status: Accepted (Slice 64)
- Context: the core profiler (ADR-era Slice 1) recorded zones only for one-off traces. Users need live frame-time percentiles and per-system/per-pass costs in the editor and a machine-readable report from `victus run`. SDL_GPU (ADR-0003) has no timestamp queries, so true per-pass GPU durations are not available on any backend.
- Options: (a) per-frame drain of the existing lock-free-per-thread zone capture, aggregated into rolling windows; (b) a separate counter API per subsystem; (c) Tracy/Optick integration.
- Decision: (a). `profiler::FrameProfiler` keeps a capture running, drains it at each frame boundary and aggregates per-name totals (nested same-name zones counted once per thread) into `SampleWindow`s, giving frame p50/p95/p99 and per-scope mean/p95/max/calls. Runtime names (systems, render passes) use `profiler::intern` for stable pointers. It can keep all zones of the next N frames for a Chrome/Perfetto trace. GPU cost is shown as CPU encode time per pass (`pass.<name>`) plus the time the CPU waits on the GPU (`gpu.acquire_swapchain`, `gpu.submit_and_wait`); memory comes from `rhi::DeviceStats` and the opt-in allocation tracker.
- Consequences:
  - One profiler per process; zone cost is two timestamps and a vector push, drained every frame, so it stays on in the editor.
  - No per-pass GPU durations until SDL_GPU exposes timestamp queries (or a native backend is added); the report names this explicitly. Rejected (b): duplicate instrumentation; rejected (c): external dependency and network listener for what the existing capture already provides.

### ADR-0062: Material graphs compile to surface-shader GLSL
- Status: Accepted (Slice 68)
- Context: surface shaders (ADR-0035) need GLSL. Artists expect node-based material editing, and VICTUS already has a typed node-graph document model, deterministic serialization and an editor canvas for visual scripts (ADR-0058/0059).
- Options: (a) reuse the visual-script graph model with a material domain and compile graphs to the surface function of the existing surface-shader path; (b) a separate material graph model and editor; (c) a new shader pipeline with its own uniforms, samplers and permutations per graph.
- Decision: (a). A `.vmatgraph` is a `victus.graph` document with `"domain": "material"` (`script::GraphDomain`), registered as `AssetKind::Shader`. Material nodes (`mat.*`: Surface Output, Material Surface, UV/positions/view/normals/vertex colour/time, Parameter 0-3, the four material texture slots, constants, generic math, vector, UV and effect nodes; 55 in total) are pure GLSL expression templates. Generic "any" pins take the widest connected type (float < vec2 < vec3 < vec4) and narrower values are splatted or padded, wider ones truncated. The compiler (`compile_material_graph`) emits one local per used node output in dependency order and assigns the Surface fields whose output inputs are linked or given a constant; unlinked fields keep the material's values. `runtime::load_surface_shader_code` turns a shader asset into GLSL (text for `.vshader`, compiled graph for `.vmatgraph`), so `GpuAssetCache`, hot reload, the built-in PBR fallback, `victus check` and export are shared with hand-written shaders. The Graph Editor switches its palette, pin colours, literal editors (colour pickers, vectors) and side panel by domain; saving compiles the GLSL and reports errors.
- Consequences:
  - A material graph has exactly the capabilities of a surface shader: no new uniforms or samplers, four vec4 parameters, the material's four textures. Graph errors name the file and node; GLSL errors name generated lines.
  - Script graphs keep their exact file format (no domain key); the script compiler refuses material graphs.
  - Rejected (b): duplicate model, serialization and canvas. Rejected (c): pipeline permutations and new resource bindings per graph; revisit when graphs need custom textures or vertex-stage nodes.

### ADR-0063: Chunked heightfield terrain with index-list LODs, skirts and vertex splat weights
- Status: Accepted (Slice 69)
- Context: roadmap item 18 needs large outdoor ground that scales to mobile: LOD, layered materials, collision and editing. The renderer already selects mesh LODs by screen-space error and culls per draw (frustum, GPU occlusion); surface shaders can read four material textures, four vec4 parameters and vertex colours; Jolt has a native height-field shape.
- Options: (a) CPU chunks as procedural meshes with LOD index lists and skirts, splat weights in vertex colours, a built-in surface shader; (b) GPU clipmaps / geometry from a height texture in the vertex shader (needs vertex texture fetch in mesh shaders, new pipelines and a terrain-specific pass); (c) CDLOD quadtree with morphing (needs per-draw morph uniforms and a custom vertex shader); (d) splat weights in a dedicated texture (needs a fifth sampler or a terrain-only material layout).
- Decision: (a). A `.vterrain` stores u16 heights and RGBA8 splat per sample (2^n+1 per side). Each 32x32-quad chunk is a `scene::ProceduralMesh` whose LODs are index lists over one vertex set (strides 2..32, same diagonal as the full grid); errors are max(geometric error, splat-weight deviation x half the coarse cell) and monotonic, so the existing `select_lod` and instancing/culling paths work unchanged. Skirts (depth max(1.25 x worst geometric error, 0.2% of height, 5 cm)) hide cracks without stitching. The built-in terrain surface shader decodes splat weights from vertex colours (undoing the vertex shader's sRGB decode) and blends layer textures carried in the four material texture slots with per-layer tint and tiling in the shader parameters. Collision uses Jolt `HeightFieldShape` (block size 2/4, ~1 mm quantization) via a runtime-only `physics::StaticHeightfieldComponent`, so physics stays independent of the terrain module. `Heightfield` revisions per chunk let several scenes share one field and rebuild only edited chunks.
- Consequences:
  - Painting resolution equals the sample spacing; no per-layer normal/roughness maps (roughness is per terrain); four layers maximum.
  - No geomorphing: LOD switches pop slightly, bounded by the pixel error threshold.
  - The collider is rebuilt whole on every edit (fine up to 1025^2; sculpt tools may need per-region updates later).
  - Revisit (b)/(c) when the renderer gains vertex texture fetch and per-draw custom vertex shaders, and (d) when materials gain more samplers.

### ADR-0064: Projected decals as a depth-reconstruction pass between opaque and blended geometry
- Status: Accepted (Slice 77)
- Context: roadmap item 21 needs decals (stains, cracks, bullet holes, markings) in the forward renderer, on every quality tier. There is no G-buffer: PBR inputs exist only inside the forward fragment shader. Scene depth is already sampled after the forward pass (soft particles, SSAO, TAA).
- Options: (a) draw each decal box after opaque geometry, reconstruct the surface position from depth and blend into the HDR colour; (b) clustered forward decals: bin decals into the light clusters and evaluate them inside pbr.frag before lighting (needs a decal atlas or bindless textures, another storage buffer and touches every surface shader); (c) mesh decals (clipped geometry generated on the CPU per decal); (d) a thin G-buffer (albedo/normal) for decal targets.
- Decision: (a). `render::Decal` is the unit box through a transform, projecting along local -Z; `SceneRenderer::add_decal` collects up to 1024 per frame (frustum culled, nearest kept, drawn by `sort_order` then far to near). When decals are present the forward pass splits into opaque (`forward`), `decals` (no depth attachment, front-face culled box so each pixel shades once also from inside, depth-reconstructed world position, derivatives taken before any discard) and `forward_blended` (blended geometry and debug lines) so glass and water are drawn over decals. Three blend modes: Multiply (dst x mix(1, colour, alpha); modulating lit colour equals modulating albedo for diffuse light), Alpha (unlit paint) and Additive (emissive). Angle fade uses the face normal from depth derivatives; depth fade softens the box ends. `gameplay::DecalComponent` ("Decal" schema) is extracted by the runtime; the editor creates one with Create > Decal.
- Consequences:
  - Decals cannot change normals, roughness or metalness, and Multiply also scales specular highlights; Alpha decals ignore lighting and shadows.
  - Decals project onto everything opaque inside the box, including moving objects (no receiver masks yet).
  - One draw call per decal; fine for hundreds, not for thousands.
  - Revisit (b) when the renderer gains bindless textures or an atlas, or if per-material decal masks are needed.

### ADR-0065: 2D lights through a screen-space light accumulation target

- Status: Accepted (Slice 78)
- Context: 2D scenes (sprites, tilemaps, 2D particles) had no lighting; roadmap item 21 asks for 2D lights. Normal-mapped or shadow-casting 2D lighting needs per-sprite normal maps and occluder geometry that the asset pipeline does not have yet.
- Decision: `SpriteBatch` gains an opt-in lighting mode. `set_lighting(ambient)` enables it; `render_lights()` (after `prepare()`, before the colour pass) renders an RGBA16F light target at the frame size, cleared to the ambient colour, with one additive quad per point/spot light (`light2d.vert/frag`: smooth window falloff `(1-(d/r)^2)^2` raised to a falloff exponent, spot cone between inner and outer half-angles, view-rectangle culling). Lit sprites use `sprite_lit.frag`, which multiplies the sprite colour by the light texel at `gl_FragCoord`. Sprites opt in with `Sprite::lit`; additive sprites stay emissive; editor overlays are unlit. `gameplay::Light2DComponent` (Point / Spot / Global, colour, intensity, radius, angles, falloff, enabled) is extracted by `extract_sprites`: Global lights sum into the ambient, any enabled 2D light turns lighting on (scenes without them render exactly as before), spot lights shine along local -Y and radius scales with the transform. `SpriteComponent::unlit` opts sprites out; tilemaps and non-additive 2D particles are lit.
- Consequences: one extra render-target pass per lit 2D frame and one extra texture bind per lit batch; light count is unbounded in practice (per-light quads, culled). No normal maps or 2D shadows yet; those can layer on the same light target later. HDR light values above 1 brighten lit sprites but the 2D target is still RGBA8, so they clip.

### ADR-0066: Spatial upscale and contrast-adaptive sharpening for scaled-down rendering

- Status: Accepted (2026-11-18)
- Context: phones render the 3D view at 0.6-0.7 render scale without TAA; the tonemap pass stretched the low-resolution frame with one bilinear fetch, which reads as a soft, smeared image on a 400+ dpi screen.
- Decision: `RenderSettings::spatial_upscale` (default off) and `RenderSettings::sharpen` (0..1, default 0). When the view is scaled down and no temporal upscaler runs, tonemap runs at render resolution into an RGBA8 sRGB texture; `upscale_sharpen.frag` resamples it to output size with a 9-tap Catmull-Rom filter clamped to the 2x2 source texels (no ringing) and applies RCAS-style sharpening limited by the local min/max (no halos). Filtering happens in linear light (sRGB texture). FXAA, if enabled, runs after it at output resolution. `sharpen` alone at full resolution runs the same pass without resampling. `SceneStats::spatial_upscale` / `sharpened` report the path.
- Evidence: `gpu quality: spatial upscale resamples sharper than bilinear without halos` (lavapipe): texture detail energy 697k vs 660k for bilinear (full resolution 894k), brightest edge pixel 561 vs face 564 (no overshoot), mean brightness preserved.
- Consequences: one extra full-screen pass (13-17 bilinear fetches) at output resolution; tonemap becomes cheaper (render resolution). Not measured on a real Mali/Adreno device yet.

### ADR-0067: Alpha-tested shadow casters and a four-tap soft-shadow mode

- Status: Accepted (2026-11-18)
- Context: the shadow pass ignored `alpha_cutoff`, so foliage cards cast solid rectangles; phones could only choose hard 1-tap or 9-tap PCF.
- Decision: casters with `alpha_cutoff > 0` and a base colour texture draw with `shadow_alpha.vert/frag` (discard below cutoff); casters are sorted opaque first, then by texture, and only batch with matching alpha-test state. `RenderSettings::fast_soft_shadows` selects a 4-tap tent PCF (half-texel offsets) between hard and the 9-tap soft path.
- Evidence: `gpu quality: alpha-tested casters cut holes into their shadow` (8 lit / 8 shaded checker cells under a cut-out caster), `fast soft shadows widen the penumbra with four taps` (penumbra 85 hard / 101 fast / 105 soft pixels).
- Consequences: one extra pipeline and texture bind per alpha-tested caster group in the shadow pass.

### ADR-0068: Animation controllers as `.vanim` JSON state machines with phase-synced blend spaces

- Status: Accepted (2026-11-18)
- Context: Animators played one clip at a time, chosen by scripts (`play_animation("Walk")`); characters need parameter-driven state machines, 1D/2D blend spaces and interruptible cross-fades authored as assets, as in Unity Animator Controllers, Godot AnimationTree and Unreal Animation Blueprints.
- Decision: a JSON `.vanim` asset (AssetKind::AnimController) with typed parameters (float, int, bool, trigger), states that play a clip or a 1D/2D blend space, and ordered transitions (any-state first) with all-of conditions, a cross-fade duration in seconds, optional exit time and start offset. `AnimatorComponent::controller` names the asset; clips resolve by name against the Animator's model at run time. 1D weights are piecewise linear; 2D weights use Cartesian gradient bands (Johansen 2009, Unity "Freeform Cartesian") — chosen over Godot's triangulated blending because it needs no triangulation step, is exact at every point and stays defined outside the hull. Blend spaces are phase-synced (shared normalized time, weighted-sum cycle length). Transitions may interrupt a running fade; the last output pose is frozen as the fade source. Looping states check exit times below 1 every cycle on the crossing frame (Unity semantics); otherwise an exit time stays satisfied once reached. Parameters are runtime state, not serialized. A controller that fails to load falls back to plain clip playback; missing clips contribute the rest pose; both log once.
- Evidence: `victus_animation_tests` controller cases (parsing and validation errors, 1D/2D weight properties, phase-synced durations, triggers, exit time, any-state, mid-fade freeze, reload keeps parameters, load-error fallback), `fuzz: animation controllers` (mutated documents never crash; accepted ones round-trip).
- Addendum (2026-11-18, root motion): states opt in with `"root_motion": true`; the controller's `root_node` (default: the model's first root node) supplies the motion. The node's horizontal (XZ) travel and yaw since the previous update leave the pose (pinned to their clip-start values) and move the Animator's entity in its parent space, scaled and rotated by the entity's transform; vertical motion stays in the pose (Unity's default "bake Y"). Travel is measured on the unwrapped cycle so loops do not pop; blend weights and cross-fades weight it. `AnimatorComponent::apply_root_motion = false` only reports it (`AnimationSystem::root_motion`, Luau `entity:root_motion()` in world space) so a script can feed a CharacterController, as in Godot's root-motion API. Evidence: controller_tests root-motion cases (loop wrap, blend, in-place states, rotated/scaled entities, report-only mode, turning one-shot) and "script: root motion API reports world-space travel".
- Consequences: one layer per Animator (no layered/additive blending or avatar masks yet), no sub-state machines, no per-transition interruption settings beyond "the destination state's transitions may interrupt"; root motion and blend-space sync markers are future work. Duration in seconds only (Unity's normalized "Fixed Duration off" mode is not offered).

### ADR-0069: Starter characters as authored GLBs embedded in the engine, generated by a bpy script

- Status: Accepted (2026-11-18)
- Context: the 3D templates used a procedural robot built in C++ (`engine/project/src/robot.cpp`, 11 joints, two meshes). The starter-character brief (docs/handoff/VICTUS_STARTER_CHARACTERS.md) asks for two original, recognisable 20k-35k triangle hard-surface robots sharing one rig and seven clips, with editable Blender source, going through the normal import pipeline. Alternatives: (a) keep growing the procedural C++ generator; (b) author GLBs and ship them in a data install directory next to the binaries; (c) author GLBs and embed them in the engine binary, written into projects by the template.
- Decision: (c). `tools/characters/build_vanguard.py` builds the rig, both meshes, materials, sockets and clips with Blender's `bpy` module (5.0.1) and exports self-contained GLBs (deform bones only, actions as NLA strips, active vertex colour) plus the `.blend`. `cmake/EmbedBinary.cmake` turns the committed GLBs into byte arrays; `project::starter_characters()` exposes them and the templates write them with fixed `.meta` UUIDs into `assets/models/characters/`. Projects import them through the asset database like any model; `assets::import_gltf_memory` imports the embedded bytes directly when a scene is built before the project exists (instantiation moved to `assets/instantiate.hpp` so the project module can use it). (a) was rejected because hard-surface detail (bevels, weighted normals, curved shells) is far easier to review and edit in Blender and the brief requires editable source; (b) was rejected because `victus new` must work from a single binary and installers/tests would need a located data root. Embedding adds about 3 MB to binaries that create projects.
- Licensing: Blender's licence says output is the user's sole property and published `bpy` scripts must be GPL-compatible (https://www.blender.org/about/license/); the generator is Apache-2.0, which the FSF lists as GPLv3-compatible (https://www.gnu.org/licenses/license-list.html). Blender is a build tool only and is not distributed. The GLBs are original VICTUS assets under the repository licence.
- Evidence: `victus_asset_tests` starter-character cases (zero importer warnings, shared 21-joint skeleton and bind pose, clip lengths, sockets, budget, template hierarchy, controller state flow, V-02/none options, in-memory import rejecting external references), `victus_project_tests` 3D template case (jump, fall, land), `victus_cli_smoke`.
- Consequences: rigid skinning (one joint per vertex) suits the armour but would need weight painting for soft shells; the exporter is not bit-reproducible, so the reviewed GLBs are committed rather than regenerated in CI; regenerating needs a Python 3.11 `bpy` wheel. The old `robot.cpp` generator is removed; the arena sample keeps its own `robot.gltf`.

### ADR-0070: Coverage-preserving alpha mips for alpha-tested textures

- Status: Accepted (2026-11-18)
- Context: Camera-responsive fidelity (roadmap 6b, Workstream H3 item 8) asks that alpha-cutout surfaces stay readable during zoom. `render::build_mip_chain` box-filters alpha, so sparse cutout textures (leaves, chain-link fences) average below the material's cutoff in coarser levels. The GPU test (`gpu_alpha_coverage_tests.cpp`) measured on-screen coverage of a 30% speckle texture dropping from 0.28 at a close-up to 0.002 at 15 m and 0 at 40 m. Alternatives: (a) Castaño's coverage-preserving mips: per level, bisect for the alpha reference that gives the base level's alpha-test coverage, then scale alpha by cutoff / reference (offline, no runtime cost; Unity's "Mip Maps Preserve Coverage", NVTT); (b) scale alpha in the shader by the sampled LOD (Golus; a fixed formula, needs `textureQueryLod` or derivatives in every alpha-tested shader including shadows); (c) hashed alpha testing (Wyman and McGuire 2017; fixes sub-texel erosion too but is noisy without TAA); (d) alpha-to-coverage (needs MSAA, which the renderer does not use).
- Decision: (a) in `render::preserve_alpha_coverage(chain, cutoff)`, applied at cook time. Coverage is matched to the full-resolution source, so levels dropped by `max_size` do not drift. `TextureImportSettings::alpha_coverage_cutoff` (0 = off, stored only when set) enables it for textures, with a "Preserve alpha coverage" toggle and cutoff slider in the editor's Texture Import Settings. The glTF importer applies it to the base colour texture of `MASK` materials at their `alphaCutoff`, and caches textures per (image, sRGB, cutoff). Importer versions bump to texture v4 and model v6, so existing assets re-import.
- Evidence: `victus_render_tests` "coverage-preserving alpha mips..." (coverage within 0.1 of the source on every level with at least 16 texels, colour untouched, no-ops for cutoff 0/1 and single levels); `victus_asset_tests` "alpha-tested textures get coverage-preserving mips" (settings JSON, `max_size` drop, MASK vs OPAQUE glTF); `victus_gpu_tests` "gpu alpha coverage..." (on-screen coverage at 0.5/6/15/40 m: 0.28/0.11/0.15/0.18 preserved against 0.28/0.11/0.002/0 plain).
- Consequences: one-texel features still erode under bilinear alpha testing at mid distances (6 m in the test: both chains render 0.11), which only (c) or (d) addresses. Hashed alpha is the next step if foliage needs it, after TAA becomes standard on all tiers. Coverage, not shape, is preserved, so a thin silhouette can thicken slightly as holes fill. Blended (`blend: alpha`) materials are not affected.

### ADR-0071: Overdraw debug view as a depth-complexity count

- Status: Accepted (2026-11-18)
- Context: Camera-responsive fidelity (roadmap 6b, Workstream H2) asks for measured overdraw, separate from the triangle and shading-cost counters in `SceneStats` (commit 1483e14). Foliage, fences and blended layers cost fill rate that triangle counts do not show. Alternatives: (a) depth complexity: redraw the visible batches without depth testing into an additive 8-bit counter, show it as a heat ramp and read it back (Godot's `DEBUG_DRAW_OVERDRAW` draws meshes additively in the same spirit; Unreal's Quad Overdraw colours blue to red to white); (b) Unreal-style quad overdraw: count 2x2 helper-lane quads with atomics on a storage image, which needs fragment-stage storage writes the RHI does not expose on every backend and a second resolve; (c) GPU pipeline statistics queries (fragment invocations), which SDL_GPU does not expose and which give one number, not a per-pixel picture.
- Decision: (a). `RenderSettings::debug_view = DebugView::Overdraw` replaces the final image: the opaque, alpha-tested and blended batches selected for the main view (after frustum culling and LOD selection, before occlusion culling) are drawn with the pre-pass vertex path (plain or skinned, culled or double-sided) and `overdraw.frag`, which adds 1/255 per fragment into a persistent RGBA8 counter at render resolution. `overdraw_heat.frag` maps 0/1/2/3/4/5-7/8+ to black/blue/green/yellow/orange/red/white. `SceneRenderer::read_overdraw()` returns covered pixels, total layers, the maximum and the mean per covered pixel. The lit passes have no consumer that frame and are culled by the render graph; TAA history and eye adaptation restart when the view returns. The editor toggles it from View > Overdraw View and the command palette; it is never saved to the project.
- Evidence: `victus_gpu_tests` "gpu overdraw..." (three stacked opaque planes give a maximum of 3 and a yellow centre with black empty space; opaque + alpha-tested + blended stacks count 3; a back-facing plane counts only when double-sided; turning the view off restores the lit image and empties the readback; out-of-range values sanitise to None); `victus_editor_tests` "editor: overdraw view..." (toggle, readback from the 3D template, survives quality changes, not persisted).
- Consequences: it measures rasterised layers, not shaded fragments: the depth pre-pass and early-z reject most hidden opaque layers in the real image, so the view shows where geometry stacks, not exact pixel-shader cost. Alpha-tested holes are counted as covered (the counter does not sample textures), particles, decals, terrain-only paths and lines are not counted, and counts saturate at 255. Quad overdraw and per-pixel shader cost remain open (they need storage writes from fragment shaders).

### ADR-0072: In-process crash reports and local diagnostics bundles

- Status: Accepted (2026-11-18)
- Context: Workstream D (docs/handoff/COMPETITIVE_MATURITY_GAP_CLOSURE.md) asks for crash reports, symbol handling, diagnostics bundles and explicit privacy controls; the competitor benchmark (docs/audits/COMPETITOR_BENCHMARK.md) puts it first among unblocked gaps. Before this, `install_crash_handlers` only printed a line on a fatal signal. Alternatives: (a) Crashpad or Breakpad: out-of-process handler and minidumps, the most robust capture (the handler survives a corrupted process) but a large dependency with its own build, a separate handler executable to ship per platform and minidump tooling to read results; (b) Sentry Native or a similar SDK: Crashpad plus an upload service, which means sending users' data to a third party by default; (c) an in-process handler that writes a plain-text report with module+offset frames and the last log lines, like Godot's backtrace-on-crash and Unity's local crash folder, plus a separate offline symbolizer.
- Decision: (c). `crash::Session` (victus/core/crash.hpp) installs SIGSEGV/SIGABRT/SIGFPE/SIGILL/SIGBUS handlers on an alternate stack (Windows: an unhandled-exception filter and CRT signals), a `std::terminate` handler, a 64-line breadcrumb log sink and a per-session log file flushed per line; reports are formatted into static buffers and written with `open`/`write` in the handler, frames carry module path + offset and, on Linux, the module's GNU build-id. A `sessions/<app>-<pid>.running` marker left by a dead process tells the next start the previous session ended unexpectedly. `player::create_diagnostics_bundle` (victus/player/diagnostics.hpp) zips crash reports, recent logs, system facts, `victus.project` and `victus check` results with a README and manifest, replacing the home folder, user name and project path by default; `victus diagnose` exposes it and the editor can call the same function. `tools/crash/symbolize.py` resolves frames offline with llvm-symbolizer/addr2line and refuses symbol files whose build-id differs. ZIP output is a small stored-only writer (victus/core/zip.hpp) rather than a new compression dependency. Nothing is ever uploaded.
- Evidence: `victus_core_tests` "crash: ..." (report format, listing, stale markers, pruning) and "zip: ..." (CRC-32 check value, round trip, unsafe names, corruption); `victus_export_tests` "diagnostics: ..." (contents, limits, redaction, opt-outs, unopenable project); `victus_cli_diagnostics` (real SIGSEGV, uncaught exception and failed `VICTUS_VERIFY` in child processes each leave a report with frames; `victus diagnose` bundles them and the zip extracts with `cmake -E tar`). Symbolizer checked by hand against a `-g` test program, a split `.debug` file and a deliberately mismatched one (docs/STATUS.md).
- Consequences: an in-process handler is best effort: heap corruption or a smashed stack can stop it from writing; there are no minidumps (no register or memory state), no symbols uploaded or served, and no automatic upload or crash aggregation. Windows and macOS handlers compile in CI but have not been run against a real crash locally; Android reports have no frames. A future out-of-process handler (Crashpad) can write next to these reports without changing the bundle format.

### ADR-0073: Inverse kinematics as post-animation constraint components

- Status: Accepted (2026-11-18)
- Context: the competitor benchmark lists "no IK" as an animation gap; Godot 4.6+ ships TwoBoneIK3D, FABRIK3D, CCDIK3D and LookAtModifier3D as SkeletonModifier3D nodes, Unity has Animation Rigging constraints, Unreal has Two Bone IK/FABRIK/CCDIK nodes. Alternatives: (a) CCD only: simple but curls chains unnaturally; (b) Jacobian / damped least squares: general, joint-limit friendly, but heavier and needs tuning; (c) analytic two-bone (law of cosines, pole/bend hint) for limbs plus FABRIK (Aristidou & Lasenby, Graphical Models 73(5), 2011) for longer chains plus an aim constraint.
- Decision: (c). `IKConstraint` (victus/animation/ik.hpp) is a reflected component on the chain's end entity with `solver` (two_bone, chain, look_at), `weight`, a target entity or `target_position`, an optional pole entity, `match_rotation`, `chain_length`, `iterations`, `tolerance`, `max_extension` and look-at `aim_axis`/`max_angle`. `apply_ik` runs inside `AnimationSystem::update` after clips and controllers are sampled, parents' chains first by hierarchy depth, writes only local rotations, and blends with the animated pose by nlerp. An internal `IkRuntime` component caches the input pose so procedural (unanimated) rigs with weight < 1 do not drift. Luau gets `entity:set_ik_target` and `entity:ik_state`.
- Evidence: `victus_animation_tests` "ik: ..." (9 cases, 75 assertions: reach, unreachable clamping, pole plane, FABRIK convergence and bone lengths, look-at cone, weights, ordering, no drift), `victus_script_tests` "script: IK targets from Luau".
- Consequences: no joint limits on Chain, no pole for Chain, non-uniform parent scale approximated, a disabled constraint on an unanimated rig leaves the last IK pose, no editor gizmo. Full-body IK and physics-based characters remain future work.

### ADR-0074: Controller layers with bone masks and additive blending

- Status: Accepted (2026-11-18)
- Context: one state machine per character cannot shoot while running or add breathing on top of locomotion; the benchmark lists "no additive layers or masks". Unity Animator layers (override/additive, Avatar masks, layer weights, additive = offset from the clip's first frame), Unreal Layered blend per bone and Godot AnimationTree blend/add nodes with filters cover this. Alternatives: (a) a general blend graph (Unreal AnimGraph, Godot AnimationNodeBlendTree): most flexible, much more authoring surface; (b) Unity-style layers in the existing `.vanim` file: each layer a state machine over the shared parameters, with a node-name mask, a weight and a blend mode.
- Decision: (b). `.vanim` gains `"layers"`: `name`, `weight`, `weight_parameter`, `blend` (`override` | `additive`), `reference` (`first_frame` | `rest`, additive only), `mask`/`exclude` (node names, subtrees included; the nearest listed ancestor decides) and its own `default_state`/`states`/`transitions` (parsed by the same code; errors are prefixed `layers[i].`). Layer states may be empty (no clip: no influence). Layers apply in order after the base layer and before IK. Override layers sample over the current base pose, so nodes their clips do not animate and empty states keep the base, and cross-fades inside a layer blend from the base. Additive layers sample a delta (translation difference, local rotation `ref⁻¹·pose`, scale ratio) against each state's normalized-time-0 pose or the rest pose; deltas are cross-faded in delta space and applied scaled by weight × mask. Triggers consumed by a layer transition are consumed for every layer. Runtime weights (`set_layer_weight`) survive hot reloads by layer name. Root motion stays on the base layer.
- Evidence: `victus_animation_tests` "layers: ..." (6 cases: parsing and nested errors, override by weight/parameter/runtime weight, mask/exclude/unknown nodes, empty states and in-layer fades, additive translation and rotation against first frame and rest, hot reload), `victus_script_tests` layer weights case.
- Consequences: no per-bone mask weights (masks are 0/1), no layer sync (timing shared with another layer), no layer IK pass flags, no blend graph. The editor Animation window does not show layers yet (Studio session).

### ADR-0075: Retarget clips between rigs by bone name

- Status: Accepted (2026-11-18)
- Context: clips bought or captured for one character (Mixamo, a store pack) cannot drive another rig; the benchmark lists "no retargeting". Unity retargets only Humanoid models through a configured Avatar (https://docs.unity3d.com/6/Documentation/Manual/Retargeting.html); Unreal's IK Retargeter maps bone chains between two IK Rigs, with optional IK for hand and foot contact (https://dev.epicgames.com/documentation/en-us/unreal-engine/ik-rig-animation-retargeting-in-unreal-engine?application_version=5.2); Godot maps each skeleton onto SkeletonProfileHumanoid with a BoneMap on import, can normalize position tracks by the Hips height and overwrite bone rests (https://docs.godotengine.org/en/stable/tutorials/assets_pipeline/retargeting_3d_skeletons.html). Alternatives: (a) a humanoid profile with muscle space (Unity) — needs an avatar authoring UI and only covers humanoids; (b) chain mapping with IK (Unreal) — needs IK rig assets; (c) per-bone mapping by name, baking each mapped bone's world-space rotation change relative to its rest pose, root translation scaled by the root's rest height.
- Decision: (c). `AnimatorComponent::clip_source` names another model whose clips are retargeted onto this Animator's model and merged with its own clips (same name: the model's own clip wins). `map_bones` matches target to source bones by an explicit `bone_map`, then by exact name, then by normalized name (namespace before the last `:`/`|` stripped, lowercased, `_ . - space` removed, so `mixamorig:Left_Arm` matches `LeftArm`); each source bone drives at most one target bone, explicit mappings first. `retarget_clip` samples the source at the union of its key times (resampled uniformly at `max_sample_rate`, 60 Hz, when denser) and, per mapped bone, sets the target's world rotation to `(Ws·Ws0⁻¹)·Wt0` (source world rotation change since rest, applied to the target's rest world rotation), converted back to local through the target's own (possibly unmapped) parents. Only the root (the first mapped bone whose source animates translation) gets translation: the source travel in world space, scaled by the ratio of the rest-position lengths, rotated into the target parent's space. Other bones keep the target's rest lengths; unmapped bones keep their rest. Retargeted sets are cached per (model, source) and rebuilt when either model reloads.
- Evidence: `victus_animation_tests` "retarget: ..." (5 cases: name normalization and mapping priority, identical rigs reproduce the pose, world rotation change preserved across a different rest orientation and a Z-up unmapped armature with proportions kept, root travel scaled ×2, resampling cap, merge/skip report, Animator `clip_source` end to end); `victus check` warns when no bone of `clip_source` matches and checks controller clips against the merged set; export fails on a missing `clip_source` model.
- Consequences: no humanoid profile or automatic T/A-pose matching (the rest poses should be similar), no IK pass for foot or hand contact (use IKConstraint), no per-bone offsets or translation retargeting below the root, no editor bone-map UI (the `bone_map` option is C++ only for now). Baked at first use, so the first frame that plays a large source set pays the cost.

### ADR-0076: glTF morph targets, CPU-morphed per entity, weights as pose nodes

- Status: Accepted (2026-11-18)
- Context: facial expressions, lip sync and corrective shapes need morph targets (blend shapes); the benchmark lists "no morph targets" and the importer dropped them with a warning. glTF 2.0 defines targets as per-primitive attribute deltas, default weights in `mesh.weights` that `node.weights` overrides, names by the `mesh.extras.targetNames` convention, and `weights` animation channels (https://registry.khronos.org/glTF/specs/2.0/glTF-2.0.html). Unity exposes them as blend shapes on SkinnedMeshRenderer with `SetBlendShapeWeight(index, value)` (https://docs.unity3d.com/6/Documentation/ScriptReference/SkinnedMeshRenderer.SetBlendShapeWeight.html); Godot as blend shapes on MeshInstance3D, set by index with lookup by name (https://docs.godotengine.org/en/4.1/classes/class_meshinstance3d.html). Alternatives for evaluation: (a) GPU morphing from target buffers in the vertex shader or a compute pre-pass — no CPU cost, but needs storage buffers or a compute stage in every backend, new pipeline variants and per-draw weight uniforms; (b) CPU morphing of sparse deltas into a per-entity vertex buffer that the existing (skinned or static) pipelines draw unchanged. Alternatives for animation: (c) a separate weight track evaluator beside the pose; (d) weights as pseudo nodes of the pose.
- Decision: (b) and (d). Targets are stored sparsely (only moved vertices) with position and optional normal deltas; `apply_morphs` sums weighted deltas and renormalizes normals (tangents re-orthogonalized). The GPU cache keeps one morphed vertex copy per drawing entity sharing the base mesh's index, LOD and skin buffers, re-uploaded with a discard upload only when the weights change, released when weights return to zero, when unused for a few frames, and on model eviction; all-zero weights draw the base mesh. `expand_morph_weights` turns `weights` channels into translation channels of one weight node per target (`<node>/<target>`, child of the mesh node, rest = node or mesh default weight), so cross-fades, blend spaces, override/additive layers and node masks blend morph weights with no extra code; the Animator writes animated weight nodes into a runtime-only `MorphWeightsComponent` on the node entity. Weights resolve from the drawing entity, then its parent (multi-primitive nodes), then static `node.weights`, then `mesh.weights`; scripts write the same component.
- Evidence: `victus_animation_tests` morph cases (expansion incl. cubic-spline layout, validation and dropped channels, Animator writes/cross-fades, name/index API), `victus_asset_tests` morph cases (cooked v7 round trip and corruption, glTF export -> import with optimisation and node weights, morph math), `victus_script_tests` morph case, `victus_gpu_tests` morph case on lavapipe.
- Consequences: CPU cost proportional to moved vertices times active targets per changed frame, plus one vertex upload per changed mesh — fine for a few hero faces, not for crowds (GPU morphing is the upgrade path behind the same data). No tangent deltas (tangents are re-orthogonalized instead), no per-vertex motion vectors for the deformation (TAA may smear fast morphs), skinned bounds ignore morph offsets, weights set from scripts are not saved with the scene, and retargeting skips weight nodes.
### ADR-0077: LOD hysteresis keyed by motion id, bounded by the pixel budget

- Status: Accepted (2026-11-18)
- Context: ADR-0049 selection is stateless, so an object resting on a threshold (idle character, swaying camera, slow dolly) switches levels every frame; the camera-responsive LOD audit (finding 3) and A.E.G.I.S. Slice 2 ask for a measured way to stop that. Unity LOD Group cross-fades or switches at fixed screen-relative heights with an optional fade band (https://docs.unity3d.com/Manual/class-LODGroup.html); Unreal static mesh LODs switch on screen size and dither between levels (https://dev.epicgames.com/documentation/en-us/unreal-engine/static-mesh-automatic-lod-generation-in-unreal-engine); Godot 4 uses a `lod_threshold` in pixels with no transition (https://docs.godotengine.org/en/stable/tutorials/3d/mesh_lod.html). Alternatives: (a) dithered cross-fade: hides pops but draws two levels during the fade and needs a dither path in every opaque, alpha-tested and shadow pipeline; (b) a symmetric hysteresis band around the threshold: cheap, but lets the drawn level exceed the pixel budget by the band; (c) a one-sided band: keep the previous level while it lies between the stateless pick and the pick for a budget shrunk by a fraction.
- Decision: (c). `RenderSettings::lod_hysteresis` (default 0.25, 0..0.9, 0 = stateless). For a draw submitted with a motion id, the renderer keeps last frame's level clamped to [pick(budget × (1 − h)), pick(budget)]: refining happens as soon as the stateless rule asks for it, coarsening only once the error is h below the budget, so the projected error never exceeds `lod_error_pixels`. History is keyed by (motion id, mesh), kept per renderer for the last output size, dropped by `reset_history()`, not recorded by frames with LODs off or forced, and not used for draws without a motion id (instanced foliage). Main views of a different size (a scope, a thumbnail) therefore stay stateless and independent. `SceneStats::lod_held` counts draws kept finer than the stateless pick. Shadow levels follow (lod + `shadow_lod_bias`).
- Evidence: `victus_gpu_tests` "gpu lods: hysteresis keeps a level at a threshold without exceeding the budget": a sphere breathing ±1% around its LOD 0/1 threshold switches 15 times in 16 frames stateless and at most once with hysteresis, never coarser than the stateless pick; receding 5% past the threshold holds LOD 0 (`lod_held` 1), 2x coarsens, approaching refines at once; `reset_history()`, a different output size and untracked draws fall back to the stateless rule. The existing FOV, render-scale, rapid-zoom, secondary-view and terrain seam cases are unchanged.
- Consequences: pops are rarer, not hidden: there is still no cross-fade or geomorph (alternative (a) stays open for A.E.G.I.S.). Two same-size views alternating on one renderer share history (still within budget); call `reset_history()` between them or use separate renderers. Draws without a motion id (instanced foliage, editor previews) stay stateless.

### ADR-0078: native plugin SDK as a versioned C ABI with JSON manifests

- Status: Accepted (2026-11-18)
- Context: the competitor benchmark lists "no plugin SDK" as the extensibility gap; ARCHITECTURE.md asks for versioned plugin APIs, module lifetime, ABI compatibility and failure isolation before promising binary compatibility. Godot's GDExtension describes each extension with a `.gdextension` file naming the `entry_symbol`, `compatibility_minimum`/`compatibility_maximum` and one library per platform/feature tag (https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/gdextension_file.html); the C example shows the engine passing a `get_proc_address` function at initialization through which the extension requests API functions by name (https://docs.godotengine.org/en/stable/engine_details/engine_api/gdextension/gdextension_c_example.html). Unreal describes plugins with a JSON `.uplugin` descriptor listing modules and their loading phase (https://dev.epicgames.com/documentation/en-us/unreal-engine/plugins-in-unreal-engine). Alternatives: (a) a C++ class interface exported from the plugin — natural for C++, but ties plugins to one compiler, standard library and engine header set; (b) a C ABI with versioned, append-only interface structs looked up by name; (c) only scripting-level extension (Luau modules, bridges), which exists already but cannot run native code.
- Decision: (b). `victus_plugin.h` is a self-contained C header (no engine code to link). A plugin library exports `victus_plugin_entry(host, out)`; the host passes `get_interface(name)`, and each interface name (`victus.log.1`, `victus.systems.1`, `victus.scene.1`, `victus.functions.1`) identifies a frozen struct beginning with `struct_size`; changes ship as a new name. `VICTUS_PLUGIN_API_MAJOR.MINOR` versions the set: same major and plugin minor <= host minor, checked both from the manifest (before loading) and from the descriptor the library returns (after loading). A JSON `<name>.vplugin` manifest in `plugins/<name>/` gives name, semver version, required API, entry symbol, one library per platform (sandboxed relative paths), dependencies with minimum versions, targets (player/editor) and enabled. `plugin::PluginManager` discovers manifests, resolves dependencies topologically (cycles, missing or old dependencies, duplicates and incompatible APIs rejected, transitively), loads libraries with `dlopen(RTLD_LOCAL)`/`LoadLibraryW`, calls `init` in order, isolates each failure (its registrations dropped, dependents skipped), adds registered systems to the `Simulation` as `plugin.<plugin>.<name>`, and shuts down in reverse order, disabling the systems before unloading code. Plugin functions exchange JSON text and are reachable from Luau through `plugins.call`/`plugins.has`, wired by the player and CLI through `HostOptions::plugin_call` so `engine/script` does not depend on `engine/plugin`. `victus plugins` lists, loads and scaffolds plugins (embedding the SDK header in the scaffold); `victus check` validates them; `victus export` ships the host-platform libraries as loose files next to `game.vpak`.
- Evidence: `victus_plugin_tests` (6 cases, 102 assertions; four test libraries built from one C source: lifecycle with two copies of the same library, systems moving entities, functions incl. plugin-to-plugin calls, refused late registration, reverse-order shutdown with inert systems afterwards, failures for init error, newer built-against API, missing entry, manifest API, missing library, editor-only and disabled plugins, broken manifest), `victus_script_tests` `plugins.call` case, `victus_cli_plugins` (scaffold, real CMake build of the template, list/check/load, Luau call in `victus simulate`, missing-dependency error, export layout and `export.json`).
- Consequences: plugins are trusted native code without a sandbox, so they suit studios and tool authors, not untrusted mods (Luau remains the safe extension path). API 1.0 covers logging, systems, transforms/entities and functions; components, rendering, assets and physics need new interfaces. No hot reload, no editor loading or plugin UI yet, export copies host-platform libraries only and does not sign them, Android packaging is untested.

### ADR-0079: convex-hull and triangle-mesh colliders from model, primitive or procedural geometry

- Status: Accepted (2026-11-18)
- Context: `Collider` only had box/sphere/capsule/cylinder, so imported levels, rocks and props needed hand-placed primitives. Jolt provides `ConvexHullShape` (hull of a point set, at most 256 hull points) and `MeshShape` (triangles); its architecture notes say mesh shapes are "mostly used for static geometry", "cannot calculate their mass and inertia" and do not collide with other mesh or height-field shapes, and that `ScaledShape` scales any shape (https://jrouwe.github.io/JoltPhysics/index.html). Unity uses the same split: concave mesh colliders are static or kinematic only and collide only with convex colliders; "Is Convex" builds a hull for dynamic bodies (https://docs.unity3d.com/Manual/mesh-colliders-introduction.html). Alternatives for the geometry source: (a) a separate collision-mesh asset kind with its own importer; (b) reuse what the entity already renders (cooked model mesh, MeshRenderer primitive, `ProceduralMesh`), with an optional override naming a model mesh; (c) automatic convex decomposition (V-HACD/CoACD) at import.
- Decision: (b). `Collider.shape` gains `convex` and `mesh`, plus `mesh_asset`/`mesh_index` (nil = use the entity's geometry: `ProceduralMeshComponent`, else the MeshRenderer model mesh, else its primitive). Physics stays below assets in the layer map, so geometry arrives through a `CollisionMeshProvider` callback (like height fields and tilesets); `assets::collision_mesh_provider(db)` reads cooked models, primitives are built once and shared. `PhysicsWorld` owns a `CollisionMeshCache` (one load per model+mesh index or primitive; procedural meshes by identity) and builds each Jolt shape once per mesh, shared by every collider using it; per-entity scale (signed, so mirrored copies stay mirrored) and offset wrap it in `ScaledShape`/`RotatedTranslatedShape`. A dynamic body with a `mesh` collider simulates the hull (warned once; `victus check` warns too). Missing geometry creates no body, logs once per entity and is an error in `victus check`. Hot reload calls `PhysicsWorld::invalidate_mesh(model)` and bodies rebuild. Navigation rasterizes the source triangles of static convex and mesh colliders when a physics world is bound to the scene (edit-mode builds without one skip them). The editor overlay draws up to 4 096 triangle edges per collider through its own cache.
- Evidence: `victus_physics_tests` mesh-collider cases (validation, a gapped mesh floor holds a box while a box over the gap falls through and rays miss there, the hull of the same floor spans the gap, dynamic convex/mesh-fallback bodies rest at 0.5 m, provider called once per source with one shared hull for three pillars, non-uniform scale + offset, mirrored meshes, no-geometry/late geometry/invalidation/removal, procedural mesh replacement, reflection round trip and overlay lines); navigation case over a concave mesh floor; asset provider case on a cooked glTF; `victus check` case (no geometry, missing model, dynamic mesh warning).
- Consequences: concave dynamic objects need several convex colliders on child entities until convex decomposition (alternative (c)) exists; hulls above 256 points are simplified by Jolt; mesh colliders build synchronously on first use (large meshes stall that frame; no background cooking of Jolt shapes yet); kinematic mesh bodies do not collide with static meshes or height fields (Jolt rule). 2D polygon/chain colliders are a separate slice.

### ADR-0080: 2D polygon and chain colliders, with VICTUS-normalized chain sides

- Status: Accepted (2026-11-18)
- Context: `Collider2D` had box/circle/capsule only, so slopes, irregular platforms and level outlines needed many boxes (with ghost collisions at their seams). Box2D 3.2 polygons are convex with at most `B2_MAX_POLYGON_VERTICES` = 8 points built through `b2ComputeHull`; chains (`b2CreateChain`) are designed "to eliminate ghost collisions", "are one-sided", "have no mass and should be used on static bodies" and collide on the right of the segment direction, and "should not self intersect (this is not validated)" (box2d/types.h, `b2ChainDef`; https://box2d.org/documentation/md_collision.html). Godot's `CollisionPolygon2D` accepts concave outlines and decomposes them into convex pieces (https://docs.godotengine.org/en/stable/classes/class_collisionpolygon2d.html). Decomposition alternatives: (a) Bayazit's or Keil's near-optimal decompositions, (b) ear clipping plus Hertel-Mehlhorn merging (at most 4x the optimal piece count, simple and robust), (c) convex hull only (loses concavity).
- Decision: `Collider2D.shape` gains `polygon` and `chain`, with `points` (a new reflected `Vec2List` field kind, JSON `[[x, y], ...]`, at most 4 096 entries), `loop` and `inside`. Polygons accept any simple outline in either winding up to 256 points; `physics::decompose_polygon` cleans duplicate/collinear points, rejects crossings, ear-clips and merges with Hertel-Mehlhorn into pieces of at most 8 points, each a Box2D shape on one body (RigidBody2D mass is spread over them). Chains are normalized so authors never deal with Box2D's right-hand rule: open chains are solid on the left of their direction (ground drawn left to right is solid from above; mirroring keeps the local side), loops are solid outside, or inside with `inside`; ghost points continue the end segments; points closer than 7.5 mm are merged. Dynamic or trigger chains are filled as polygons (warned once). Invalid outlines create no body, are logged once and are not rebuilt until the collider changes; `victus check` reports them. The collider overlay draws outlines plus ticks on each chain segment's solid side; the inspector edits point lists.
- Evidence: `victus_physics_tests` (63 cases; 7 in `polygon_chain_2d_tests.cpp`: decomposition area/convexity/piece-size checks incl. a 42-point comb, errors; a box falls into a concave cup; dynamic triangle rests with its mass; open chains one-sided in both directions and mirrored; loops outside/inside in both windings; dynamic and trigger fallbacks; invalid outlines and recovery; reflection limits; overlay lines), `victus check` case.
- Consequences: no polygon rounding (box only); polygons over 256 points must be split by the author; Hertel-Mehlhorn is not minimal; tilemap colliders still use boxes (merging tile edges into chains is a follow-up); no in-viewport point handles yet (inspector rows only).

### ADR-0081: Tilemap solids collide through traced edge outlines

- Status: Accepted (2026-11-18)
- Context: Tilemaps built one Box2D box per greedily merged rectangle. Bodies sliding over the seams between separate convex shapes can catch on internal corners ("ghost collisions"); Box2D's one-sided chain shapes avoid this by giving each segment its neighbouring ghost vertices (https://box2d.org/posts/2020/06/ghost-collisions/). Unity's `CompositeCollider2D` offers the same choice as Geometry Type Outlines vs Polygons (https://docs.unity3d.com/Manual/class-CompositeCollider2D.html). Options: (a) keep boxes, (b) trace each solid region's boundary into closed loops, (c) marching squares with smoothing (not grid-exact).
- Decision: `Tilemap.edge_collision` (default on) makes `TilemapSystem` emit `tilemap::collision_outlines`: directed boundary edges of solid cells with the solid on the left, walked into closed rings preferring left turns (regions touching only at a corner stay separate), split at any repeated vertex into simple loops, collinear points removed. `physics::StaticShapes2DComponent` gained `loops`; Box2D builds each as a chain loop, whose collision side (right of travel) faces away from the solid, so outer outlines push outward and holes push into the room. One-way tiles stay boxes (they need per-shape pre-solve and only their top matters). `edge_collision = false` restores filled boxes. Box2D's geometric mover treats chain segments as two-sided segments, so 2D characters behave as before.
- Evidence: `victus_tilemap_tests` (9 cases): outlines for a block, L shape, ring (outer counter-clockwise, hole clockwise, areas add up), diagonal cells, a hole pinched to the outside (all loops simple), far coordinates; a crate resting inside a hollow room and on its roof, rays from inside the room hitting walls, a crate sliding 81 tiles without upward velocity, switching back to boxes; the existing character/one-way/dig test; `victus_sample_dungeon_crawler` and `victus_sample_platformer` pass.
- Consequences: chains have no interior, so bodies created inside solid tiles are not pushed out (switch to boxes when that matters); very small cells (< 7.5 mm after scale) merge points and may drop loops; the whole map is retraced on any edit.

### ADR-0082: Durable, verified writes and generation history for project data

- Status: Accepted (2026-11-18)
- Context: `fs::write_atomic` wrote a temporary with `std::ofstream` and renamed it. Rename alone is atomic but not durable: without flushing the file before the rename and the directory after it, a power loss can leave an empty or stale file (LWN, "Ensuring data reaches disk": fsync the temp file, rename, fsync the containing directory; https://lwn.net/Articles/457667/). Errors from a full disk surfaced only as a generic stream failure, nothing checked that the bytes on disk matched, and scenes, prefabs and `victus.project` kept no previous copy (save games had a validated `.bak`). Roadmap 6l asks for transactional writes that keep a verified prior generation and survive interruption, disk-full and permission failures.
- Decision: `write_atomic` writes the temporary with native calls (POSIX `write` + `fsync`, `F_FULLFSYNC` on Apple; Windows `WriteFile` + `FlushFileBuffers`), reports the OS reason, reads the temporary back and compares it, renames, then flushes the directory. Temporaries are hidden (`.<name>.tmpXXXXXXXX`) so a crash never leaves a file that asset scans import. New `fs::write_safely` adds a transaction on top: validate the new bytes, stage the verified temporary, copy the current file into generation 1 (`.<name>.vbak1`, older ones shift, default 2 kept) only if it validates, otherwise move it to `.<name>.damaged`, then rename. `path` always holds a complete file. `fs::read_with_recovery` returns the newest valid copy and logs which generation it used; a `VersionMismatch` from the validator stops the search so an older generation never silently replaces newer data. `restore_generation` restores through `write_safely`, so a restore can be undone. `json::document_validator(format)` checks parse and `format`. Scenes, prefabs and `victus.project` save and load through it; save games keep their existing `.bak` layout but now get durable verified writes for both files. One-shot fault injection (`fs::testing::inject_write_fault`: disk full, corrupted temporary, crash before the swap) drives the tests. New projects' `.gitignore` ignores history, damaged and temporary files.
- Evidence: `victus_core_tests` `fs:*` (disk full, corrupt temporary caught by read-back, read-only directory, history rotation and dropping, interrupted swap, torn current file recovered from generation 1 and preserved as damaged, missing current file, undoable restore, newer-version stop, all-invalid error naming each copy, history 0, hidden files out of listings); `victus_scene_tests` (torn scene loads from its previous generation); full ctest.
- Consequences: each scene/prefab/project save writes the file twice (current copy into history), acceptable for documents of this size; Windows does not flush directory entries (NTFS journals the rename); cooked assets, materials, tile sets and editor layout still use plain durable `write_atomic` without history; the editor does not yet show history or offer a restore UI (API only); migrations and safe mode (rest of 6l) remain.

## ADR-0083 — Audio voice budget: priorities, virtual voices and fades (accepted 2026-11-18)

**Context.** `AudioEngine` mixed every playing source and cut the oldest one-shot when `max_one_shots` was exceeded, so a scene with many looping emitters (torches, machines) cost mixing time for inaudible sounds and the one-shot cap clicked. Roadmap 6k asks for concurrency, priority, virtualisation and click-free reclaim.

**Decision.** Follow the established virtual-voice model of [FMOD's virtual voice system](https://www.fmod.com/docs/2.04/api/managing-resources-in-the-core-api.html) and [Unity's `AudioSource.priority`](https://docs.unity3d.com/ScriptReference/AudioSource-priority.html), implemented in VICTUS on top of miniaudio (no new dependency):
- `EngineOptions::max_voices` (default 96) real voices shared by entity sources and one-shots. After each `update()` and `play_one_shot()` all live voices are ranked: priority (0..255, higher wins, default 128) strictly first, then audible before inaudible, then audibility (sound volume × bus/Master gain × miniaudio's own distance model evaluated on the CPU), then age.
- Entity sources that lose, or whose audibility is below −60 dB (`kInaudibleGain`), become virtual: faded out and stopped in miniaudio, while the engine records the cursor and engine time. When they win again the cursor is advanced by the elapsed engine frames (× pitch × clip/engine rate), wrapped for loops, and the sound resumes in place with a fade-in; non-looping clips that ended meanwhile stop. `is_playing` stays true while virtual; `is_virtual` reports the state.
- One-shots are short, so losers are stolen (faded out) rather than virtualised. `OneShot::priority` and `OneShot::max_instances` (same-clip polyphony limit, oldest fades out) are new; the `max_one_shots` cap fades too.
- Every voice-manager stop uses a 10 ms (`kVoiceFadeMs`) fade, which removes the clicks of hard cuts. Dying one-shots past a hard limit are released outright so no-device engines without `render()` calls cannot accumulate them.
- Stats gain `real`, `virtual_voices`, `stolen` and `virtualised`; Luau `audio.play` accepts `priority` and `max_instances`.

**Alternatives.** FMOD/Wwise themselves: proprietary licences, rejected for a core engine path. Virtual voices that keep decoding silently: costs CPU for nothing; cursor arithmetic is enough for file-backed clips. Restart-from-start on resume (FMOD's `VIRTUAL_PLAYFROMSTART`): left for later as a per-source option.

**Consequences.** Mixing cost is bounded by `max_voices`. Ranking is O(n log n) per update on the game thread, not in the audio callback. Limits: audibility ignores clip loudness, filters and reverb sends; virtual streamed clips seek on resume (may hitch on slow storage); no per-bus voice limits or virtual-voice cap; fades progress only while audio is mixed.

## ADR-0084 — Particle flipbooks and velocity-stretched billboards (accepted 2026-11-18)

**Context.** ADR-0053 gave the particle renderer per-instance flipbook frames and a height/width ratio, but `ParticleEmitter` never filled them, so authored effects could not use sprite-sheet smoke or flame textures or streaking sparks, and the 2D path ignored both. Common practice: [Unity's Texture Sheet Animation module](https://docs.unity3d.com/6000.3/Documentation/Manual/PartSysTexSheetAnimModule.html) (grid tiles, frame over time or fixed FPS, random start frame) and [stretched billboards](https://docs.unity3d.com/Manual/PartSysRendererModule.html) (Length Scale and Velocity Scale stretch along the velocity).

**Decision.** Emitter fields `flipbook_columns/rows` (1..15, the ADR-0053 grid limit), `flipbook_frames`, `flipbook_fps` (0 = frames span each particle's life once, holding the last frame; > 0 = loop at that rate), `flipbook_random_start`, and `velocity_stretch` (seconds). The simulation writes frame, grid and aspect into the billboard's former reserved floats (layout unchanged, 48 bytes) and exposes world velocities only for stretched emitters. The default rotation aims along the velocity's XY direction, which is exact for 2D and for a camera looking down -Z; `extract_scene` re-aims stretched billboards per camera with the derivative of the perspective projection (screen direction ∝ d.xy·(−p.z) + p.xy·d.z in view space) and shortens them by the fraction of motion across the view. The 2D sprite path maps frames to `Sprite::uv` (`particles::flipbook_uv`) and stretches sprite height. Random start frames draw from the emitter stream only when enabled, so existing emitters keep bit-identical output.

**Alternatives.** A GPU-side stretch with velocity in the instance: needs a larger instance layout and a renderer change for a CPU-simulated system. Frame blending: needs two samples and motion vectors; left out (ADR-0053 consequence). Ribbon trails: a different primitive (connected strips), still open.

**Consequences.** One batch per emitter regardless of frame. Stretched emitters copy their billboards once per 3D view. Limits: no frame blending, no curves for frame-over-life, no ribbons; aim is per camera only in the 3D extraction (editor thumbnails or secondary views use the main camera).

## ADR-0085 — Particle ribbon trails (accepted 2026-11-19)

**Context.** Comets, tracers, sword swipes and magic bolts need a continuous ribbon behind each particle; ADR-0084 streaks only stretch a single quad along the current velocity, so curved paths and lingering trails were impossible. Common practice is [Unity's Trails module](https://docs.unity3d.com/Manual/PartSysTrailsModule.html) in Particle mode: a trail vertex is added once the particle has moved a minimum vertex distance, vertices expire after a trail lifetime, width and colour vary over the trail, and trails can die with their particles.

**Decision.** Emitter fields `trail_lifetime` (seconds; 0 = off), `trail_min_distance`, `trail_max_points` (2..64 per particle; the oldest point is dropped when full), `trail_width` (× particle size at the head), `trail_width_end` and `trail_alpha_end` (fractions at the tail) and `trail_billboards` (also draw the heads). Each emitter keeps a flat block of `trail_max_points` points per particle, moved with the particle on swap-removal and restarted when the cap changes; history is recorded in simulation space, so local-space trails follow their entity. Every update emits `RibbonPoint`s (position, width, colour, v) tail to head plus the live head position, one strip per particle, and the emitter bounds include them. `SceneRenderer::submit_ribbons(points, strips, material, bounds)` turns each strip into a triangle list with two edge vertices per point in the 48-byte particle layout (signed half width, tangent from central differences, v along the trail); a new `ribbon.vert` pushes each edge along cross(tangent, to-eye), falling back to the camera right axis when the trail points at the eye, and reuses `particle.frag`, so ribbons get the soft depth fade, occlusion, additive/alpha blending and back-to-front batch ordering of particles. Without a texture the soft disc's middle row is sampled (soft edges across the trail; width and alpha carry the fade along it). The 2D path draws one sprite per segment, end to end (overlap would double up under additive blending).

**Alternatives.** Stretched billboards per segment in the existing instanced pipeline: no new shader, but visible joints and doubled overlap at every point. Unity's Ribbon mode (one strip connecting all particles by age) and texture tile modes: useful for lightning and lasers, left for later. GPU-generated strips from a history buffer: needs GPU simulation (ADR-0053's CPU particles remain).

**Consequences.** One extra draw per trailed emitter; six vertices per segment uploaded each frame. `SceneStats::ribbon_vertices` and `ExtractStats::particle_trails` count them. Limits: trails die with their particles; no Ribbon mode, texture tiling, width/colour curves or lit trails; ribbons inside one emitter are not sorted against each other (alpha trails crossing themselves may order wrongly); the 2D path leaves small wedge gaps at sharp bends.

## ADR-0086 — Background Jolt mesh-shape building (accepted 2026-11-19)

**Context.** ADR-0079 built convex hulls and triangle meshes synchronously the first time a step saw a mesh, so a large imported level mesh stalled that frame (Jolt's `MeshShapeSettings::Create` builds a bounding-volume tree and `ConvexHullShapeSettings::Create` runs a hull builder, both proportional to the input). [Jolt's architecture notes](https://jrouwe.github.io/JoltPhysics/index.html) describe `ShapeSettings::Create` as cooking self-contained data (all information is copied into the Shape) and allow body preparation from a background thread; each build here uses its own settings object and only reads the immutable `CollisionMesh`, so it shares no state with the stepping thread except Jolt's thread-safe allocator and atomic reference counts.

**Decision.** `PhysicsSettings::async_mesh_triangles` (default 4096). With a job system, a mesh above the threshold submits a `Background`-priority job that builds the shape from the immutable `CollisionMesh` into a shared build record; the step returns without a body, and a later step that finds the build finished caches the shape (shared by every body using the mesh, as before) and creates the bodies. Failed builds are cached as failed, exactly like synchronous ones. `PhysicsStats::mesh_shapes_pending` counts builds in flight. The world keeps every submitted build until it has finished and waits for them on destruction, so Jolt is never released under a running build even when its cache entry was replaced or cleared.

**Alternatives.** Keeping the old body until the new shape is ready: complicates the change-detection path for a rare case (mesh edits replace the body a few frames later). A placeholder box shape while building: wrong collisions are worse than none for level geometry. A dedicated thread: the engine job system already has a background priority.

**Consequences.** Bodies over large meshes appear a few frames late (58 steps in the 7200-triangle test on a 2-vCPU host with workers shared); dynamic bodies dropped onto them meanwhile fall through, so levels should spawn players after `mesh_shapes_pending` reaches zero. Without a job system or with the threshold at 0 behaviour is unchanged.

## ADR-0087 — V.A.U.L.T. stage 1: asynchronous texture/model loading with a per-frame upload budget (accepted 2026-11-19)

**Context.** `GpuAssetCache::texture()`/`model()` read the cooked file, decoded it (and, in a project, re-imported a stale source) and uploaded it on the render thread the first time `extract_scene` met an asset, so every newly visible asset stalled its frame; a failed load was retried (re-read from disk) every frame. The established engines split the work the same way: [Unreal's `FStreamableManager::RequestAsyncLoad`](https://dev.epicgames.com/documentation/en-us/unreal-engine/API/Runtime/Engine/Engine/FStreamableManager/RequestAsyncLoad) returns a handle with a priority and calls back once loaded, [Unity Addressables](https://docs.unity3d.com/Packages/com.unity.addressables@2.0/manual/AddressableAssetsAsyncOperationHandle.html) hand out reference-counted operation handles whose early release discards the result when it completes, and [Godot's `ResourceLoader.load_threaded_request`](https://docs.godotengine.org/en/stable/classes/class_resourceloader.html) loads per path on threads with a status the game polls on later frames.

**Decision.**
- `assets::AsyncLoader` (CPU stage, no GPU): one slot per (UUID, type) shared by every caller; requests are dispatched in priority then request order with at most `max_in_flight` decodes on `Background` jobs; `take(byte_budget)` hands decoded payloads out by priority under a byte budget (always at least one, so a large asset never starves); failures keep their `Error` until `forget()`; `forget()` of a running load discards its result when the worker finishes (the job owns its record). Without a job system the same code path loads inside `request()`.
- `GpuAssetCache::set_async_loading(jobs, {upload_budget_bytes = 8 MiB, max_in_flight = 4})`: `texture()`/`model()` return the new `ErrorCode::Pending` while loading; `pump()` (called by `extract_scene`/`extract_sprites`) uploads within the budget and rebuilds cached materials after a texture arrives. Extraction skips meshes, sprites, decals and particle emitters whose asset is pending (counted in `ExtractStats::loading_assets`, not `missing_assets`) instead of drawing them untextured; terrain layers and `.vmat` texture slots render without the texture until it arrives. `evict()`/`clear()` forget slots, so hot reload re-requests. `finish_loads()` (loading screens, tests) and `wait_loads()` (before `AssetDatabase::refresh()`; `AssetHotReloader::set_before_refresh` calls it) bound the asynchronous window.
- `JobSystem::wait` on a thread outside the pool no longer runs `Background` jobs, so the game thread waiting on physics or animation work never picks up a decode (or an ADR-0086 mesh build) and stalls for its duration; workers still run them.
- The player enables it for interactive runs (`--sync-assets` opts out); fixed-frame, recorded and replayed runs stay synchronous so screenshots, perf budgets and captures remain deterministic. The editor stays synchronous for now (many panels call `refresh()` directly).

**Alternatives.** Handing out placeholder textures while loading: a checker or white surface reads as a bug in shipped games, and skipping is what the other engines' handle model leads to. Decoding on a dedicated I/O thread: the job system already has a starvation-safe background queue. Uploading on workers: the RHI is single-threaded by contract.

**Consequences.** Newly referenced assets appear a frame or more late in interactive runs; scenes that must be complete on their first frame call `finish_loads()`. Not yet: CPU/GPU residency budgets and eviction, prefetch by distance, texture-mip streaming, dependency closure, async environment-map bakes and editor support; those are the next V.A.U.L.T. stages. The database must not be refreshed while decodes run (`wait_loads()`).

## ADR-0088 — V.A.U.L.T. stage 2: GPU residency budget with idle-LRU eviction (accepted 2026-11-19)
- Context: stage 1 streams assets in but never releases them; long sessions over large worlds grow GPU memory without bound. Unreal's texture streaming pool, Unity's Addressables reference-counted release and Godot's ResourceLoader cache all bound or release resident data.
- Decision: `GpuAssetCache` records each texture/model's upload bytes and the frame it was last used (direct lookups, and cached materials through the texture references recorded when they were built). With `ResidencySettings::budget_bytes > 0`, `pump()` evicts assets idle at least `min_idle_frames` (hysteresis against thrashing), least recently used first and larger first on ties, until under budget; in-use assets are never evicted, `over_budget` reports the overflow. Eviction is safe with frames in flight because `SDL_ReleaseGPUTexture`/`SDL_ReleaseGPUBuffer` defer the free until the GPU is done.
- Consequences: deterministic (frame-count based), opt-in per project (`rendering.asset_budget_mb`); evicted assets cost a reload (async in the player). Not yet: mip-level dropping, CPU-side budgets, non-cache resources.
- References: https://docs.unity3d.com/Packages/com.unity.addressables@2.0/manual/AddressableAssetsAsyncOperationHandle.html , https://docs.godotengine.org/en/stable/classes/class_resourceloader.html , https://wiki.libsdl.org/SDL3/SDL_ReleaseGPUTexture

## ADR-0089 — V.A.U.L.T. stage 3: texture mip streaming by projected footprint (accepted 2026-11-19)
- Context: stage 2 can only evict whole idle assets; a scene in view over the budget stays over it, and distant textures hold full-resolution levels they never sample. Unreal's texture streamer computes per texture "the wanted number of mip-levels" from "approximately how many pixels the texture occupies on the screen" and, when the pool is short, streams out levels from low-priority textures (https://docs.unrealengine.com/udk/Three/TextureStreaming.html).
- Decision: extraction reports each material/decal texture's largest projected footprint per frame (bounding-sphere diameter in pixels at the nearest point, times UV tiling). The wanted top level is the first whose edge still covers the footprint, clamped so the top stays at least `min_streamed_size`. Raises apply on the next pump (largest footprint first, partially when the budget does not fit the full raise); drops wait `mip_drop_frames` (hysteresis). Over budget with nothing idle, the largest in-use textures lose one top level per pump, and raises stop. A level change re-decodes the cooked texture (through the async loader when present) and uploads the mip-chain suffix to a new texture, swapping the handle; the old one is released with SDL's deferred free, and cached materials are rebuilt.
- Why not partial residency / sparse textures: SDL_GPU exposes no sparse binding or per-mip residency, so a smaller texture plus a swap is the portable option (as Unreal's mip-change reallocation does on most RHIs). Why re-decode instead of keeping CPU copies: CPU copies would double memory, the thing being budgeted.
- Consequences: opt-in (`rendering.texture_streaming`); deterministic (frame-clock based) in synchronous runs. Not yet: model-embedded textures, per-mesh UV density, GPU-side mip copies on downgrade.

## ADR-0090 — World streaming stage 1: grid cells, streaming sources, gated activation (accepted 2026-11-19)
- Context: scenes load whole (`Scene::load` clears the scene); a large environment must fit in memory at once and every asset loads before the first frame. 6h asks for a world model with stable cells, multiple streaming sources with radii, hysteresis and cancellation, V.A.U.L.T.-backed dependency loading and no partially active cells.
- Prior art: Unreal World Partition divides a world into grid cells that load around streaming sources (the player controller by default) within a per-grid loading range, prioritises by distance and caps concurrent cell loads (`wp.Runtime.MaxLoadingLevelStreamingCells`), and can block on slow streaming (https://dev.epicgames.com/documentation/unreal-engine/world-partition-in-unreal-engine). Unity loads scenes additively (`LoadSceneMode.Additive`, https://docs.unity.com/en-us/engine/6000.3/script-reference/unityengine/scenemanagement/scenemanager/loadscene), and Addressables' `activateOnLoad = false` separates loading from activation because the final part of scene activation runs on the main thread (https://docs.unity3d.com/Packages/com.unity.addressables@1.16/manual/LoadSceneAsync.html).
- Decision: new layer-3 module `engine/world`. A world is a persistent scene plus a `.vworld` descriptor (`victus.world` v1: name, `load_radius`, `unload_margin`, cells with a stable uuid, project-relative victus.scene path, AABB and optional radius). `WorldStreamer::update(scene, sources)` wants a cell when any source's distance to its AABB is within radius × source scale, keeps it until beyond radius + margin (hysteresis), starts reads nearest first up to `max_loading` (Background jobs; synchronous without a job system), cancels reads no source wants, and activates at most `activations_per_update` parsed cells per update through the new `Scene::load_additive` (all-or-nothing, parents may be persistent entities, uuid collisions roll back). A parsed cell first requests the asset uuids its components reference through `Dependencies` (the player passes `runtime::world_dependencies(GpuAssetCache&)`, which prefetches textures, models and material textures through V.A.U.L.T.) and activates only when all are settled, or after `max_wait_updates` (counted). Unloading snapshots the cell's root subtrees (`save_subtree`), so moved, changed or destroyed entities persist across unload/reload; `save_state`/`load_state` write that into save games. Sources are `StreamingSource` components, else the camera. `partition_scene` (CLI `victus world`) buckets root subtrees by XZ grid cell and keeps cameras, scripts, characters, UI, terrain, tilemaps, network identities, directional lights and wider-than-a-cell content persistent. Deterministic runs (`--frames`, captures) read synchronously.
- Why not reuse scene transitions or prefabs: transitions replace the scene; prefabs instantiate copies with new uuids, which breaks stable identity and saved state. Why snapshot instead of hibernating entities in the ECS: unloaded cells must free memory; snapshots are the same JSON the editor's undo and save games already use.
- Consequences: the player, export (descriptor and cells packed, every cell checked like a scene) and `victus check` understand worlds. Not yet: cross-cell entity references beyond parents in the persistent scene, data layers, prefetch-by-velocity, server-side interest management and cell ownership, physics/navmesh readiness gates beyond assets, a Studio world overview.

## ADR-0091 — A.R.C. stage 1: articulated ragdolls on Jolt (accepted 2026-11-19)
- Context: 6f needs an articulated-body foundation before any reactive behaviour. VICTUS exposed rigid bodies, five joint types and character controllers, but no ragdoll; the pinned Jolt 5.7.0 ships `RagdollSettings`/`Ragdoll` (skeleton, swing-twist parts, `DriveToPoseUsingKinematics`, `DriveToPoseUsingMotors`, `DisableParentChildCollisions`) and the PoweredRigTest sample drives a ragdoll toward an animation pose with motors.
- Decision: a `Ragdoll` component on the character root (mode Off/Kinematic/Powered/Passive, total mass, motor frequency/damping/torque, blend, pin_root, gravity_compensation, friction, damping, layer/mask) plus one `RagdollBone` component per simulated bone (capsule/box/sphere, radius, length, mass, swing/swing_plane/twist limits, strength). A component per bone because reflection has no vector-of-struct fields, and because bones stay ordinary entities editable in the inspector and saved in scenes. `make_humanoid_ragdoll(scene, root)` recognises 16 humanoid bones across mixamorig/Unreal/plain naming, skips helpers (ik_, twist, finger, toe, end, eye, jaw, pole, target), and applies per-role shapes and limits.
- Backend: the Jolt backend gathers bones depth-first (each bone's anchor is its nearest bone ancestor; plain entities in between are folded into the parent frame), builds one `RagdollSettings` with `SwingTwistConstraint` parts (twist along the bone; `swing` about the bone's local Z, `swing_plane` about the axis perpendicular to both), runs `Stabilize()` and reads back the masses Jolt actually simulates, and gives every part a subgroup of a private `GroupFilterTable`: parent/child and initially-overlapping pairs never collide, and the owner's `CharacterController` inner body (subgroup n) ignores its own ragdoll. Raycasts that ignore the root and the character's own sweep ignore its ragdoll bodies too. Body user data is the bone entity, so queries, contacts, impulses and velocities work per bone.
- Pose flow: animation writes bone Transforms in Update; the PostUpdate system captures any Transform that differs from what physics last wrote as the new animated target, then writes the simulated pose back (local to the parent bone, `blend` 0 = animation, 1 = simulation). Kinematic mode follows the target with `DriveToPoseUsingKinematics`; Powered uses `DriveToPoseUsingMotors` with `pin_root` keeping the root bone kinematic; Passive switches motors off. Mode switches keep pose and momentum (no rebuild).
- Motors: Jolt's frequency mode tunes a joint spring against only the two bodies it connects, so an 8 Hz shoulder motor moved the whole arm at ~0.6 Hz and badly underdamped (measured: 1.4 s period, overshoot). VICTUS converts `motor_frequency`/`motor_damping` into stiffness and damping from the rest-pose inertia of the subtree each joint carries (parallel axis about the pivot), so the response holds for the limb as a whole; default 4 Hz (stiffer chains can chatter in the iterative solver). Gravity compensation applies equal and opposite internal joint torques cancelling each joint's carried weight (subtree COM about the pivot), so momentum is unchanged and motors only correct the remaining error; it scales with `gravity_compensation` and is capped by the joint's torque limit.
- Why not PhysX articulations or Featherstone: Jolt is the pinned backend and its maximal-coordinate ragdolls are production-proven; switching solvers is a separate research item (RESEARCH_REGISTER A.R.C.).
- Consequences: Studio shows ragdolls as orange wireframes with collider gizmos; scripts get `entity:set_ragdoll(mode[, blend])`, `entity:ragdoll_state()` and `entity:ragdoll_root()`. Not yet: get-up and root/capsule follow, partial-body masks beyond per-bone strength, reactive behaviours and balance, an editor ragdoll wizard, ragdoll networking, 2D ragdolls.

## ADR-0092 — V.A.U.L.T. stage 4: mip streaming for glTF-embedded textures (accepted 2026-11-19)
- Context: ADR-0089 streamed texture assets only. Imported models carry their textures inside the cooked model, so most real content (glTF characters and props) was uploaded at full resolution whatever its screen size, and the only way to re-read a texture was to decode the whole model, meshes included.
- Decision: each embedded texture streams under a deterministic key derived from (model uuid, texture index) and reuses the ADR-0089 `Streamed` state, wanted-level rule, hysteresis, budget drops and per-pump restream limit. Extraction notes a footprint for the textures of the mesh's own material (when no `.vmat` override replaces it). `deserialize_model_texture` reads the cooked model only up to the wanted texture (textures come first in the format) and `AssetDatabase::load_model_texture` exposes it; re-decodes run on loader jobs when async loading is on, found through a mutex-guarded key registry shared with the workers. Level changes swap the handle in the model's texture slot, patch the model's resolved mesh materials and adjust the model's residency bytes by the levels added or dropped. When a model is evicted, per-mesh bounds and texture use are kept so a mesh seen while it reloads still reports a footprint and the reload uploads only the needed levels.
- Why not split model textures into separate texture assets at import: it would change asset identity, the cooked format and the export/packaging contract for every project; keys over the existing format keep cooked data and saved scenes unchanged.
- Consequences: a re-stream still reads the cooked model file from disk (decoding stops at the texture). Not yet: sprites, terrain layers and particles; partial file reads.

## ADR-0093 — Destruction stage 1: deterministic Voronoi fracture with connection-graph support (accepted 2026-11-19)
- Context: 6j. VICTUS only had breakable joints; nothing could break a prop or a wall. Production engines (Unreal Chaos Destruction, NVIDIA Blast) pre-fracture geometry into Voronoi pieces, hold them in a connection graph, break on damage thresholds and keep "world-supported" (anchored) pieces static until their support is gone.
- Decision: a `Destructible` component on any entity with a mesh or collider. `physics::fracture_convex` clips the convex hull of the entity's visible mesh (exact planes for convex meshes such as the primitives; a 90-direction discrete-orientation polytope for concave input; the collider shape when there is no mesh) into Voronoi cells seeded by a PCG stream from `seed`, using bisector-plane polyhedron clipping and pseudo-angle ordering (no libm trigonometry), so fracture is bit-identical across runs and platforms and volume-conserving; cut faces record the neighbouring cell, giving the connection graph. Breaking is triggered by contacts — `ContactEvent` now carries `speed` and an `impulse` estimate (closing speed times the pair's reduced mass, taken in Jolt's `OnContactAdded`) — or by `PhysicsWorld::damage` / Luau `entity:damage(point, impulse)`, at or above `strength`. The original is hidden and loses its body; each fragment becomes a child entity (ProceduralMesh with flat-shaded faces and darker cut faces, copied MeshRenderer, Convex collider with the original's material and layers, RigidBody, `DestructibleFragment{owner, piece}`). Dynamic originals burst fully, fragments inherit linear and angular velocity and split the mass by volume. Static/kinematic originals free only the pieces within `damage_radius` of the hit (plus the nearest), then run a support pass: static pieces touching the original's base are anchors, and static pieces no longer reachable from an anchor through static neighbours fall. Pieces of one destructible never damage each other. Debris obeys `debris_lifetime` and `max_debris` (oldest retired first). Fragment geometry is not saved: `restore_fragments` (run by each step) regenerates it deterministically from the owner after load, so a broken scene saves only components.
- Why not a fracture asset format first: the fracture is a pure function of (source geometry, pieces, seed), so cooked data adds nothing until author-edited fractures, hierarchical clusters or non-convex sources need it; the function is the seam such an asset will cache. Why not runtime boolean cuts at the impact point: unbounded cost and non-deterministic replay. Why not Blast: an extra native dependency for a feature Jolt bodies already cover; reconsider for very large structures.
- Consequences: the source is fractured as its convex hull (concave meshes lose their concavities); fragments use the MeshRenderer's material asset/tint and box-projected UVs, not the model's own textures; the projectile has already been resolved by the solver when the break happens (it bounces off rather than passing through). Not yet: hierarchical clusters, strain accumulation, Studio fracture preview, network replication, LOD/simplified debris collision, world-cell lifetime.

## ADR-0094 — Gameplay framework primitives: tags, events, timers, attributes/effects, abilities, inventory (accepted 2026-11-19)

**Context.** VICTUS had AI blackboards and sequencer events but no shared vocabulary for gameplay state: scripts could not message each other, there were no timers, statuses, stats, cooldowns or inventories, and every game re-implemented them in Luau. Unreal's Gameplay Ability System (attributes, gameplay effects with instant/duration/infinite policies, periodic execution, stacking, granted tags; abilities gated by tags, cost and cooldown) is the established reference.

**Decision.** `engine/gameplay/framework.hpp` adds small, composable ECS primitives instead of one monolithic ability component:
- `Tags` (reflected string, hierarchical dot tags: `Status` matches `Status.Burning`); effects can grant tags while active; `find_tagged` queries in entity order.
- A per-scene `EventBus` resource: `emit_event` runs C++ listeners immediately (re-entrancy depth 16), keeps events for two ticks (`begin_event_tick` in PreUpdate, cap 4096) and scripts receive them as `on_event(name, payload, sender)` next frame — targeted or broadcast in entity-index order.
- `Timers` (one-shot/repeating/pausable), firing an event named after the timer.
- `AttributeSet` definitions (`health = 80 [0..max_health]`, bounds may name attributes) instanced into a saved runtime `Attributes` component; effects with Add/Multiply/Override, instant/timed/infinite durations, periods, Refresh/Stack/Independent stacking; `attribute_changed` and `attribute_depleted` events.
- Abilities as a stateless check: required/blocked tags, all-or-nothing costs, cooldown stored as the effect `cooldown.<name>` granting `Cooldown.<name>` (so it saves and is queryable like any status).
- `Inventory` slots with per-item stacking, capacity, removal from the last slot and transfers; `inventory_changed` events.
FixedUpdate systems `gameplay.timers` and `gameplay.attributes` advance them deterministically. Everything serializes with the scene, so save games and checkpoints keep cooldowns, buffs and items. Luau exposes all of it on entities plus `events.emit` and `scene.tagged`.

**Alternatives.** A full GAS port (prediction keys, ability tasks, execution calculations) was rejected for now: VICTUS has no replication of gameplay state yet and the complexity would dominate. Ability graphs/assets can be layered on these primitives later.

**Consequences.** Hand-written serializers mean Studio's inspector shows the definition components (`Tags`, `AttributeSet`) but not runtime timers/effects/inventory yet. No networking of attributes; no modifier magnitudes computed from other attributes beyond bounds.

## ADR-0095 — Gerstner water volumes with screen-space refraction and Jolt buoyancy (accepted 2026-11-19)

**Context.** VICTUS had terrain, foliage, a physical sky and fog, but no water: no surface to render, nothing for bodies to float in, no way for gameplay to know whether a point is under water. The established real-time approaches are (a) a sum of Gerstner (trochoidal) waves evaluated on a grid in the vertex shader (GPU Gems ch. 1, used by most shipped games for lakes and stylised seas), and (b) Tessendorf's FFT spectrum for open ocean. Buoyancy in engines that use Jolt is done with `Body::GetSubmergedVolume` + `Body::ApplyBuoyancyImpulse` (exact polyhedral submerged volume, Game Programming Gems 6 §2.5).

**Decision.**
- `gameplay::WaterComponent` ("Water", category Environment) describes an axis-aligned water volume: size, shallow/deep colour, clarity (Beer-Lambert metres), wave height/length/direction/steepness/speed, foam, refraction, roughness, grid resolution, physical density (kg/m³), Jolt linear/angular drag, a linear `damping` and a current.
- Waves: four Gerstner waves derived from the primary (wavelength ratios 1/0.618/0.382/0.236, direction offsets 0/23/-31/47°), deep-water dispersion ω = √(g k), amplitude split so Σ Qᵢ kᵢ Aᵢ = steepness (crests never loop). Phases are wrapped in double precision so water stays smooth after days of play time. A `WaterClock` resource is advanced by the FixedUpdate system `gameplay.water`, so physics, scripts and rendering see the same surface.
- CPU queries invert the horizontal Gerstner displacement with a 4-step fixed point (`sample_waves`), giving the height, normal and Jacobian that match the rendered grid to centimetres; `query_water` / `water_volumes` serve gameplay and physics.
- Rendering (`SceneRenderer::add_water`): a vertex-indexed grid (no vertex buffers) displaced by the same sums, waves shorter than four grid cells faded out of the geometry, border vertices pinned. After decals, the HDR target is copied (`water_scene_copy`), then the water pass reads that copy and the depth buffer: screen-space refraction with depth-validated offsets, Beer-Lambert absorption by refracted depth, Schlick Fresnel against the environment cube (or sky gradient), GGX sun glint, crest/shore foam, fog, an underwater flip and soft shoreline alpha. A depth-only pass then writes the surface so blended geometry behind water is occluded. Up to 16 surfaces per frame, frustum-culled, nearest kept.
- Physics: every dynamic Jolt body whose bounds reach into a volume gets `GetSubmergedVolume` against the wave plane at its centre and `ApplyBuoyancyImpulse` with buoyancy = density · volume / mass (Jolt's factor is the density ratio), the current as fluid velocity and the volume's drags. Jolt's drag is quadratic and vanishes for slow motion, so a linear damping (default 1.5/s × submerged fraction, modelling wave-radiation damping) settles bobbing. `water_entered`/`water_exited` gameplay events fire in entity order; `PhysicsWorld::water_contact` reports the submerged fraction.
- Luau: `water.query(pos)`, `water.height(x, z)`, `entity:water_state()`; scripts receive the events through `on_event`.

**Alternatives.** FFT ocean (Tessendorf) gives richer open-sea spectra but needs compute passes and readback for physics; the Gerstner sum is exact on the CPU and cheap, so it is the base layer and an FFT cascade can be added behind the same component later. Planar reflections double the scene cost per water plane; SSR needs a depth/normal G-buffer VICTUS's forward path does not keep. Both were deferred in favour of environment-cube reflections.

**Consequences.** Volumes ignore rotation and have no bottom (bodies below the surface anywhere in the footprint are in the water). Reflections show only the sky/environment, not scene objects; water receives no shadows and writes no TAA motion vectors. Buoyancy samples a single plane per body (long boats see one slope), uses Jolt's bounding-box volume for capsules/cylinders, and ignores 2D bodies and ragdoll bones. The editor preview animates with wall-clock time when the simulation clock is not running.

## ADR-0112 — Cloud shadows on lit surfaces

- Status: Accepted (2026-11-19)
- Context: ADR-0111 added a ray-marched cloud layer but the ground stayed fully sunlit under overcast skies. Production engines darken the sun on surfaces under clouds: Unreal's volumetric cloud component renders a cloud shadow map ([Unreal Engine docs](https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-cloud-component-properties-in-unreal-engine)), Frostbite projects a cloud transmittance texture ([Frostbite](https://www.ea.com/frostbite/news/physically-based-sky-atmosphere-and-cloud-rendering)), and Horizon Zero Dawn reuses its density field for shadowing ([Guerrilla](https://www.guerrilla-games.com/read/the-real-time-volumetric-cloudscapes-of-horizon-zero-dawn)).
- Decision: evaluate cloud shadow analytically in `pbr.frag`: intersect the sun ray from the shaded point with one height inside the layer (30% up), sample the same value-noise shape (two octaves, same wind offset, coverage threshold and scale as `clouds.frag`), turn density into optical depth over half the layer thickness divided by the sun's elevation (clamped at 0.2), and multiply the sun term by `mix(1, exp(-od), shadow_strength)`. Parameters ride in three new `LightingUniforms` vectors; `VolumetricClouds::shadow_strength` (default 1) and `EnvironmentComponent::cloud_shadows` (0..1) control it; `SceneStats::cloud_shadows` reports it.
- Alternatives: a cloud shadow map rendered per frame (extra pass, texture, more correct; deferred until a shadow-texture budget exists); applying it through CSM (would not reach beyond cascade range).
- Consequences: no new pass or texture; the shape matches the visible clouds at one height, not the full integrated column; water, 2D lit sprites, fog sun shafts and probe captures are not cloud-shadowed yet.

## ADR-0111 — Volumetric clouds: reduced-resolution ray-marched cloud layer

- Status: accepted (2026-11-19)
- Context: skies were a gradient, an HDR map or the physical atmosphere (ADR-0074) with no clouds, the first item of the "weather and clouds" gap. Production engines ray march a cloud layer with procedural density: Horizon Zero Dawn's cloudscapes (Schneider & Vos, SIGGRAPH 2015, https://www.guerrilla-games.com/read/the-real-time-volumetric-cloudscapes-of-horizon-zero-dawn) threshold a low-frequency shape noise by coverage and a height gradient and erode the edges with high-frequency detail, lit by a short light march with Beer's law; Frostbite (Hillaire, "Physically Based Sky, Atmosphere and Cloud Rendering in Frostbite", SIGGRAPH 2016, https://www.ea.com/frostbite/news/physically-based-sky-atmosphere-and-cloud-rendering) adds energy-conserving integration and a multiple-scattering approximation; Unreal's Volumetric Cloud component (https://dev.epicgames.com/documentation/en-us/unreal-engine/volumetric-cloud-component-properties-in-unreal-engine) exposes layer bottom/height, tracing sample counts and a view sample scale per quality level.
- Decision: `Environment::clouds` (`VolumetricClouds`: coverage, extinction per metre, bottom/top heights, shape and detail sizes, detail erosion, wind in m/s, anisotropy, sun and ambient multipliers, march distance) describes one flat layer. A fullscreen fragment pass `clouds.frag` runs at render resolution / `RenderSettings::cloud_downsample` into an RGBA16F target after the blended geometry and before volumetric fog is composited. Per pixel it intersects the view ray with the slab, clipped at the farthest scene depth of the pixel's footprint and at `distance`, takes `cloud_steps` samples with an interleaved-gradient-noise offset that changes per frame under TAA, and evaluates density as a 4-octave value-noise fBm (rotated octaves, no textures) thresholded by `1 - coverage × profile(height)` and eroded by a 2-octave detail fBm. Each sample with density marches `cloud_light_steps` towards the sun (no detail noise) and lights the sample with three Wrenninge-style multiple-scattering octaves (weights 1, 0.5, 0.25; extinction 1, 0.3, 0.09; phase anisotropy halved each octave) of a dual-lobe Henyey-Greenstein phase, plus the mean sky radiance (the same SH/gradient estimate the fog uses) darkened towards the base; in-scattering is integrated per step as `T × S × (1 − e^{−σΔ})` (albedo 1). The density fades out over the last 40% of `distance`. `clouds_apply.frag` composites the target with premultiplied alpha at full resolution and leaves pixels whose geometry is nearer than the ray's entry into the layer untouched, so silhouettes in front of the clouds stay sharp; ground seen from above the layer is covered. Tiers: Low off, Medium 1/4 resolution / 32 / 4 steps, High 1/2 / 48 / 6, Ultra 1/2 / 64 / 8. Capture mode (probe bakes) skips clouds. `SceneStats::volumetric_clouds/cloud_width/cloud_height/cloud_steps` and a `volumetric_clouds` render-path feature (scene / capture_mode / quality_tier / setting / unsupported, Reduced below Ultra) report it. `EnvironmentComponent` exposes `clouds`, `cloud_coverage`, `cloud_density`, `cloud_bottom`, `cloud_thickness`, `cloud_size` (detail = 0.15 × size), `cloud_detail`, `cloud_wind`, `cloud_anisotropy`, `cloud_sun`, `cloud_ambient` and `cloud_distance`. Wind drifts the shapes by `wind × SceneRenderer time`, wrapped every 200 km.
- Alternatives: baked tileable Perlin-Worley 3D textures as in HZD (cheaper per sample and more billowy, but needs 3D texture uploads, which the SDL backend's `upload_texture` does not handle yet; revisit with a noise bake); temporal reprojection of the cloud target with 1/16 of the pixels per frame (much cheaper, but needs a history buffer and motion handling — TAA currently averages the jitter); a spherical planet shell (horizon curvature; the flat slab with a distance fade is enough for ground-level and flight views up to tens of km).
- Consequences: scenes get animated cumulus to overcast layers at 1/4–1/2 resolution. Clouds cast no shadows and are not part of the baked physical-sky IBL or reflection probes; they are composited before particles and over blended surfaces by opaque depth (as volumetric fog is); value noise gives softer, less billowy shapes than Perlin-Worley; cost scales with steps × light steps per cloud pixel and is not yet measured on target hardware.

## ADR-0110 — GPU particle trails recorded and built on the GPU

- Status: accepted (2026-11-19)
- Context: GPU emitters (ADR-0097) had no trails, so comets, tracers and magic bolts had to stay on the CPU path (ADR-0085) and its 65 536-particle cap, uploading six vertices per segment every frame. Engines that ship GPU trails keep the history on the GPU: Unity VFX Graph's strips store a fixed number of particles per strip in a ring and render them as a quad strip; Niagara's GPU ribbons build the ribbon from per-particle data in compute and draw it indirectly. The CPU path already defines the behaviour (distance-sampled points, lifetime expiry, width/alpha taper, trails-only).
- Decision: the same emitter fields drive both paths. The renderer gives each trailed GPU emitter a ring of `points` × vec4 (simulation-space position, age) per slot; the slot's count, oldest index and the point count it was recorded with live in the free `meta.yzw` of the 64-byte GPU particle, so no extra per-slot state is needed and a new point count restarts every history (as on the CPU) without dropping particles. `particle_sim.comp` records the birth point and the pre-aged point in the spawn dispatch and one point per frame in the update dispatch (after collision), with the CPU rule: append when moved ≥ `trail_min_distance` (dropping the oldest when full), expire points older than `trail_lifetime`. The update dispatch then writes the slot's strip — (points + 1) edge-vertex pairs, tail to head plus the live head, in `ribbon.vert`'s 48-byte layout with the CPU's width, colour, tangent and v — and collapses unused pairs to zero width on the last point (zero-area triangles), so a static index buffer (two triangles per segment) built once per capacity draws every strip with one `draw_indexed` and no CPU work per frame. The ribbon batch is drawn before the emitter's heads; `trail_billboards` off draws only the ribbons. Memory is bounded by `SceneRenderer::kMaxGpuTrailSegments` (2^18 slots × points, about 38 MB of vertices and 6 MB of indices at the cap): larger emitters get fewer points per particle and none below two; the render-path report marks `gpu_particles` Reduced (budget) and `SceneStats::gpu_particle_trails_reduced` counts them. Bounds grow by the trail's half width (trail points lie inside the existing travel bounds).
- Alternatives: a separate compute pass that compacts live strips and draws indirectly (less vertex work for sparse emitters, but needs indirect-argument plumbing and a second dispatch; revisit if vertex cost shows up in profiles); a vertex shader that reads the rings straight from storage buffers (no ribbon buffer, but a new pipeline layout with vertex-stage storage and duplicated colour/size logic in the vertex stage); a CPU copy of GPU positions (readback latency, defeats the GPU path).
- Consequences: GPU emitters can carry trails at GPU particle counts (e.g. 16 384 particles × 16 points). Vertex work is proportional to capacity × points even when few particles live; ribbons of one emitter are not sorted against each other (same as the CPU path); trails die with their particles and are 3D only like every GPU emitter; local-space trails are stored in emitter space and follow the entity.

## ADR-0109 — Per-tier effect budgets for decals, water and CPU particles

- Status: accepted (2026-11-19)
- Context: decals, water and particles used fixed per-frame caps (1024 decals, 16 water surfaces, no particle cap) on every tier, so a Low device paid the Ultra cost for effects and the render-path report (ADR-0105) could only say `budget`. Unreal's Niagara scales effects per quality bucket with effect-type scalability (max distance, max instances, spawn count scale), and with a significance handler keeps the N most significant instances and culls the rest.
- Decision: `RenderSettings` gains `max_decals` (Low 128, Medium 256, High 512, Ultra 1024), `max_water_surfaces` (Low 4, Medium 8, High and Ultra 16) and `max_particles` (CPU billboards plus ribbon vertices drawn per frame: Low 16384, Medium 65536, High 262144, Ultra 1048576), clamped by `sanitized()` to the renderer's hard caps. Distance is the significance: decals and water keep the nearest, as before. Particle batches are kept whole from the nearest until the next batch would go over; when the nearest batch alone is over it is cut to the budget (ribbon batches are never cut), so a budget always draws something. GPU emitters are not counted, since their cost is their capacity. `RenderPathFacts` gains `particle_batches_in_view`, `particles_in_view` and `particle_budget`, and the decals, water and particles features name the cause of a cut: `quality_tier` when the budget equals the tier preset, `setting` when it was lowered by hand, and `budget` when even the Ultra reference could not hold everything.
- Consequences: Low and Medium devices draw fewer effects in dense scenes, and the report and the viewport's "below ultra" line say why. Dropping a whole far batch can pop when the camera moves; there is no distance fade or per-emitter significance yet, and the simulation still runs for culled emitters (spawn-count scaling would belong in the particle module).

## ADR-0108 — Particle sub-emitters (birth and death events)

- Status: accepted (2026-11-19)
- Context: fireworks, impact sparks and smoke puffs left by embers need one emitter to spawn particles where another emitter's particles end. Unity's Sub Emitters module (Birth, Collision, Death, Trigger, Manual) and Godot's `sub_emitter` with `SUB_EMITTER_AT_END` / `AT_COLLISION` both reference a second emitter and spawn at the parent particle's position.
- Decision: `ParticleEmitterComponent` gains `sub_emitter` (entity reference, remapped by prefabs like every UUID field), `sub_emitter_trigger` (death, birth), `sub_emitter_count` and `sub_emitter_inherit_velocity`. During a CPU emitter's update each death (at the position the particle would reach in its last step) or birth queues an event with its world position and scaled velocity, at most 4096 per update. After the parallel update the system delivers events serially in work order to the target's queue (also at most 4096), so results are bit-identical with or without jobs. On its next update the target spawns `count` particles per event after its own spawns, within its `max_particles`: its own shape sample is moved to the event position and oriented by the target transform, its own speed is added to the inherited velocity, and local-space targets store the result relative to themselves. GPU targets turn the events into spawn records at the start of the step. Targets spawn whether or not they are emitting, like `emit()`, so a target with rate 0 acts only as a sub-emitter. Chains work; a self-reference, a missing entity or an entity without an emitter drops the events, counted in `ParticleStats::sub_emitter_dropped`. GPU emitters cannot be sources, because their particle positions live only on the GPU.
- Consequences: two-stage effects need no script. The target spawns one update after the source event, and collision events are not available (CPU emitters do not collide, GPU emitters cannot be sources).

## ADR-0107 — GPU depth sorting of alpha-blended GPU particle emitters

- Status: accepted (2026-11-19)
- Context: GPU emitters (ADR-0097) drew their instance buffer in slot order. With alpha blending the result depends on draw order, so far particles could cover near ones and the order changed as slots were recycled. Only additive emitters looked correct.
- Decision: a compute shader `particle_sort.comp` runs a bitonic sort of (key, slot) pairs after the simulation, for every visible alpha-material GPU emitter outside capture mode. The key is `0xFFFFFFFF - floatBits(distance² to the eye)` (non-negative floats sort like unsigned integers), so the sort ascends into far-to-near order; dead slots and the padding up to `n = max(256, bit_ceil(capacity))` get the largest key and end up last. Steps with k ≤ 256 run in shared memory in one dispatch, larger merge steps use one global dispatch per j ≥ 256 followed by one shared-memory dispatch for j = 128..1, and a gather pass writes the instances in sorted order into a second buffer that the draw reads. Each step is its own compute pass, because SDL_GPU does not synchronise dispatches inside one compute pass. Pass count is 3 + Σ_{k=512..n}(log2 k − 7); 1024 slots need 8 passes. Additive emitters are not sorted (order-independent). `SceneStats::gpu_particle_sorted_emitters` / `gpu_particle_sort_passes`, `SceneRenderer::read_gpu_particle_draw` and the render-path detail (", N depth-sorted") expose it. Bitonic sorting was chosen over a radix sort because its fixed, data-independent network needs no atomics or prefix sums, and Unity's VFX Graph likewise turns on GPU sorting by default for alpha and premultiplied outputs.
- Consequences: alpha-blended GPU smoke and mist draw back to front within an emitter; cost is O(n log² n) per emitter per view each frame. Separate emitters are still ordered only by batch distance, and particles do not interleave with other transparent geometry. Sorting uses distance to the eye, not view depth.

## ADR-0106 — Script Debugger in Studio play mode (nested frame loop)

- Status: accepted (2026-11-19)
- Context: the Luau source debugger (ADR-0099) only ran in the headless game behind `victus debug-adapter`. Studio play runs scripts inside the UI frame on the UI thread, so a breakpoint there would freeze the window. Moving the game loop to its own thread would touch every play-mode system (physics, audio, animation, networking, the viewport's reads of the play scene) and was not justified for this step.
- Decision: keep the game on the UI thread and stop it with a nested frame loop. `HostOptions::debugger` is on for Studio play. The stop handler installed by `Editor::apply_debugger_to_play()` ends the UI frame that was being built (`FramePump::suspend`, ImGui::EndFrame), runs whole Studio frames through the application's `FramePump::frame` until the user picks Continue / Step Over / Step Into / Step Out, then begins a new UI frame (`FramePump::resume`) so the interrupted frame can finish. The handler runs from `tick_play`, which `Editor::frame()` calls before any panel draws, so the interrupted frame holds no open windows. While stopped, `Editor::frame()` does not tick play, autosave, poll assets or advance previews; the menu bar, toolbar and all panels except the Script Debugger draw inside `ImGui::BeginDisabled`, and shortcuts are off. Stop while stopped is deferred: the call continues without further stops and play stops when `tick_play` returns. Closing the window ends the stop the same way. Opening or closing a project is refused while stopped. `victus_editor --frames N` never waits at a breakpoint for more than N frames. Without a frame pump (headless embedding) stops are counted and never block. The new Script Debugger panel (Window menu, Scripting and Debugging layouts) shows a read-only source view with a clickable breakpoint gutter and the current line, the call stack, locals and upvalues with lazily expanded tables, watches and an evaluate box for the selected frame, and the breakpoint list with conditions and log messages. Breakpoints and the break-on-error choice live in `.victus/breakpoints.json` per project. This follows the in-editor model of Defold's Lua debugger (gutter breakpoints, the game halts at a breakpoint while the editor stays live) and the stopped → stack → scopes → variables flow of the Debug Adapter Protocol, reusing the same `DebugStop` API as the DAP server.
- Consequences: scripts can be debugged where they are written, with the viewport showing the frozen frame. The whole game stops, including physics and audio, as in the headless debugger. The game cannot be stepped one frame at a time from a stop, and the source view is read-only. A game loop on its own thread is still the route to attaching to a running player.

## ADR-0105 — Render-path report for decals, water, particles and probes; water pass lifetime fix

- Status: accepted (2026-11-19)
- Context: the rendering-path report (ADR-0103) did not cover decals, water, particles or reflection probes. These are the passes most likely to be silently missing from a frame: culled, over a fixed budget, never captured, or needing compute.
- Decision: `RenderPathFacts` gains submitted / in-view / drawn counts and budgets for decals (max 1024 nearest) and water (max 16 nearest), CPU particle batches, particles and ribbon vertices, GPU emitters submitted versus simulated, and reflection probes requested / not captured / over budget (max 64) / used, plus draws inside a probe box. `SceneRenderer::add_reflection_probe` now counts rejected probes instead of dropping them silently. `describe_render_path` adds five features: decals, water, particles, gpu_particles and reflection_probes. Their reasons are `scene`, `not_needed` (outside the view), `budget`, and `unsupported` (GPU emitters without compute are not drawn). No tier reason is used, because no tier preset scales these passes today. A third reference scene `effects.vscene` (water pool, two decals, seeded CPU sparks with trails, GPU mist, a probe around a chrome sphere) is added to `victus_reference_scenes`, which requires all five features to be active.
- Bug fixed: the `water_scene_copy` and `water` execute lambdas captured the block-local `water_scene` render-graph handle by reference. The graph runs them after that block ends, so the handle was read from a dead stack slot. In Debug the `std::vector::at` range check threw on the first frame with water (index 2771602000 of 14). Both lambdas now capture the handle by value. A scan of the other block-local `RGTexture`s in `render()` found no other by-reference use.
- Consequences: a missing effect can now be traced to a reason. The effects scene is pixel-identical across runs on lavapipe (FLIP 0), including GPU particles. Per-tier scaling of these passes, and its reporting, is still open.

## ADR-0104 — Deterministic perceptual reference scenes

- Status: accepted (2026-11-19)
- Context: the compare harness (ADR-0102) and render-path report (ADR-0103) had nothing fixed to measure. The perceptual-equivalence handoff (Slice 0) asks for deterministic exterior and interior reference scenes, with software-renderer correctness recorded separately from a high-end hardware reference.
- Decision: a generated sample project `samples/reference_scenes` (`tools/generate_reference.py`, uuid5 names, so regenerating gives identical files) with `exterior.vscene` and `interior.vscene`. Each has a fixed camera, no scripts/physics/particles, and one `Rotator` object for a temporal signal. Exterior covers the sun cascades, physical sky, height + volumetric fog, a 6-step roughness ramp on dielectric and metal spheres, 13 posts with 4 cm rails, stairs and a wall, an emissive bar. Interior covers a closed room with only local light: a shadowed point light, a shadowed spot aimed so the box and cylinder cast onto the back wall, an emissive panel, a FogVolume, a glossy floor. Goldens are lavapipe captures at ultra, 320x180, frames 15 and 30, in `golden/lavapipe_ultra_320x180/`. The CTest `victus_reference_scenes` (label gpu, skipped without `VICTUS_REQUIRE_GPU=1`) compares fresh captures with `--max-flip 0.005 --max-tile-flip 0.01 --min-tile-ssim 0.99 --max-temporal 0.005`, requires the scene's key path features to be `active` (exterior: sun_shadows, volumetric_fog, bloom, ssao, taa; interior: local_lights, local_shadows, volumetric_fog, bloom, ssao), and logs low-vs-ultra FLIP without gating. `VICTUS_UPDATE_GOLDENS=1` rewrites the goldens. Ground truth approved by hand and replaced on purpose follows Unreal's screenshot comparison workflow.
- Tolerances were measured, not guessed. The same driver reproduces the goldens exactly (FLIP 0). Exterior with bloom off gives mean 0.025, worst tile 0.043. Interior with spot shadows off gives mean 0.0013, worst tile 0.019, tile SSIM 0.966, and the limits reject it (exit 4). Low quality gives mean 0.118 (exterior) and 0.215 (interior). A mean-only limit would have missed the spot-shadow regression, which is why worst-tile limits matter.
- Consequences: renderer changes now have a fixed visual regression check. The goldens assume the same rasteriser, so another Mesa or a hardware GPU needs regenerated goldens. There is no high-end reference capture yet, and no per-tier tolerance.

## ADR-0103 — Rendering-path diagnostics with reason codes (accepted 2026-11-19)

**Context.** Slice 1 of the perceptual-equivalence handoff asks for reason codes and output-quality metadata for the existing LOD, culling, render scale, shadows and effects, with honest unavailable states for costs the platform does not expose. `SceneStats` counted work but did not say why a feature was missing: SSAO off because of the tier, a setting override, AO intensity 0 in the environment, or a missing depth pre-pass all looked the same. Once `victus compare` (ADR-0102) reports a difference, the next question is which decision caused it.

**Decision.**
- `victus/render/render_path.hpp`: `RenderPathFacts` (what the renderer saw and decided, filled in `SceneRenderer::render` at the existing decision points, no new policy) and the pure `describe_render_path(settings, facts)` producing a `RenderPathReport`: 18 features (render scale, TAA, temporal/spatial upscale, FXAA, sun shadows, local lights, local shadows, irradiance volume, SSAO, bloom, auto exposure, volumetric fog, LODs, occlusion culling, instancing, motion vectors), each `active`, `reduced` or `off` with a reason (`quality_tier`, `setting`, `scene`, `not_needed`, `replaced`, `requires`, `capture_mode`, `unsupported`, `budget`, `no_history`) and a detail with the output quality (cascades and resolution, SSAO samples and resolution, froxel grid, LOD error, lights kept of visible, atlas tiles).
- The reference is the Ultra preset: cheaper parameters are `reduced`. The reason is `quality_tier` when the value matches the active tier's preset, else `setting`, so user overrides are visible.
- GPU execution cost is reported as unavailable: SDL_GPU exposes no timestamp queries (libsdl-org/SDL#11696, open, milestone 3.6). CPU per-pass cost stays with the profiler (`--profile`, `--trace`).
- Surfaces: `SceneRenderer::path_report()`, `PlayerReport::render_path`, `victus run --render-report F.json` (prints a table and writes JSON), and a "below ultra: ..." line in the editor viewport overlay that names non-tier reasons.

**Alternatives.** A global quality manager deciding features (rejected by the handoff: extend owning systems); free-text log lines (rejected: not machine-readable for CI); estimating GPU time from draw/triangle counts (rejected: not a measurement; the handoff asks for honest unavailable states); Vulkan timestamp queries behind SDL_GPU's back (rejected: SDL_GPU does not expose the VkDevice or command buffers).

**Consequences.** CI and users can see exactly why a frame differs from the Ultra path; the CLI compare test checks low reports SSAO `off/quality_tier` and ultra `active/none` on a real frame. New decision points in the renderer must also fill `RenderPathFacts`, or the report goes stale for that feature.

**Sources.** Perceptual-equivalence handoff Slice 1 (docs/handoff/VICTUS_PERCEPTUAL_EQUIVALENCE_RENDERING.md); SDL GPU query API issue (https://github.com/libsdl-org/SDL/issues/11696); the SDL3 GPU chapter of the Linux graphics stack book (https://github.com/turbofish-pk/linux-graphics-stack-book/blob/main/chapters/part-18-rendering-abstractions/ch81-sdl3-gpu.md).

## ADR-0102 — Perceptual capture/compare harness: FLIP, SSIM, worst tile, temporal error (accepted 2026-11-19)

**Context.** The perceptual-equivalence goal (docs/handoff/VICTUS_PERCEPTUAL_EQUIVALENCE_RENDERING.md, Slice 1) needs a reproducible way to tell whether a cheaper rendering path still looks like the reference. VICTUS only had `assets::image_psnr`, and PSNR tracks pixel error, not visibility. A single average can also hide one broken object in an otherwise correct frame, and a per-frame score cannot see flicker. While building the harness, the first comparison of two identical fixed-frame runs showed they were not pixel-identical: the player never set `SceneRenderer::set_time`, so surface-shader time followed the wall clock.

**Decision.**
- `victus/render/image_compare.hpp`: `compare_images` reports mean, p95 and max LDR-FLIP (NVIDIA's `FLIP.h`, vendored at d3ab02a, BSD-3-Clause, sRGB8 decoded to linear, default 67 pixels per degree), mean SSIM on luma (Wang et al. 2004: 11-tap Gaussian σ 1.5, K1 0.01, K2 0.03, L 255, interior pixels only, as in scikit-image), PSNR, the fraction of pixels with FLIP above 0.1, and the same metrics pooled over ~64 px tiles with the worst tile's rectangle. `compare_sequences` adds a temporal error: the mean |Δtest − Δref| of linear luminance between consecutive frames, worst pair. `flip_heatmap` renders the error map in FLIP's magma map. `check_limits` turns `CompareLimits` into readable failures.
- `victus run --capture-dir DIR --capture-every N` writes every Nth frame of a fixed-frame run as `frame_NNNNN.png`; `victus compare <ref> <test>` takes two PNGs or two folders with matching names, prints per-frame and sequence metrics, writes `--heatmap` and `--json`, and exits 4 when outside `--max-flip`, `--max-tile-flip`, `--min-ssim`, `--min-tile-ssim` or `--max-temporal`.
- The player sets surface-shader time from game time (`sim.time().time`), so animated materials pause with the game and fixed-frame runs repeat exactly.
- No pass/fail thresholds are claimed for quality tiers: they need reference scenes and hardware baselines.

**Alternatives.** PSNR/MSE only (rejected: not perceptual); full SSIM/MS-SSIM only (kept SSIM as a structural second opinion; FLIP models viewing distance and colour, which SSIM on luma does not); HDR-FLIP on pre-tonemap buffers (deferred: the player captures display-referred LDR frames); writing FLIP from the paper (rejected: the reference implementation is small, header-only and permissively licensed); an image-diff library such as pixelmatch (rejected: anti-aliasing heuristics, not perceptual).

**Consequences.** Rendering changes can now be gated on image and sequence tolerances with localized evidence. `victus_cli_render_compare` (GPU) checks that two runs match exactly and that low vs ultra exceeds a tight worst-tile limit with exit 4. Comparison is single-threaded CPU code (FLIP compiled -O2 even in Debug; ~0.7 s per 640×360 frame pair on the CI VM).

**Sources.** FLIP paper and project (https://research.nvidia.com/publication/flip, https://research.nvidia.com/sites/default/files/node/3260/FLIP_Paper.pdf); reference code (https://github.com/NVlabs/flip); SSIM (Wang et al. 2004, https://docs.rs/crate/ssim/0.1.0/source/image-quality-assessment.pdf); scikit-image SSIM (https://github.com/scikit-image/scikit-image/blob/v0.18.0/skimage/metrics/_structural_similarity.py); MS-SSIM (https://www.cns.nyu.edu/pub/lcv/wang03b.pdf).

## ADR-0101 — Editor safe mode after unfinished project openings (accepted 2026-11-19)

**Context.** ROADMAP 6l asks for a safe mode that opens a project after repeated startup failures without running editor scripts or restoring a known-bad workspace or scene. Before this, a project whose startup scene, scripts, assets or autosave crashed the Studio crashed it again on every opening; the only way out was editing files by hand. Godot's recovery mode is the reference: when the editor crashes while opening a project it offers to reopen it in recovery mode, which disables tool scripts, editor plugins, GDExtension addons, automatic scene restoring and running the project, and it can also be started with `--recovery-mode`.

**Decision.**
- Detection: every `Editor::open_project` writes `<project>/.victus/editor_startup.json` with the number of openings in a row that did not finish (`unfinished`, atomic write). The record is removed after `EditorOptions::startup_frames` frames (120, about 2 s), when the project closes or when the Studio quits normally; a crash, hang or kill leaves it. A torn record counts as one. When the count reaches `safe_mode_after` (2; 0 = never) the project opens in safe mode. The count is per project, so one broken project does not affect others, and the safe opening is recorded too, so a project that still crashes in safe mode stays in it.
- Also on request: `victus_editor --safe-mode` (every project this run), launcher Recent > right-click > Open in Safe Mode, Help > Reopen in Safe Mode.
- Safe mode skips everything that runs project content automatically: the startup scene (an empty scene opens instead), the edit-time script host (Inspector script properties), asset re-import, thumbnails, the background project check, autosave recovery offers and autosave writes (copies stay on disk untouched for a normal start) and play mode. Opening scenes, editing, saving and Check Project still work. The editor has no native plugin loading (only the player, `simulate` and `serve` load plugins), so there is nothing extra to skip there.
- A card lists what was skipped and why, with Restart Normally (disabled while there are unsaved changes), Report a problem and Hide; the window title and status bar say Safe Mode. Restart Normally closes and reopens the project with everything on.

**Why not restart the process.** Reopening in-process is enough because nothing that safe mode skipped has run, and it keeps the user's window and layout. The workspace layout is a per-user ImGui file loaded before any project opens, so it is not part of the per-project failure; resetting it remains available through Window > Layout.

**Consequences.** A project that crashes the Studio twice while opening opens in safe mode the third time, with a clear explanation and a one-click way back. Tests: `victus_editor_tests -tc="studio safe mode*"` (2 cases, 71 assertions: record and removal, two unfinished openings switch it on, each skipped item, the untouched autosave, play refused, manual scene opening, Restart Normally, Open in Safe Mode, closing, torn record, `--safe-mode`, `safe_mode_after = 0`). Limits in KNOWN_LIMITATIONS: crashes before a project opens are not counted, a hang that the user waits out still counts after 120 frames as finished, and there is no per-item choice of what to skip.

**Sources.** Godot project manager, recovery mode (https://docs.godotengine.org/en/stable/tutorials/editor/project_manager.html); Godot command line `--recovery-mode` (https://docs.godotengine.org/en/latest/tutorials/editor/command_line_tutorial.html).

## ADR-0100 — Versioned format migrators, per-component versions and `victus migrate` (accepted 2026-11-19)

**Context.** Every VICTUS document carried a `version` field, but readers only compared it with the build's version: an older file could never be upgraded, a renamed component became an unknown component, and a field change inside a component had nowhere to go. ROADMAP 6l asks for explicit versioned migrators with tests for migration, backup, unknown-field preservation and malformed input. Shipped engines version data at two levels: Unreal stores a custom version per system in each package (`FCustomVersionContainer`, `FCustomVersion`) so each serializer upgrades its own data, and Unity keeps renamed fields and types readable with `FormerlySerializedAs` and `MovedFrom`.

**Decision.**
- `victus/core/migration.hpp`: a `migration::Format` is a name, a current version and a chain of `Step{from, summary, apply}` (one step per version). `upgrade(doc)` reads `version` (missing, non-integer or zero is a ParseError; newer than the build is VersionMismatch, "written by a newer VICTUS; this build reads versions 1 to N"), runs the steps in order on a copy and replaces the caller's document only when every step succeeded, so a failed migration changes nothing. It returns a `Report` (from, to, the steps applied). Chains with a gap are rejected when built.
- Formats: `victus.scene`, `victus.prefab`, `victus.project` and `victus.world` load through their `*_format()`. All are still at version 1, so the chains are empty until a format changes; the next format change adds one step instead of new branches in the reader.
- Per-component versions (Unreal's custom-version idea): `SerializerRegistry::set_version(name, version, steps)` and `add_former_name(name, former)` (Unity's `FormerlySerializedAs` for components). Saved components carry `"$version"` when their version is above 1. `scene::migrate_components` renames former names (the current name wins if both are present), runs the component's steps and records one note per change; loading strips `$version` before the component's own reader runs. Data from a newer component version is not read: it stays an unknown component and is saved back unchanged.
- Scenes and prefabs keep the notes (`Scene::migrations()`, `Prefab::migrations`). The first save of a migrated file keeps the original next to it as `<file>.premigration` (`fs::keep_premigration_copy`, written once and never replaced), in addition to the 2 verified generations of ADR-0082.
- `player::migrate_project(dir, write)` scans `victus.project`, `.vscene`, `.vprefab` and `.vworld` files (skipping dot folders, `build` and `node_modules`). Project and world files are upgraded as raw JSON so fields this build does not know survive; scenes and prefabs go through their loaders. `victus migrate <project> [--write]` prints what would change and exits 3 when files need migrating, 1 when a file is unreadable or newer, 0 otherwise; with `--write` it saves them.

**Why not migrate silently on every load and save.** Loading does migrate in memory, but writing is explicit (a save in the editor or `victus migrate --write`), so a project opened by mistake in a newer build is not rewritten, and the original is always kept once.

**Consequences.** Format and component changes now have a tested upgrade path. Tests: `victus_core_tests -tc="migration*"` (chain order, report, newer/missing/invalid versions, failing step leaves the document unchanged), `victus_scene_tests -tc="scene migration*"` (component steps, former names, `$version` written, newer data round-trips, `.premigration` kept once, prefabs) and `victus_export_tests -tc="migrate*"` (report, newer file error, dot folder skipped, write, rescan clean). Limits are in KNOWN_LIMITATIONS: no real document migrations exist yet, prefab overrides are not migrated per field, and tile set, sprite, controller, sequence and graph files keep their own version checks.

**Sources.** Unreal Engine `FCustomVersionContainer` (https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FCustomVersionContainer?lang=en-US) and `FCustomVersion` (https://dev.epicgames.com/documentation/unreal-engine/API/Runtime/Core/FCustomVersion?lang=en-US); Unity `FormerlySerializedAsAttribute` (https://docs.unity.com/en-us/engine/6000.0/script-reference/unityengine/serialization/formerlyserializedasattribute); Unity forum discussion of `MovedFrom` for serialized references (https://discussions.unity.com/t/formerlyserializedasattribute-for-serializereference/878027).

## ADR-0099 — Luau source debugger with breakpoints, stepping and inspection over the Debug Adapter Protocol (accepted 2026-11-19)

**Context.** Scripts could only be debugged with `log.info` and the error overlay; the only debugger was the visual-graph trace view (ADR-0060). Every comparable engine ships source-level script debugging (Godot's GDScript debugger, Unity/Unreal through IDE debuggers, Roblox Studio for Luau). Luau has the needed VM support: `lua_breakpoint` patches bytecode with BREAK instructions that cost nothing until hit, `lua_singlestep` with a `debugstep` callback steps line by line, and `lua_getinfo`/`lua_getlocal`/`lua_getupvalue` inspect frames when chunks are compiled with debug level 2 (Luau C API; Lute's debugger and luau-debugger use the same design).

**Decision.**
- `HostOptions::debugger` (off by default) compiles scripts with debug level 2 and installs the `debugbreak`, `debugstep` and error callbacks. Without it nothing changes and `set_breakpoints` reports why breakpoints cannot verify.
- Engine API in `victus/script/debugger.hpp`: `ScriptHost::set_debug_handler(handler, output)`, `set_breakpoints(path, {line, condition, hit_condition, log_message})` returning resolved `BreakpointState`s (moved to the next line with code, re-applied on every load and hot reload), `set_break_on_error`, thread-safe `request_pause`, `debug_stats`. The handler gets a `DebugStop` (reason, message, frames, locals, upvalues, table children, `evaluate(expr, frame)`, `set_variable`) and returns Continue / StepIn / StepOver / StepOut. The game thread blocks inside the handler; the time spent there is added back to the script call budget.
- Breakpoints are BREAK patches only. Stepping and pause turn on single-step mode at the next top-level call and turn it off when the step ends: measured in the Debug build, single-stepping with a trivial callback made a 3M-iteration loop 4× slower (107 ms vs 439 ms). A step requested from a breakpoint in a call that was not single-stepping patches breakpoints onto every line of every module until it completes; a step that leaves its call stops at the next script line anywhere. Line events are de-duplicated per stack depth.
- Conditions and expressions are compiled with `luau_load` in an environment table of the frame's upvalues and locals, falling back to the function's environment; the `return expr` form is tried first. Hit conditions accept `N`, `==N`, `>N`, `>=N`, `<N`, `<=N` and `%N`. Logpoints interpolate `{expr}`. Uncaught errors stop through the `pcall` error handler while the stack is still intact.
- `victus/script/dap.hpp`: `DapSession` implements the Debug Adapter Protocol requests (initialize, setBreakpoints, setExceptionBreakpoints, configurationDone, threads, stackTrace, scopes, variables, evaluate, setVariable, continue, next, stepIn, stepOut, pause, disconnect, terminate) over a `ScriptHost`; transport and `launch` stay with the application. `breakpoint` events report breakpoints that verify once their script loads. `DapDecoder`/`dap_encode` implement the Content-Length framing.
- `victus debug-adapter` serves DAP on stdio. It keeps the original stdout for the protocol and points file descriptor 1 at stderr, so console logging cannot corrupt the stream. A reader thread feeds a queue. `launch {project, scene, frames, stopOnEntry, saves, noDebug}` opens the headless game of `victus simulate` with the debugger on, then runs it at 60 Hz once `configurationDone` arrives. Script logs and warnings go to the debug console. `tools/vscode-victus` contributes the `victus` debug type to VS Code. Other DAP clients (nvim-dap, Zed, Helix) can launch the same command.
- `ChildProcess::read_bytes` reads exact byte counts for framed protocols.

**Why not a socket server inside the player or editor first.** The protocol logic is reusable and transport-free. Stdio lets editors start it with no port management, and the headless game is deterministic and testable in CI. The Studio's in-process play runs scripts inside the ImGui frame, so blocking there would freeze the editor. That integration needs a game thread or a re-entrant UI loop (see KNOWN_LIMITATIONS).

**Consequences.** Line, conditional and hit-count breakpoints, logpoints, stop on uncaught errors, step over/in/out, pause, call stacks, locals/upvalues/table inspection, watch/hover evaluation and editing locals all work for `.luau` scripts. Tests: `victus_script_tests -tc="script debugger*"` (8 cases, 340 assertions) and `victus_cli_debug_adapter` (end to end over stdio on the 3D template). With the debugger off there is no cost. With it on, breakpoints cost nothing until hit and stepping is slow only while active.

**Sources.** Lute debugger architecture (https://lute.luau.org/cli/debug/ARCHITECTURE.html), Luau C API (https://luau.org/api/), Luau performance notes on breakpoints (https://luau.org/performance/), luau-debugger (https://github.com/sssooonnnggg/luau-debugger), godot-luau-script debugger discussion (https://github.com/Fumohouse/godot-luau-script/discussions/2), Debug Adapter Protocol overview (https://microsoft.github.io/debug-adapter-protocol/overview).

## ADR-0098 — Froxel volumetric fog with shadowed sun, clustered local lights, fog volumes and temporal reprojection (accepted 2026-11-19)

**Context.** VICTUS fog was a per-material distance term (Slice 35.1): it could not be lit, cast no light shafts, ignored shadows and local lights and had no local density. Shipped engines (Assassin's Creed 4, Frostbite, Unreal, Godot 4, HDRP, The Last of Us Part II) all use the camera-aligned froxel volume of Wronski (SIGGRAPH 2014, https://bartwronski.com/wp-content/uploads/2014/08/bwronski_volumetric_fog_siggraph2014.pdf): light and density are evaluated once per froxel by a compute pass, a second pass marches each froxel column from the camera accumulating in-scattering and extinction, and shading looks the result up at the pixel's depth. Hillaire (Frostbite, SIGGRAPH 2015, https://advances.realtimerendering.com/s2015/) made it physically based (scattering/extinction coefficients, phase function) and replaced the naive accumulation by an analytic step that conserves energy at any slice thickness. Godot's fog volumes (https://godotengine.org/article/fog-volumes-arrive-in-godot-4/) add authored density shapes to the same grid.

**Decision.**
- Grid: render-resolution tiles of `RenderSettings::volumetric_fog_tile` pixels (Medium/High 16, Ultra 8; capped at 160×90 columns) × `volumetric_fog_slices` (48 / 64 / 96), view depth distributed quadratically (depth = far·t²) up to `VolumetricFog::distance` (8–1000 m, default 80). Low disables it. Stored as vec4 storage buffers rather than 3D textures because the RHI has no read-write storage-texture binding yet; the composite does its own trilinear fetch (8 loads).
- `fog_inject.comp` (4×4×4 groups): per froxel, at a per-frame R1-jittered depth inside its slice, extinction = exponential height fog (uniform below `height`, exp(−falloff·(y − height)) above) plus up to `kMaxFogVolumes` (8, nearest visible first) oriented boxes with soft edges; scattering = extinction × albedo. In-scattered radiance = sun irradiance × Henyey-Greenstein phase (g = `anisotropy`) × the cascade shadow (one hardware-PCF tap, same atlas and matrices as the forward pass, faded at the shadow distance) + the mean sky radiance (SH band 0 of the environment map, or the analytic zenith/horizon/ground average; the isotropic phase integrates a uniform sky to its radiance) + every clustered local light of the froxel's cluster with the forward pass's attenuation, spot cone and local shadow atlas. Each term has a scale (`sun_intensity`, `ambient_intensity`, `local_light_intensity`). The froxel centre is reprojected with last frame's unjittered view-projection and camera; inside the old grid the result is blended with a trilinear history fetch (`temporal`, default 0.9; 0 = no jitter and no history, deterministic). History is dropped on grid or distance changes, `reset_history()`, frames without fog and capture mode.
- `fog_integrate.comp` (8×8 columns): front to back, slice thickness × 1/cos of the column ray, per slice T·(S − S·e^(−σt·ds))/σt and T ·= e^(−σt·ds) (Hillaire 2015); stores (scattered light, transmittance) at each slice's far edge.
- `fog_apply.frag`: full-screen pass after the blended geometry and water, before particles and TAA; linearises the depth (sky = far end of the grid), interpolates the grid in x/y and in √(depth/far)·slices, and writes (scattering, 1 − T) with premultiplied-alpha blending, i.e. scene·T + scattering.
- API: `Environment::volumetric_fog` (`VolumetricFog`), `SceneRenderer::add_fog_volume(FogVolume)`, `SceneStats::volumetric_fog/fog_froxels_x/fog_froxels_y/fog_slices/fog_volumes`; `EnvironmentComponent::volumetric_*` (reflected, saved) and the new `FogVolumeComponent` ("FogVolume", Rendering; size scaled by the entity transform, density, albedo, edge fade, visible), extracted only while the environment's fog is on; editor Create menu / command palette entry "Fog Volume" with its box as selection bounds. The light and cluster buffers gain compute-read usage.

**Why not ray marching per pixel, or 3D textures now.** Per-pixel marching costs O(pixels × steps × lights) and needs heavy denoising; the froxel grid is O(froxels × lights) independent of resolution (an 80×45×64 grid is 230 k cells against 2 M pixels at 1080p). 3D storage textures would give hardware trilinear filtering in the composite and in particles/transparent shading; they need an RHI extension (read-write storage textures in compute passes), recorded as the follow-up.

**Consequences.** Lit, shadowed fog with light shafts, local light halos and authored fog boxes on Medium and above; a uniform medium matches the analytic solution (tests: within 3/255 of L·T + A·(1−T) at T = e^−1 and e^−2, and with the distance limit). Limits: blended (transparent) surfaces, water and particles are fogged only by what lies behind them (the composite runs after them and uses the opaque depth); no volumetric shadows from the fog itself (self-shadowing) or from particles; fog volumes are boxes only (no ellipsoids or density textures, no noise animation); froxel resolution blurs shadow edges; one tap of cascade and local shadow per froxel (temporal jitter softens it); no GPU timing measured (lavapipe only).

## ADR-0097 — GPU particle simulation with CPU-owned emission, curl-noise turbulence and depth-buffer collision (accepted 2026-11-19)

**Context.** VICTUS particles (Slice 13, ADR-0084/0085) were simulated and billboarded on the CPU and uploaded every frame: fine for a few thousand sparks, too slow and too bandwidth-heavy for the hundreds of thousands of particles of rain, embers, magic or debris that current engines draw. Shipped approaches: Wicked Engine (and the Frostbite/Unity VFX Graph lineage) keep the whole particle life cycle on the GPU with dead/alive index lists and atomic counters, emit in a compute pass, simulate in another and collide against the depth buffer (https://wickedengine.net/2017/11/gpu-based-particle-simulation/); Unreal Niagara splits emitter logic (spawn rate, bursts, lifetime of the emitter) on the CPU from per-particle scripts on the GPU. Turbulence in film and games is commonly curl noise (Bridson, Hourihan, Nordenstam 2007), divergence-free so particles swirl without bunching.

**Decision.**
- Split like Niagara, with the slot bookkeeping kept exact on the CPU: `ParticleEmitterComponent::gpu` switches an emitter to the GPU path. The particle system keeps the existing emission schedule (rate, bursts, cycles, `emit()`), a min-heap of death times and a free-slot stack, and produces spawn records — the initial particle state from the same PCG32 stream and shape sampling as the CPU path, spawn times spread over the step, emitter translation interpolated from the previous to the current transform. Live counts, `status()`, `finished` and conservative bounds (spawn boxes grown by speed·life + ½·(|g| + turbulence)·life² and the drawn extent) therefore stay exact and deterministic with no GPU readback, and the slot of a particle is known before the GPU sees it, so no atomics or append buffers are needed.
- The renderer owns the GPU state per emitter key (64-byte particle per slot plus a 48-byte instance per slot) and runs `particle_sim.comp` in the render graph after depth is complete and before the particle pass: a spawn dispatch writes new records into their slots, pre-aged to the frame clock, then an update dispatch integrates every live slot over the frame and writes its billboard (dead slots collapse to size 0). The particle pass draws `capacity` instances straight from that buffer (vertex + compute-write usage). A new emitter instance, a `reset()` or a capacity change zeroes the state; records already seen (by spawn index) are skipped, dead ones dropped, so a renderer that misses frames catches up. States not submitted for 300 frames are released. GPU emitters are always simulated (also when off screen) but only drawn when their bounds are visible; capture-mode renders (probes) draw without simulating.
- Integration mirrors a C++ reference kernel (`particles::gpu_integrate`/`gpu_billboard`) exactly: substeps of at most 1/30 s (up to 8), semi-implicit Euler, exponential drag, spin, size/colour over life, flipbook frames and velocity-stretched aiming identical to the CPU path. Tests compare GPU readback against the reference.
- Turbulence (both paths): a sum of two octaves of a periodic curl field, each component a cosine of one other coordinate (so ∇·a = 0 exactly), the second octave rotated by an orthonormal matrix and at 2.13× frequency; `turbulence` (m/s²), `turbulence_frequency` (cycles/m), `turbulence_speed` (phase rad/s, wrapped in double so it stays precise for days). CPU emitters with `turbulence = 0` are unchanged.
- Depth collision (`collision`, world-space GPU emitters): a particle projected behind the visible surface by at most `collision_thickness` is moved back onto it along the view ray, the surface normal is rebuilt from neighbouring depth texels, and the normal velocity is reflected with `bounce` and the tangential velocity reduced by `friction`. Off-screen or hidden particles do not collide (the standard screen-space limitation).
- Limits up to `kMaxGpuParticles` (2^20) slots per emitter; `max_particles` now accepts that range (CPU emitters still clamp at 65 536).

**Why not a fully GPU-driven life cycle (dead/alive lists, indirect draws).** It removes the CPU spawn cost but makes alive counts, `finished`, bounds and script queries asynchronous (readback latency) and the result order-dependent across GPUs; the CPU cost here is a few hundred nanoseconds per spawned particle and nothing per live particle. Revisit when spawn rates in the millions per second are needed or for GPU-side events (sub-emitters on collision).

**Consequences.** Simulation and billboarding move off the CPU and the per-frame upload shrinks to the new spawns; GPU emitters stay deterministic and inspectable. Limits: 3D only (the 2D sprite path skips GPU emitters), no trails, alpha particles are not depth sorted (use additive or low-alpha), collision is screen-space, multiple renderers (e.g. two viewports) each simulate their own copy and collide against their own camera's depth.

## ADR-0096 — Geometry occlusion with Steam Audio material transmission, reverb zones and underwater filtering (accepted 2026-11-19)

**Context.** VICTUS audio (miniaudio, ADR-0083 voice management) attenuated spatial sources by distance only: a sound behind a concrete wall was as loud and as bright as one in the open, every room shared one hand-set reverb, and a camera under the new water (ADR-0095) heard the world dry. Shipped approaches: Steam Audio (Valve) traces the direct path against scene geometry and applies per-band transmission from acoustic materials (3 bands centred at 400 Hz, 2.5 kHz, 15 kHz; `IPL_MATERIAL` presets in `core/src/core/phonon.h`), with volumetric occlusion that traces several rays across a source radius; Wwise/FMOD-style engines add authored reverb zones/rooms that crossfade the reverb as the listener moves. The roadmap's dependency gate asked for a small VICTUS-owned ray/query path to be compared before adopting Steam Audio.

**Decision.**
- Geometry: `PhysicsWorld::raycast_all` (Jolt `AllHitCollisionCollector<CastRayCollector>`, sorted, triggers excluded). Audio does not link physics: a new `gameplay::SegmentQuery` scene resource (`gameplay/queries.hpp`) is installed by `physics::bind(scene, world)` and cleared with `bind(scene, nullptr)`; any future provider (navmesh, a baked acoustic mesh) can install the same hook.
- Materials: `AcousticMaterialComponent` ("AcousticMaterial", Audio) with Steam Audio's eleven presets (energy transmission per band, copied from phonon.h) or Custom values; lookup walks to the nearest ancestor with the component, otherwise Generic.
- Occlusion (opt-in `AudioSource.occlusion`, optional `occlusion_radius` for 5 rays: centre plus ±u/±v perpendicular to the listener→source direction): per ray the band energies of all surfaces in between multiply; rays average (unblocked rays count 1). Hits on the listener's or source's own hierarchy are ignored. Amplitudes are √energy. The low band sets the voice gain; the mid/low ratio sets a per-voice first-order low-pass (cutoff solved in closed form so |H(2.5k)|/|H(400)| equals the ratio, clamped 150 Hz–20 kHz) inserted between the sound and its bus group only while needed, with the filter's own 400 Hz loss compensated. Gain and log-cutoff are smoothed (τ = `occlusion_smoothing`, 80 ms); the first trace snaps. A per-update ray budget (`max_occlusion_rays`, 64) is shared round-robin, never-traced voices first.
- Reverb zones: `ReverbZoneComponent` ("ReverbZone", Audio) — an oriented, scaled box with `fade` margin, `decay`, `wet` (send for Sfx/Ambient/Voice), optional `lowpass`, `priority` (then smallest box wins). The zone's weight and character are smoothed (τ = `zone_smoothing`, 0.25 s) and layered on the user's bus settings: send = max(user, w·wet), decay = lerp(user, zone, w), low-pass = min of user/zone/water in log-frequency. Music and Ui are untouched; `bus_*` getters keep returning user values; with no zone the effective values equal the user's exactly.
- Underwater: when `gameplay::query_water` reports the listener below a surface, Sfx/Ambient/Voice blend to `underwater_cutoff` (600 Hz) by smoothstep over the first 0.3 m (`underwater_filter` toggles it).
- Fix found on the way: miniaudio's spatializer bypasses master volume and panning entirely for `ma_attenuation_model_none`, so spatial sources with Attenuation None ignored their volume; VICTUS now runs None as linear with zero rolloff.
- API: `AudioEngine::update(scene, dt)` (the PostUpdate system passes the frame dt), `acoustics()` (zone, weights, effective decay/sends/low-pass, rays, occluded count), `occlusion(entity)`; Luau `audio.acoustics()` and `entity:audio_occlusion()`.

**Why not Steam Audio now.** Its direct-path model is what is adopted (same material data, same volumetric idea), but the SDK adds a ~10 MB binary per platform, its own scene/BVH that must mirror physics, and threading/licensing integration; the VICTUS path reuses Jolt's broadphase and stays a few hundred lines. HRTF, reflections/propagation and baked probes remain the reason to revisit it.

**Consequences.** Occluded sources lose level and brightness by material, partial cover gives in-between results, rooms change the reverb smoothly. Cost is bounded by the ray budget (one Jolt ray per voice per update by default). Limits: transmission only (no diffraction around edges, no reflections/propagation, no portals), thickness is not modelled (each surface counts once), the zone low-pass and reverb are global (one listener), first-order tilt filter. Sources: Steam Audio phonon.h (https://github.com/ValveSoftware/steam-audio/blob/480dd64f513cc8a6437e7d5b9eb0d3f1d30c2fac/core/src/core/phonon.h), Jolt `CastRay` with collectors (https://jrouwe.github.io/JoltPhysicsDocs/5.6.0/class_narrow_phase_query.html), miniaudio spatializer source (`ma_spatializer_process_pcm_frames`).

## ADR-0038 — Blended materials as a sorted sub-pass of the forward pass (accepted 2026-11-17)
- Context: water, glass, decals and glows need alpha and additive blending; the forward renderer only had opaque meshes and separate particle passes.
- Decision: `Material::blend` (`.vmat` `"blend": "opaque" | "alpha" | "additive"`, inheritable by instances). Blended draws skip the depth pre-pass and shadow casting, are sorted far to near by bounds centre, and are drawn at the end of the forward pass (same lighting, fog and coverage uniforms) with depth test on and depth write off. Pipelines are created on first use per blend × skinned × double-sided, and surface shaders get the same variants. Surface shaders also read the interpolated vertex colour (`SurfaceInput::vertex_color`), so meshes can carry per-vertex data for them.
- Consequences: straight (non-premultiplied) alpha; per-object, not per-triangle, sorting — intersecting blended meshes can still order wrongly; no order-independent transparency, refraction or screen-space reflections; blended draws do not appear in SSAO or the depth used by soft particles.

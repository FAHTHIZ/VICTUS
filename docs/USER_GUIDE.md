## Make a game without code

Behaviours are ready-made gameplay components. Add one to an entity in the Inspector (Add Component > Behaviours) and the entity starts acting that way the moment you press Play, in the Studio, the player, headless runs and exported games. Every setting has a tooltip. The quickest way to see them together is the No-Code Platformer template: `victus new MyGame --template nocode`, or pick it on the Studio start screen. It is a full level (running, double jumping, coins, slimes, spikes, pits, a checkpoint, a goal flag, score, lives and a timer) with no scripts in it.

| Behaviour | Add it to | What it does |
|---|---|---|
| Platformer Movement | the player (2D or 3D) | Run with A/D or the arrows, jump with Space; double jumps, coyote time, jump buffering and an optional jump sound. Adds a character controller if there is none. |
| Top Down Movement | the player | Moves in four or eight directions with WASD (2D on x/y, 3D on x/z). |
| Camera Follow | the camera | Follows the player (or any target) smoothly with an offset. |
| Health | anything that can be hurt | Hit points, a blink after a hit, and what happens at zero: destroy, respawn at the last checkpoint, restart the scene or nothing. |
| Hazard | spikes, enemies, kill zones | Hurts what it touches, with knockback. "Stompable" lets the player defeat it by landing on it; "Instant kill" takes all health. |
| Collectible | coins, hearts, keys | Picked up on touch: adds score, heals or counts as an item, with an optional sound. |
| Patrol / Chase | enemies | Walks back and forth, turning at walls (and, with Turn At Ledges, at platform edges), or follows the player within a range. |
| Shooter / Projectile | the player, turrets | Fires on the fire action (left mouse) or automatically; bullets damage what they hit and stop at walls. |
| Spawner | anywhere | Creates copies of a prefab on a timer, up to a limit. |
| Lifetime | effects, bullets | Removes the entity after a time. |
| Checkpoint / Goal | flags | A checkpoint moves the respawn point; a goal wins, loads the next scene or a chosen one. |
| Game Rules | one per scene | Score, lives, an optional time limit and score to win, and the on-screen HUD with win and game-over messages. |

The player is found by the tag "Player" or, if nothing has that tag, by its movement behaviour. Behaviours send events that scripts and graphs can react to with `on_event`: `damaged`, `healed`, `died`, `collected`, `checkpoint`, `score_changed`, `game_won`, `game_lost`, `life_lost`, `spawned`, `fired`, `stomped` and `goal_reached`.

Touch is checked with bounding boxes, not exact shapes, and score resets when a new scene loads (see [Known limitations](KNOWN_LIMITATIONS.md)).

## Scripting

Gameplay scripts are [Luau](https://luau.org) files in `assets/`. A script returns a table; public fields become editable properties in the inspector, and `start`, `update(dt)`, `fixed_update(dt)` and `reload` are called for each entity that has a Script component pointing at the file. Saving the file reloads it while the game runs.

~~~lua
-- assets/scripts/spin_and_jump.luau
local Spin = {}
Spin.speed = 90          -- degrees per second, editable per entity

function Spin:update(dt)
    self.entity:rotate(vector.create(0, 1, 0), self.speed * dt)
    if input.pressed("Space") then
        self.entity:translate(vector.create(0, 1, 0))
        log.info(self.entity.name, "jumped")
    end
end

return Spin
~~~

### Debugging scripts

In the Studio, open Window > Script Debugger (it is part of the Scripting and Debugging layouts). Pick a script, click a line number to set a breakpoint, and press Play. When a script reaches it, the game stops and the panel shows the line, the call stack, locals and upvalues (expand tables), watches and an evaluate box for the selected frame. Continue with F5, Step Over with F10, Step Into with F11 and Step Out with Shift+F11; Stop Game ends play once the stopped call returns. The Breakpoints tab adds conditions and log messages. "Break on errors" stops on script errors before they unwind. The rest of the Studio is read-only while stopped. Breakpoints are saved in the project's `.victus/breakpoints.json`.

`victus debug-adapter` is a Debug Adapter Protocol server: editors start it and debug the project's scripts in the headless game (the same simulation as `victus simulate`). In VS Code, install `tools/vscode-victus` (see its README) and add a launch configuration:

~~~json
{ "type": "victus", "request": "launch", "name": "Debug VICTUS scripts", "project": "${workspaceFolder}" }
~~~

Click in the gutter of a `.luau` file under `assets/` to set a breakpoint. Right-click it to add a condition (`self.health < 10`), a hit count (`5`, `>=3`, `%10`) or a log message (`speed is {self.speed}`). Breakpoints turn solid once their script loads. "Uncaught Errors" stops on script errors before they unwind. While stopped, use step over/into/out, read the call stack, expand locals, upvalues and tables, hover over or watch expressions, and edit locals. Launch options: `scene`, `frames` (stop after N frames), `stopOnEntry`, `saves`. Other editors with DAP support can run `victus debug-adapter` directly. Engine programs can call `ScriptHost::set_debug_handler` with `HostOptions::debugger` set.

### Available globals

Available globals: `scene.find/spawn/destroy/query/count`, `input.down/pressed/released/axis/mouse_*`, `time.delta/now/frame`, `log.info/warn/error`, `events.emit(name, payload?, target?)` and `scene.tagged(query)`. Entities expose `position`, `rotation` (Euler degrees), `scale`, `name`, `parent`, `forward/right/up`, and `get/set/has/remove` for any component as JSON-like tables. Scripts run sandboxed with time and memory limits, so a bad loop reports an error instead of freezing the editor.

Gameplay primitives: add a `Tags` component (`Enemy.Orc, Status.Burning`; `has_tag("Enemy")` matches children) and an `AttributeSet` (`health = 100 [0..max_health]; max_health = 100`). Scripts then use `entity:add_tag/remove_tag/has_tag/tags`, `start_timer(name, seconds, repeat)` (fires `on_event(name, ...)`), `attribute/attribute_base/set_attribute/modify_attribute`, `apply_effect{name, attribute, op = "add"|"multiply"|"override", magnitude, duration, period, tag, stacking, max_stacks}` (duration 0 = instant, -1 = until removed), `remove_effect`, `effect(name)`, `activate_ability{name, cooldown, cost = {stamina = 20}, requires, blocked_by}` (returns ok, reason), `ability_cooldown`, and `add_item/remove_item/item_count/items/give_item`. Implement `on_event(name, payload, sender)` to receive events, timers, `attribute_changed`, `attribute_depleted`, `ability_activated` and `inventory_changed`. All of it is saved with the scene.

Acoustics: tick `occlusion` on an AudioSource so walls between it and the listener make it quieter and duller (set `occlusion_radius` for large sources that can be partly covered). Walls are any physics colliders; add an `AcousticMaterial` (Audio) to choose how much sound passes (concrete and rock block most, wood and glass less, metal lets the bass through; default is Generic). Add a `ReverbZone` (Audio) to a room: inside its box (`size`, rotated and scaled with the entity) the Sfx, Ambient and Voice buses get its `decay`, `wet` send and optional `lowpass`, fading over `fade` metres outside; overlapping zones use the higher `priority`. A listener under water hears the world muffled automatically. Scripts read `audio.acoustics()` (`zone`, `zone_weight`, `underwater`, `decay`, `rays`, `occluded`) and `entity:audio_occlusion()` (`blocked`, `gain`, `cutoff`).

Water: add a `Water` component (Environment) to an entity; its position is the rest surface and `size` the X/Z extent. Tune `wave_height`, `wavelength`, `wave_direction`, `steepness` and `wave_speed` for the swell, `shallow_color`/`deep_color`/`clarity` for the look, and `density`, drags, `damping` and `current` for floating. Rigid bodies lighter than the water float (a 500 kg 1 m cube floats half under) and drift with the current. Scripts use `water.query(position)` (returns `surface`, `depth`, `normal`, `current`, `water` or nil), `water.height(x, z)` and `entity:water_state()` (`water`, `submerged` 0..1, `surface`), and receive `water_entered`/`water_exited` in `on_event` (payload `speed`, `surface`; sender is the water).

### Physics

Physics: add `RigidBody`/`Collider` (3D) or `RigidBody2D`/`Collider2D` (2D) from the inspector's Add Component menu. Scripts get `physics.raycast/raycast2d/overlap_sphere/overlap_box/overlap_circle/overlap_box2d/gravity/set_gravity`, entity `velocity`, `angular_velocity`, `add_force/add_impulse/add_torque/add_angular_impulse`, and the callbacks `on_collision_enter(other, info)`, `on_collision_exit(other)`, `on_trigger_enter(other)` and `on_trigger_exit(other)`. Characters: add `CharacterController` (3D) or `CharacterController2D` (2D) and call `entity:move_character(velocity)` each fixed update, `entity:jump(speed)` (only succeeds when grounded), `entity.grounded`, `entity:character_state()` and, in 2D, `entity:drop_through(seconds?)` to fall through `Collider2D`s marked `one_way`. Tick `top_down` on a `CharacterController2D` for top-down games: it moves on both axes with no gravity and slides along walls. Joints: `Joint` (fixed/point/hinge/slider/distance) and `Joint2D` (weld/revolute/prismatic/distance/wheel) connect an entity to another or to the world, with limits, springs, motors (`entity:set_motor(on, speed)`) and `break_force`; `entity:joint_state()` reports whether it is active or broken. View > Physics Colliders toggles collider wireframes in the editor viewport. For imported geometry set the Collider shape to `convex` (a hull; use it for anything that moves) or `mesh` (exact triangles; static or kinematic level geometry). They use the entity's own mesh (MeshRenderer model or primitive, or a procedural mesh) unless `mesh_asset`/`mesh_index` name another model mesh; `victus check` reports colliders with no geometry. In 2D, `polygon` takes any outline in `points` (concave is fine, edges must not cross) and `chain` is a one-sided line for ground and walls: an open chain is solid on the left of its direction, so draw ground from left to right; a `loop` is solid outside, or inside when `inside` is ticked (cave and arena walls). The collider overlay shows ticks on the solid side. Ragdolls: add `Ragdoll` to a character root and `RagdollBone` to each simulated bone, or call `physics::make_humanoid_ragdoll(scene, root)` to set up 16 humanoid bones with limits; modes are `off`, `kinematic` (bodies follow the animation and push others), `powered` (motors track the animation; `pin_root` keeps the hips on the animation) and `passive` (limp). `blend` mixes animation (0) and simulation (1). Scripts use `entity:set_ragdoll("passive"[, blend])`, `entity:ragdoll_state()` (`valid`, `mode`, `bodies`, `awake`, `center_of_mass`, `velocity`, `pose_error`) and `bone:ragdoll_root()`. Destruction: add `Destructible` to anything with a mesh or collider; a contact or `entity:damage(point, impulse)` at or above `strength` breaks it into `pieces` fragments (the same `seed` always gives the same fragments). Moving objects shatter completely; static walls lose the pieces within `damage_radius` of the hit, and with `support` the pieces no longer connected to the base fall. `debris_lifetime` and `max_debris` bound the loose pieces. `entity:destructible_state()` returns `broken`, `fragments` and `loose`, and `on_collision_enter` info includes the impact `speed` and `impulse`.

### Audio

Audio: add `AudioSource` (clip, bus, volume, pitch, loop, play on start, stream, spatial with min/max distance and rolloff) and `AudioListener` from the inspector's Audio menu; drag a `.wav/.ogg/.mp3/.flac` asset onto the clip field, double-click an audio asset to preview it. Scripts get `audio.play(clip, {volume, pitch, bus, position})`, `audio.set_volume/volume/set_muted/muted(bus)`, `audio.available()` and entity `play_audio/stop_audio/pause_audio/audio_playing`. Buses: `master`, `music`, `sfx`, `ui`, `ambient`, `voice`. Bus effects: `audio.set_lowpass(bus, hz)` / `lowpass(bus)` (2nd-order low-pass; 0 turns it off; Master filters everything), `audio.set_reverb_send(bus, 0..1)` / `reverb_send(bus)` (every bus but Master can feed one shared reverb made of four feedback combs) and `audio.set_reverb_decay(0..0.95)` / `reverb_decay()`. Effects are reset when the scene changes or a play session starts; volumes and mutes are kept. The 3D template sends Sfx to the reverb (`reverb_send` field on the HUD script); the 2D template muffles the music once every coin is collected. Voices: at most 96 sounds are mixed at once (`EngineOptions::max_voices`). Give important sources a higher `priority` (0..255, default 128); when too many play, the lowest-priority, quietest ones go virtual — silent, but still advancing — and resume where they would be once a voice frees up. Sources that are inaudible (muted bus, zero volume, far away) also go virtual. `audio.play(clip, {priority = 200, max_instances = 3})` limits how many copies of a one-shot play at once (the oldest fades out). Reclaimed sounds fade over 10 ms instead of clicking. Set `VICTUS_NO_AUDIO=1` to run without an output device (mixing still happens). The 2D template ships generated jump/coin/music sounds and the 3D crates play impact sounds.

### UI

UI: put a `UiCanvas` on an entity and give its children `UiRect` (anchors, pivot, position, size) plus `UiPanel`, `UiImage`, `UiText` (built-in Inter or a project `.ttf`), `UiButton` (with an `action` string) or `UiLayout`. The canvas is authored at 1280x720 and scales with the window; it draws over 2D and 3D scenes in the player, editor viewport and screenshots. Scripts get `on_click(button, action)` on the button or any ancestor, entity `set_text/text`, `set_visible/visible`, `ui_state()`, and `ui.screen_size/pointer_over_ui/focus/focused/click`. Scroll views: add `UiScroll` (`vertical`, `horizontal`, `offset`, `wheel_step`, `drag_to_scroll`) to a rect; its children are laid out as usual, clipped to the rect and shifted by the offset, which is clamped to the content extent (descendants' bounding box plus `UiLayout` padding, reported as `ui_state().scroll_max`). The mouse wheel scrolls the view under the pointer, dragging more than 8 px scrolls it (and cancels a pressed button), and keyboard focus scrolls the focused child into view. Scripts use `entity:scroll_to(x, y)` and `entity:scroll()` → x, y, max_x, max_y. The multiplayer template's scoreboard is a scroll view. Both templates ship a HUD (Controls button, H toggles the panel); the 2D one counts coins and shows a banner when all are collected.

### Localization

Localization: put one string table per language in `assets/localization/<locale>.vstrings` (for example `en.vstrings`, `fr.vstrings`, `pt-BR.vstrings`):

```json
{ "name": "Français", "strings": { "hud": { "controls": "Commandes", "score": "Score : {score}" } } }
```

Nested objects become dotted keys (`hud.score`). Set a `UiText`'s `key` field to show that key's translation; its `text` stays the fallback and is what the editor viewport shows outside play mode. Scripts use `loc.text(key, params?)` (fills `{name}` placeholders from `params`; an unknown key returns the key itself so it is visible), `loc.has(key)`, `loc.locale()`, `loc.set_locale(code)` (false when there is no table; it lasts for the session, across scene loads), `loc.locales()` and `loc.name(code?)` (the table's `name`). `entity:set_text(...)` shows literal text and clears the key; `entity:set_text_key(key)` switches back to a translated key. Lookups try the current locale, then the project's `default_locale` (`"default_locale"` in `victus.project`, default `"en"`); when that locale has no table the first one in name order is used. Edited tables hot-reload in editor play mode and `victus run` (unless `--no-hot-reload`; exported games do not watch files). The 3D, 2D and multiplayer templates ship `localization/en.vstrings` for their HUD.

The built-in Inter fonts cover Latin (including Latin Extended-A/B), Cyrillic and Greek. Other scripts (CJK, Arabic, Hebrew, Devanagari, Thai, Vietnamese stacked accents) need a project font in `UiText.font`, and there is no text shaping or right-to-left layout, so Arabic and Indic scripts do not render correctly yet. There is no plural or gender selection beyond what a script does with `loc.text` and its own keys.

### Rendering from scripts

Rendering from scripts: `entity:set_material("materials/gold.vmat")` / `material()` swap a MeshRenderer's material asset (nil restores the mesh's own), `set_mesh("sphere")` or `set_mesh("models/ship.glb", index)` / `mesh()`, `set_color(vector, alpha?)` / `color()` tint a MeshRenderer or Sprite, `set_sprite("textures/coin.png")` / `sprite()`, `set_cast_shadows(bool)`, and `set_visible/visible` also hide meshes. Paths resolve through the asset database, so they work in exported games too. Add `MaterialOverrides` (Rendering menu) to scroll or offset one entity's textures and override its emissive glow while sharing a material; scripts use `set_uv_offset(v)`, `set_uv_scroll(v)` and `set_emissive(v|nil, strength?)`.

### Navigation

Navigation: add `NavAgent` (speed, acceleration, radius, stopping distance, avoidance) to any entity and call `entity:set_destination(point)`; VICTUS builds a navmesh automatically from the scene's static colliders and terrains (Recast & Detour), rebuilds it when they change (kinematic bodies carve an upright cylinder) and steers agents along the path with local avoidance (DetourCrowd). Agents with a `CharacterController` walk through the physics character mover, so gravity, steps and pushing still apply. An optional `NavMeshSurface` sets the agent size, step height, slope and voxel size the mesh is built for. Scripts also get `entity:stop()`, `entity:nav_state()` and `nav.find_path/nearest/raycast/random_point/rebuild/available`. View > Navigation Mesh draws the navmesh (and agent paths in play mode) in the editor viewport. The 3D template's companion robot follows you around the obstacles.

### AI

AI: add `BehaviorTree` with a `.vbt` tree (JSON: sequence/selector/parallel, guards, cooldowns, timeouts, waits, blackboard checks and sets, `move_to` on the navmesh, `random_point`, C++ actions or Luau script methods as tasks) and `Perception` (sight cone with line of sight, hearing, memory) to make NPCs patrol, notice `Perceptible` entities and chase them. Window > AI Debugger shows sight cones and a window with the live tree and blackboard; scripts read and write blackboards (`entity:bb_get/bb_set`), read `entity:perception()` and call `ai.report_noise`, and trees hot reload during play. The 3D template's sentry is a working example. See [docs/AI.md](docs/AI.md).

### Cinematics

Cinematics: add `SequencePlayer` with a `.vseq` timeline (JSON tracks for transforms with step/linear/smooth/cubic keys, animation clips, audio one-shots, camera cuts and events) to animate doors, lifts and cutscenes. Scripts call `entity:play_sequence/seek_sequence/stop_sequence`, receive `on_sequence_event`, and sequences hot reload during play. Author them in the editor's Window > Sequencer timeline panel. See [docs/SEQUENCER.md](docs/SEQUENCER.md).

### Terrain

Terrain: Create > Terrain adds a generated `.vterrain` heightfield. Select it and use Window > Terrain Tools to raise, lower, smooth, flatten or paint layers in the viewport (one undo step per stroke; edits are saved with the scene). Scripts can query the ground with `terrain.height(x, z)`, `terrain.sample(x, z)` (height, normal, layer weights) and `terrain.raycast(origin, dir)`. "Add Foliage" in Terrain Tools creates a child whose mesh is scattered over the current paint layer (tune density, slope, height range and draw distance on its Foliage component).

### Input

Input: scripts read named actions instead of hard-coded keys, so keyboards, mice and gamepads (up to four, SDL3 standard layout) all work. Actions live in the `input` section of `victus.project` (created with defaults when absent: `move_x`, `move_y`, `look_x`, `look_y`, `jump`, `fire`, `interact`, `sprint`, `pause`, `help`); each has `bindings` (buttons) or `positive`/`negative` (axes) and an optional `dead_zone` (default 0.2). Controls are key names (`Space`, `W`, `Left`), `Mouse0`–`Mouse2`, gamepad buttons `Pad.South/East/West/North`, `Pad.LeftShoulder`, `Pad.Start`, `Pad.Back`, `Pad.DpadUp`… (aliases `A/B/X/Y/LB/RB/LT/RT/Select/Menu`), and half-axes `Pad.LeftX+`, `Pad.LeftY-`, `Pad.RightTrigger`. Scripts get `input.action/action_pressed/action_released(name)`, `input.value(name)` (−1..1), `input.vector(x_name, y_name)` (clamped to length 1), `input.actions()`, `input.bindings(name)`, `input.rebind(name, {...})` (for the running game), `input.gamepad_connected/gamepad_button/gamepad_axis(pad?)`; raw `input.down/pressed/axis` still work. `victus check` reports unknown controls and `victus simulate --hold Pad.LeftX+` holds a gamepad control headlessly. Gamepad input is carried over the network to the server like keys. In the editor, Edit > Input Actions lists every action: click + Listen and press a key, mouse button, gamepad button or push a stick to bind it (Escape cancels), or type a control name; changes are saved to `victus.project` and apply immediately, even while playing.

### Procedural meshes and helper processes

Procedural meshes and helper processes: `entity:set_mesh_data{positions=, indices=, normals=, colors=, uvs=}` builds a mesh from Luau tables, or from packed buffers with `{vertices=, indices=, layout="position:f32x3,normal:s8x4,color:u8x4", index="u32", encoding="base64"}`; `clear_mesh_data()` and `mesh_data()` complete it. A project can declare helper programs under `"bridges"` in `victus.project` (`{"sim": {"command": ["dotnet", "sim.dll", "serve"], "working_directory": "${project}"}}`); scripts call `local b = bridge.open("sim")` and `b:request({op = "frame"})` to exchange JSON lines. `json.encode/decode`, `require("scripts/lib/util")` and `input.mouse_wheel()` are also available.

### Native plugins

Native plugins add C/C++ (or any C-ABI language) systems and functions without rebuilding the engine: `victus plugins MyGame --new hello` creates `plugins/hello/` with a manifest, a C template, a CMake file and the SDK header; build it with CMake, then `victus plugins MyGame --load` shows what it registers. Scripts call plugin functions with `plugins.call("hello.greet", { who = "world" })` (JSON-compatible arguments and results) and check for them with `plugins.has(name)`. The player, `simulate` and `serve` load plugins at startup, `victus check` reports manifest and dependency problems, and `victus export` ships the libraries next to the pack. Plugins are trusted native code; see docs/PLUGINS.md.

## Regression captures

~~~bash
./build/bin/victus run MyGame --record walk.vcapture          # play normally; input, frame times and state digests are saved
./build/bin/victus simulate MyGame --replay walk.vcapture     # headless check: exit 5 at the first frame whose state differs
./build/bin/victus run MyGame --replay walk.vcapture          # watch the recording replay in the game window
./build/bin/victus simulate MyGame --hold D,Space --frames 600 --record bot.vcapture   # scripted capture for CI
~~~

A capture stores every frame's input (keys, mouse, gamepads), the frame times, the random seed scripts used for `math.random` and a digest of the scene every 60 frames: entity names and transforms, every script's own number, boolean, string and vector fields (fields starting with `_` are left out) and the velocities of moving bodies and characters. Replaying re-runs the game from its first frame with the same input and seed and compares the digests, so a change to scripts, physics or the engine that alters how the game plays fails with the frame where it diverged. When a replay diverges it names the entities that differ, for example `replay diverged at frame 60: Buddy: position (-0.843, 0, 1.343) expected (-1.2961, 0, 1.798); ...` or `Keeper: script.score 11 expected 10` (captures keep the per-entity state behind each digest for scenes of up to 4096 entities). In the editor, the toolbar's Record button (or Play > Record Capture) plays while recording and Stop saves the capture to `<project>/.victus/captures/`; Play > Replay Last Capture / Replay Capture runs one back in the viewport, pausing at the end (Matched) or at the first divergence (Diverged, with the entities in the tooltip and status bar). Captures work offline (not with `--connect`); determinism is only verified on one machine and compiler so far. Runs with a frame count (`victus run --frames N`, `victus simulate`) seed `math.random` with a fixed value unless you pass `--seed`, so they repeat exactly; interactive sessions use a time-based seed.

## Multiplayer

~~~bash
./build/bin/victus new Arena --template multiplayer
./build/bin/victus serve Arena --port 27015                     # dedicated headless server (Ctrl+C stops it)
./build/bin/victus run Arena --connect 127.0.0.1:27015 --name ann   # each player in their own window
./build/bin/victus run Arena --host --port 27015 --name host       # or: host a session and play in it (listen server)
./build/bin/victus simulate Arena --connect 127.0.0.1:27015 --name bot --hold D --frames 600   # headless test client
./build/bin/victus simulate Arena --connect 127.0.0.1:27015 --conditions latency=80,jitter=15,loss=0.05
~~~

### How sessions work

The server owns the game: it runs scripts and physics, spawns a copy of the scene's player template (an entity whose `NetworkIdentity` has `player_template` on) for every client, applies each client's input to that player only, and sends snapshots of every `NetworkIdentity` entity (transform, velocity, script-declared values) 30 times a second, each encoded as millimetre deltas against the last snapshot the client acknowledged (entities the client already knows cost nothing). Clients predict their own player and reconcile with the server, and interpolate everyone else 100 ms in the past. Scripts get `net.role/is_server/is_client/authority/id/connected/local_player/clients/stats`, `net.send(name, value, to?)` with `on_net_message(name, value, sender)`, and entity `set_net/get_net` (replicated values), `has_authority`, `is_local`, `owner`. Clients of a different game or engine build are refused. `--conditions` emulates latency, jitter and loss on either side. Traffic is encrypted and authenticated by default: `victus serve` creates a server key in `<project>/.victus/server.key` and prints its public half (`encrypted; server key 43ae...`); players can pin it with `--server-key <hex>` so nobody can pose as the server, and `victus serve --password <p>` makes players send `--password <p>` (only ever over the encrypted channel). Forged, altered and replayed packets are dropped. `--insecure` on both sides turns encryption off for trusted networks. With `--host` (also on exported games' `victus_player`) a player hosts the session and plays in it: the host's character is simulated by the server with no network delay, shows up as player 0 to everyone, and the session ends when the host quits; use `victus serve` for fair or long-running games. Hosting takes the same `--port`, `--max-clients`, `--key`, `--password` and `--insecure` options as `victus serve`. Dropped connections recover on their own: the server keeps a player's character for 30 s after the connection drops, and the client keeps trying to rejoin for 20 s and gets the same character, score and player number back. Scripts see `client_joined`, `client_dropped`, `client_rejoined` and `client_left` in `on_net_message` on the server.

In the editor, Play > Play as Host (or the toolbar's Play button with Play > Network Mode set to Host) runs Play mode as such a session with you as player 0; Window > Network shows the server key and a ready-to-copy join command, bandwidth graphs, connected players and every replicated entity with its owner and traffic. `victus_editor <project> --host --port 27960 --show network` opens straight into it. Set In-editor clients (Network window, or `--clients 2`) to add up to three more players inside the editor, each with its own world; the toolbar's View menu or Ctrl+1..4 picks which player you see and control.

### Basics

In the editor: Play/Stop runs the scene in place on a copy (edits made during play are discarded), Ctrl+S saves, Ctrl+Z/Ctrl+Y undo/redo, F frames the selection, right-drag orbits, middle-drag pans, the wheel zooms. Drop `.gltf`/`.glb`/`.png`/`.jpg` files into the project's `assets/` folder and press Reimport; drag a model from the asset table into the viewport to instantiate it, or a `.luau` script onto an entity's Script component (double-click attaches it to the selection).

### Prefabs

Prefabs: select an entity in the editor and choose Create Prefab (hierarchy context menu) to save it and its children as `assets/prefabs/<Name>.vprefab`; drag or double-click the prefab to place instances. Changes you make to an instance are kept as overrides (shown in the inspector's Prefab section) when the prefab changes; Apply writes them back to the prefab, Revert discards them and Unpack turns the instance into plain entities. Scripts spawn prefabs with `scene.instantiate("prefabs/crate.vprefab", { position = vector.create(0, 2, 0) })`; in the 3D template, E or the gamepad X button drops a crate.

### Scene transitions

Scene transitions: `scene.load("scenes/level2.vscene", { lives = 3 })` switches to another project scene at the end of the update (it returns `nil, error` for a missing or broken scene), `scene.reload()` restarts the current one, `scene.current()` returns its path and `scene.params()` the table passed to the load. Scripts restart in the new scene; module-level Luau variables carry over. `victus check` and `victus export` report `scene.load` calls that name scenes which do not exist.

### Streamed worlds

Large levels can stream in cells around the player instead of loading at once. `victus world <project> --scene scenes/main.vscene --out worlds/main --cell-size 64` moves the scene's props into grid cell scenes under `worlds/main/`, writes `worlds/main.vworld` and leaves the camera, player, scripts, UI, lights, terrain and anything wider than a cell in the scene, plus a World Streaming entity that names the world (`--dry-run` previews). When the game runs, cells within the world's `load_radius` (96 by default; per cell in the `.vworld`) of the camera load in the background and appear once their textures and models are ready; they leave again past `load_radius + unload_margin`. Add a Streaming Source component to the player (or several entities) to stream around them instead, with `radius_scale` to widen their reach. Changes to streamed entities (moved crates, destroyed props) are kept when their cell unloads and come back with it. `victus check` and `victus export` include every cell.

### Animation controllers

Animation controllers: a `.vanim` file is a state machine for a character's clips — states play a clip or blend several by a parameter (`blend1d`: Idle at 0, Walk at 1.6, Run at 5; `blend2d` for strafing), and transitions switch states when conditions on parameters hold (`grounded` is true, `speed > 0.1`, the `jump` trigger was set), with a cross-fade. Set the Animator's `controller` field to the file (for example `anim/player.vanim`), then drive it by setting parameters — `entity:set_anim_param("speed", 3)`, `entity:anim_trigger("jump")`, or the Animation nodes in visual scripts — and the controller picks and blends the clips (`entity:anim_state()` tells you where it is). `victus check` reports mistakes with the element that has them, controllers hot reload while the game runs, and a broken controller falls back to the Animator's plain clip. The 3D and Multiplayer templates show it end to end: their Vanguard robot uses `assets/anim/characters/vanguard_locomotion.vanim` (Idle, Walk and Run blended by `speed`, then Jump, Fall, Land and Interact states), fed by a few lines in the player script. Window > Animation (or the command palette) opens the Animation window for the selected Animator: it lists the controller's states, the cross-fade progress, the current clip weights and every parameter; press Preview to run the controller in the edit scene, then drag sliders, tick bools, fire triggers or click a state to jump to it (End Preview restores the pose; previews also end on save, play and scene change). Clips that travel can drive the character instead: mark a state `"root_motion": true` and the root node's horizontal travel and turn move the Animator's entity (or, with `apply_root_motion` unticked, are reported by `entity:root_motion()` for the player script to pass to `move_character`). The full format is in [Animation controllers](ANIMATION.md).

Layers: add `"layers"` to a `.vanim` to play a second state machine on part of the body — an upper-body "Shoot" layer masked to `["Spine"]` while the legs keep running, or an `additive` breathing layer on top of everything. Change a layer's strength with its `weight_parameter` or `entity:set_anim_layer_weight("UpperBody", 0.5)`. See [Layers](ANIMATION.md#layers).

Inverse kinematics: add `IKConstraint` to a hand, foot or head to bend its bones toward a target after the animation plays — `two_bone` for arms and legs (with an optional pole entity for the elbow or knee), `chain` for tails and spines, `look_at` for heads and turrets. Point it at an entity or call `entity:set_ik_target(position)` from a script (`nil` turns it off; `entity:ik_state()` reports whether it reached). See [Inverse kinematics](ANIMATION.md#inverse-kinematics). Retargeting: set an Animator's `clip_source` to another model (for example a Mixamo clip pack) to play its clips on this character; bones are matched by name, ignoring prefixes like `mixamorig:` and case. See [Retargeting](ANIMATION.md#retargeting).

Morph targets: faces and shapes exported with glTF morph targets (blend shapes) import with their names and default weights, and their weight animations play, cross-fade and layer like bone animation. From a script call `entity:set_morph_weight("Smile", 0.8)` (or a 1-based index) and read back with `entity:morph_weight("Smile")`; `entity:morph_targets()` lists the names. See [Morph targets](ANIMATION.md#morph-targets).

### Sprite animation

Sprite animation: a `.vsheet` sprite sheet slices one texture into a grid (`columns`, `rows`) and names clips — `{"frames": [0, 1, 2, 1], "fps": 6}` or `{"from": 4, "to": 7, "fps": 12, "loop": false}`. Right-click a texture in the editor's Assets panel and choose "Create Sprite Sheet...", then double-click the sheet to animate the selected entity (a `SpriteAnimator` plays the clip on its Sprite; frames preview while editing). Scripts call `entity:play_sprite("run")`, `entity:sprite_animation()` (clip, frame, finished, ...) and `entity:sprite_clips()`. A Sprite's `uv` field draws one region of a texture by hand.

### Particles

Particles: add `ParticleEmitter` (Effects) for sparks, fire, smoke and dust: rate and bursts, shape (point, sphere, cone, box), speed, gravity, drag, size and colour over life, spin, alpha or additive blending, an optional texture and soft fading into geometry; 2D scenes draw the same emitters as sprites on `layer`. Flipbooks: for a texture laid out as a grid of frames (left to right, then top to bottom), set `flipbook_columns` and `flipbook_rows` (up to 15 x 15) and optionally `flipbook_frames` when the last row is not full. With `flipbook_fps` 0 the frames play once over each particle's life (smoke that thins out, an explosion); a positive `flipbook_fps` loops them at that rate (flickering flames); `flipbook_random_start` starts each particle on a random frame so neighbours do not move in step. Streaks: `velocity_stretch` (seconds) lengthens each particle by its speed times that value along its on-screen motion, for sparks, rain and tracer trails; particles that move toward the camera shorten instead. Trails: set `trail_lifetime` (seconds) to leave a ribbon behind every particle, for comets, tracers and magic bolts. A point is recorded each time the particle moves `trail_min_distance` (up to `trail_max_points`), and points older than the lifetime disappear; the ribbon starts `trail_width` x the particle size wide and narrows to `trail_width_end` and fades to `trail_alpha_end` at its tail. Turn off `trail_billboards` to draw only the trails. A trail texture runs across the ribbon in x and along it in y (top = head). Turbulence: `turbulence` (m/s²) adds a swirling flow that moves particles without clumping them; `turbulence_frequency` sets the size of the swirls (cycles per metre, 0.5 = 2 m eddies) and `turbulence_speed` how fast the flow changes. GPU particles: tick `gpu` to simulate the emitter on the graphics card, for rain, embers, snow or magic with up to about a million particles (`max_particles`). Counts, `particles()`, bursts and resets behave the same; GPU emitters are drawn in 3D only. Trails work on GPU emitters too, recorded on the graphics card with the same settings; an emitter keeps at most 262 144 trail segments (`max_particles` x `trail_max_points`), so very large emitters get fewer points per trail, and none past 131 072 particles (the render-path report says so). Alpha-blended GPU particles are sorted back to front on the graphics card every frame, so smoke and mist layer correctly within one emitter; additive emitters skip the sort because their order does not matter. With `gpu` and `world_space` on, `collision` makes particles bounce off whatever the camera sees (`bounce` 0 stops them, 1 is fully elastic; `friction` slows sliding; `collision_thickness` is how far behind a surface still counts as solid); particles off screen or hidden behind other objects pass through. Sub-emitters: set `sub_emitter` to another emitter entity to make it burst `sub_emitter_count` particles wherever this emitter's particles die (`sub_emitter_trigger` death, for fireworks and impact sparks) or are born (birth, for a puff at every launch). The burst uses the target's own shape, speed, colours and lifetime, oriented like the target entity, plus `sub_emitter_inherit_velocity` times the particle's velocity; give the target a `rate` of 0 so it only fires from events. The source must be a CPU emitter (`gpu` off); the target can be either. Scripts use `emit_particles(n)`, `set_emitting(on)`, `reset_particles()` and `particles()`.

Distance fog (`fog_mode` on the Environment) also covers particles, trails, rain and snow: alpha particles fade to the fog colour and additive ones (fire, sparks) fade out.

### Volumetric fog

Volumetric fog: on the scene's `Environment`, tick `volumetric_fog` for fog that is lit by the sun, the sky and point and spot lights, shows light shafts through gaps in shadowing geometry and glows around lamps. `volumetric_density` is how thick it is (0.02 = objects about 50 m away are mostly hidden; 0.1 = about 10 m), `volumetric_height` is the level below which it is uniformly thick and `volumetric_falloff` how quickly it thins above that (0 = the same everywhere). `volumetric_albedo` tints the scattered light, `volumetric_anisotropy` (0 to 0.95) makes it brighter when looking toward the sun, and `volumetric_distance` (8 to 1000 m) is how far the fog is computed; beyond that geometry and sky keep the last value. `volumetric_sun`, `volumetric_ambient` and `volumetric_local_lights` scale each light source's contribution, and `volumetric_temporal` (0 to 0.98) smooths the fog over frames (0 turns smoothing off). Add a `FogVolume` (Rendering, or Create > Fog Volume in the editor) for extra fog in one place, like mist in a valley or smoke in a room: a box of `size` (scaled by the entity's transform) with its own `density`, `albedo` (colour) and `edge_fade` (soft edges). Up to 8 fog volumes are drawn, nearest first; they only appear while the environment's volumetric fog is on. Volumetric fog needs Medium quality or above (Low turns it off). Transparent surfaces, particles, trails, rain and snow are fogged at their own distance, so a glass pane or a smoke puff in front of a foggy room looks as hazy as its distance suggests; fog does not appear in reflection probe captures.

### Volumetric clouds

On the scene's `Environment`, tick `clouds` for a layer of moving 3D clouds lit by the directional light and the sky. `cloud_coverage` goes from clear (0) through scattered cumulus (about 0.3 to 0.5) to overcast (1). `cloud_density` is how thick each cloud is (higher = darker undersides, less sky showing through). `cloud_bottom` and `cloud_thickness` place the layer in metres of world height (default 1500 m to 3500 m); fly the camera above it to look down on the cloud tops. `cloud_size` is the size of the cloud shapes, `cloud_detail` frays their edges, `cloud_wind` moves them (metres per second), `cloud_anisotropy` brightens clouds in front of the sun, `cloud_sun` and `cloud_ambient` scale the two light sources, and `cloud_distance` is how far away clouds are drawn before fading out. Clouds are drawn at half resolution on High and Ultra and quarter resolution on Medium; Low turns them off. `cloud_shadows` (0 to 1, default 1) is how strongly clouds shade the sun on the ground and other lit surfaces; water, 2D sprites and fog light shafts are not shaded by them yet. Clouds do not appear in reflection probes or the physical sky's ambient lighting, and are drawn behind particles.

### Rain, snow and wet surfaces

On the scene's `Environment`, set `precipitation` to `rain` or `snow`. Drops fill a box `precipitation_radius` metres around the camera (default 15) and stay in place in the world as you move. `precipitation_intensity` (0 to 1) is how much of the quality tier's drop count is used: Low draws 2048 drops at full intensity, Medium 8192, High 16384 and Ultra 32768. `precipitation_wind` (metres per second) slants rain and drifts snow. `precipitation_speed`, `precipitation_size` and `precipitation_opacity` override the defaults (rain falls at 9 m/s, snow at 1.2 m/s; 0 keeps them), and `precipitation_color` and `precipitation_brightness` tint and light the drops. `wetness` (0 to 1) makes lit surfaces look wet: rough materials such as stone, soil and wood get darker and shinier, and anything facing up gets a glossy film; polished metal stays the same. For snow lying on the ground, use the `coverage_*` settings. While it rains or snows, roofs and other opaque geometry above stop the drops and keep the surfaces underneath dry, within about one and a half times `precipitation_radius` of the camera. The quality tier sets how sharp this is (Low 256, Medium 512, High and Ultra 1024 texels, render setting `precipitation_occlusion`; 0 turns it off). `puddles` (0 to 1) fills that share of flat ground with standing water in patches about `puddle_size` metres across (default 3); while it rains, `precipitation_ripples` (0 to 1) sets how strongly drops ripple the water and the wet ground. Rain also splashes where it lands: small crowns appear briefly on the ground and roofs near the camera, about a quarter as many as there are drops; `precipitation_splashes` (0 to 1, default 1) scales them and 0 turns them off. Splashes need the roof occlusion above (they are placed from it), so they disappear when `precipitation_occlusion` is 0.

### Tilemaps

Tilemaps: a `.vtileset` tile set slices a texture into a grid, marks tiles as `solid` or `one_way` (default `collision` plus per-tile `tiles` overrides) and defines autotiling `terrains` — 16 tiles indexed by which side neighbours share the terrain (north 1, east 2, south 4, west 8). Add a `Tilemap` component that names the tile set; painted cells save with the scene, draw through the sprite batch and become static 2D colliders that the 2D character mover stands on. Solid tiles are traced into one-sided edge outlines (`edge_collision`, on by default), so bodies slide across tile seams without catching; turn it off for filled boxes when bodies may start inside solid tiles. One-way tiles are always boxes. Scripts edit maps at run time with `entity:set_tile(x, y, tile|nil)`, `tile(x, y)`, `fill_tiles(x0, y0, x1, y1, tile|nil)`, `clear_tiles()`, `paint_terrain(x, y, "ground"|nil)`, `world_to_tile(point)`, `tile_to_world(x, y)` and `tile_bounds()`; `victus check` validates tile sets. In the editor, right-click a texture → Create Tile Set..., double-click the tile set to give an entity a Tilemap, then paint in a 2D viewport with the Tile Palette (B paint, E erase, R rectangle, T terrain, I pick, X/Y flip; Alt-drag pans; one undo step per stroke).

### Pixel art

Pixel art: right-click a texture and choose "Import Settings..." → Filter "nearest" to keep it crisp (sprites, 2D particles and materials using it sample point-filtered), and tick "Pixel Snap" on the 2D camera so the view moves in whole screen pixels.

Cutout foliage and fences: for a texture used by an alpha-tested material (`alpha_cutoff` > 0), tick "Preserve alpha coverage" in its Import Settings and set the same cutoff (`.meta` `"alpha_coverage_cutoff": 0.5`). The importer rescales the alpha of each mip so the same share of texels passes the alpha test as in the full-size image, and leaves and railings no longer fade away as the camera moves back or zooms out. glTF models do this automatically for the base colour texture of `MASK` materials. Very thin (one-texel) features can still erode at a distance; that is a limit of alpha testing itself.

Texture sharpness at grazing angles: floors, roads and terrain seen at a shallow angle use anisotropic filtering, set by the rendering quality: Low 2x, Medium 4x, High 8x, Ultra 16x. Higher levels keep distant ground textures sharp instead of blurring them to a flat colour, at a small texture-bandwidth cost. Materials with nearest filtering (pixel art) are never filtered this way.

Overdraw view: View > Overdraw View (or "View: Toggle Overdraw View" in the command palette) replaces the 3D viewport with a heat map of how many surfaces are drawn into each pixel: black none, blue one, green two, yellow three, orange four, red five to seven, white eight or more. Opaque, cutout and transparent meshes are all counted, so dense foliage, stacked glass and overlapping walls show up as hot areas. It counts layers before depth testing, so it shows where geometry piles up rather than the exact shading cost; particles and decals are not counted. The setting stays in the editor and is not saved with the project.

### Save history

Scenes, prefabs and `victus.project` are saved as a transaction: the new file is flushed to disk and read back before it replaces the old one, and the two previous good versions are kept next to it as hidden `.<name>.vbak1` and `.vbak2` files. If a file is torn or damaged (for example by a power cut or a sync tool), loading uses the newest good version and logs which one; the damaged file is kept as `.<name>.damaged` on the next save instead of being overwritten. To go back by hand, copy a `.vbak` file over the original. New projects ignore these files in `.gitignore`.

### Save games

Save games: scripts store progress and settings with `save.write("profile", { volume = 0.8 })` / `save.read("profile")`, and capture the whole game with `save.checkpoint("quick")` / `save.restore("quick")`; each script keeps its own data across a checkpoint through `function M:save_state()` / `function M:load_state(state)`. Rigid bodies (3D and 2D) keep their linear and angular velocity across a checkpoint; character controllers, animation, particle and audio playback restart from rest. Files are checksummed, written atomically (flushed to disk and read back before replacing) and recovered from a backup if damaged; raise `save_version` in `victus.project` and register `save.migrate(old_version, fn)` when the saved data changes shape. The 2D and 3D templates quick save with F5 (gamepad LB) and quick load with F9 (RB). Exported games keep saves in the per-user VICTUS folder; editor play mode, `victus run` and `victus simulate` use the project's `.victus/saves` (`--saves <dir>` overrides).

### Hot reload

Hot reload: while `victus run` (unless `--no-hot-reload`) or the editor is running, saving a texture, model (or its `.meta` settings, `.bin` or textures) or audio clip under `assets/` swaps it in within about a second, and scripts reload as before. If a file is saved half-way and cannot be imported, the previous version keeps running and the error is shown. Material (`.vmat`) and surface shader (`.vshader`) edits reload too. Scene and font changes appear the next time the game or project starts; the built-in shaders are part of the engine and are not reloaded.

Background loading: `victus run` (and exported games) load textures and models on worker threads and upload a few megabytes of them per frame, so entering an area with new assets does not freeze the game. An object whose model or texture is still loading is not drawn for those frames (it never appears untextured or white). Runs with `--frames`, `--record` or `--replay` load everything synchronously so screenshots and captures are identical every time; `--sync-assets` does the same for an interactive run.

Memory budget: set `"asset_budget_mb": 512` in the `rendering` section of `victus.project` to cap the GPU memory used by loaded textures and models. When the cap is exceeded, assets not used for about a second (60 frames) are released, oldest first, and load again the next time something needs them. Assets in use are never released, so a scene that needs more than the cap still draws everything. 0 (the default) means no cap.

Texture streaming: set `"texture_streaming": true` in the `rendering` section to keep distant material and decal textures at a lower resolution. Each texture keeps only the detail its on-screen size needs (never below 64 pixels), sharpens as soon as you get closer and lowers half a second after you move away. With `asset_budget_mb` set, streaming also lowers the largest textures in view instead of going over the cap. Textures inside glTF models are not streamed yet.

### Material instances

Material instances: in the Material Editor, Create Instance makes a material that inherits everything from the open one; change only what differs (the `x` next to an overridden field goes back to the parent's value, Detach makes it standalone). In the file this is `"parent": "<uuid>"` plus just the overridden keys, and parents can themselves be instances.

### Surface shaders

Surface shaders: a `.vshader` file holds one GLSL function, `void surface(SurfaceInput i, inout Surface s)`, that runs per pixel before VICTUS's lighting, shadows and post-processing. Read `i.uv`, `i.mesh_uv`, `i.world_position`, `i.view_dir`, `i.vertex_normal`, `i.time` (seconds) and `i.params[0..3]`; change `s.base_color`, `s.alpha`, `s.normal`, `s.metallic`, `s.roughness`, `s.emissive`, `s.occlusion` or `s.unlit`; the material's textures can be sampled again with `texture(u_base_color, i.uv)` (also `u_metal_rough`, `u_normal_map`, `u_emissive`). Create one with Assets > New Surface Shader (or New in the Material Editor's Shader section), pick it for a material there and set its four `params` rows. Shaders compile when first used (glslang/SPIRV-Cross); an error is shown with its file and line, and the mesh keeps drawing with the built-in shader until you fix it. `victus check` and `victus export` compile every shader. The 3D template's spinning cube uses `shaders/energy.vshader`. While playing, `i.time` is game time (seconds since play started), so `victus run --frames` renders the same frames every run; in edit mode it follows the clock.

### Comparing renders

To check that a change (a quality tier, a cheaper effect, a new GPU) still looks the same, capture a frame sequence and compare it with a reference: `victus run <project> --frames 120 --capture-dir ref --capture-every 30`, change something, capture again into `test`, then `victus compare ref test --heatmap diff.png --json report.json`. It prints, per frame, the mean, 95th-percentile and maximum FLIP error (NVIDIA's perceptual metric: 0 = no visible difference, 1 = maximal; `--ppd` sets the viewing condition), SSIM, PSNR, the share of visibly different pixels, and the worst 64-pixel tile so one broken object cannot hide in a good average; for sequences it adds a temporal error that catches flicker and ghosting. `--max-flip`, `--max-tile-flip`, `--min-ssim`, `--min-tile-ssim` and `--max-temporal` make it exit with code 4 when outside tolerance, for CI. The heatmap (black = same, bright = different) shows where the worst frame differs.

For renderer work, `samples/reference_scenes` has two fixed-camera scenes built to exercise the renderer: `exterior.vscene` (sun shadows, sky, fog, a roughness ramp on dielectric and metal spheres, thin posts, bloom) `interior.vscene` (shadowed point and spot lights, an emissive panel, a fog volume) and `effects.vscene` (water, decals, CPU and GPU particles, a reflection probe). The `--render-report` table also lists decals, water, particles, GPU particles and reflection probes, with how many were drawn and why any were left out (outside the view, over the per-frame budget, not captured yet, or no compute shaders). Committed software-renderer goldens sit in `golden/`; the `victus_reference_scenes` test compares fresh renders against them. See the sample README for how to regenerate the goldens on another GPU.

To see why two renders differ, add `--render-report path.json` to `victus run`: it prints every rendering feature (shadows, SSAO, bloom, TAA, upscaling, fog, LODs, occlusion culling and more) as active, reduced or off, with the reason (`quality_tier`, `setting` when you changed it from the tier preset, `scene` when the scene does not ask for it, `budget` when a per-frame limit such as `max_point_lights` dropped something, `requires`, `unsupported`, ...) and its quality (cascades, samples, resolution). The editor viewport overlay shows the same as a "below ultra" line. Decals, water surfaces and CPU particles also have per-tier limits per frame (Low 128 decals, 4 water surfaces, 16384 particles; Medium 256, 8, 65536; High 512, 16, 262144; Ultra 1024, 16, about a million); the nearest are kept, far particle emitters are skipped whole, and the report says which tier or setting cut them. GPU time per pass is reported as unavailable because the graphics layer does not expose GPU timers yet.

## Shipping

Safe mode: if VICTUS Studio crashes, hangs or is killed while opening a project twice in a row, the next opening uses safe mode. The project opens with an empty scene and without running anything from it: no editor scripts, asset re-import, thumbnails, automatic project check, autosave restore or play mode. A card explains what was skipped; open the scene that causes trouble from the Assets panel, fix it, then press Restart Normally. You can also choose safe mode yourself: right-click a recent project > Open in Safe Mode, Help > Reopen in Safe Mode, or start `victus_editor --safe-mode`.

Opening an older project: VICTUS upgrades scenes, prefabs, `victus.project` and world files from older versions as it loads them, and renamed components keep loading under their new names. Nothing is rewritten until you save; the first save keeps the original as `<file>.premigration`. `victus migrate <project>` lists the files that need upgrading and what will change (exit code 3), and `victus migrate <project> --write` saves them all. Files written by a newer VICTUS are refused with a clear message instead of being read wrongly, and components from a newer version are kept unchanged.

Before shipping, `victus check <project>` validates every scene, prefab, material, shader, sprite sheet, tile set, terrain, behaviour tree, sequence, animation controller and script and exits 1 on errors (warnings, such as unknown components or clips a model lacks, do not fail it). Tools and the editor get the same checks as structured diagnostics (severity, category, file, entity, suggested fix) from `player::validate_project` in `victus/player/validate.hpp`.

Ship a game with `victus export` (see [Getting started](GETTING_STARTED.md#export-a-game)); the result runs anywhere the player runs, with no editor or SDK installed. Your project files are plain JSON and assets you own; Apache-2.0 allows commercial use.

### Crash reports and diagnostics

If the editor, the player or `victus` crashes, it writes a plain-text crash report (reason, stack frames, the last log lines) to the per-user diagnostics folder and prints where it is; each run also keeps a session log there. `victus diagnose [project] --out bug.zip` collects the newest reports and logs, system facts and, with a project, `victus.project` and the `victus check` results into one zip for a bug report. Home folder, user name and project path are replaced by `<home>`, `<user>` and `<project>`; `--keep-paths` turns that off and `--no-logs`, `--no-crashes`, `--no-system`, `--no-project`, `--no-validation` leave sections out. Nothing is uploaded. See [Diagnostics](DIAGNOSTICS.md).

For Visual Studio/Xcode generators, binaries are under `build/bin/<Config>/`. See [CMake presets](CMakePresets.json).
